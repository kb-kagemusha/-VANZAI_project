# Context7 利用ルール

最終更新: 2026-04-08

---

## 1. 目的

Context7 は、実装時に最新のライブラリ情報やバージョン別ドキュメントを素早く確認するための補助参照ツールとして利用する。

一方で、本プロジェクトにおける設計判断・正本定義・セキュリティ判断・会計定義・承認ルールの最終根拠にはしない。

---

## 2. 基本方針

- Context7 は参考資料であり、正本ではない
- Context7 で得た情報は、必ず公式ドキュメントまたは現行コードで再確認する
- Context7 の出力を、そのまま本番コードや設計根拠として採用しない
- セキュリティ、認証、個人情報、帳票、会計、承認フローは Context7 依存で決めない
- 本プロジェクトの正本は、常に「現行コード」「既存 DB / migration」「設計書」「公式ドキュメント」の順で確認する

---

## 3. 参照優先順位

実装・調査時の参照優先順位は以下とする。

| 優先度 | 参照先 |
|:---:|---|
| 1 | 現行コード |
| 2 | 既存 DB / migration |
| 3 | プロジェクト設計書・決定ログ |
| 4 | 公式ドキュメント |
| 5 | **Context7** |
| 6 | その他の記事、ブログ、生成結果 |

Context7 は、公式ドキュメントの代替ではなく、公式ドキュメントへ素早く到達するための補助線として使う。

---

## 4. Context7 を使ってよい用途

### 4.1 実装前の一次探索

- FastAPI / Pydantic / SQLAlchemy / React などの最新 API 形の確認
- バージョン差分や deprecated 項目の確認
- 公式 docs の該当トピック特定
- サンプルコードや設定例の入口確認

### 4.2 実装雛形の作成補助

- API ルートの叩き台作成
- フォーム実装の叩き台作成
- migration 記法の一般例確認
- UI ライブラリの基本利用例確認

### 4.3 周辺技術の補助参照

- npm / package 構成の確認
- フレームワーク更新状況の確認
- ドキュメントの版差把握

---

## 5. Context7 を正本にしてはいけない用途

### 5.1 設計判断

- request → master 承認反映ルール
- payout recipient 正本設計
- sales_reports の immutable / supersede ルール
- supplier_type を相手属性に持つか案件関係属性に持つか
- vanzai_manager_id と既存 manager 系カラムの責務分離

### 5.2 セキュリティ判断

- token / PIN 設計
- 身分証アップロード方式
- 保存期間・削除ポリシー
- 権限制御・監査ログ
- 暗号化・署名 URL・ウイルススキャン方針

### 5.3 会計・集計定義

- PL の定義
- 個人成績の算定元
- 確定値 / 見込値の区別
- 遅刻回数の閾値
- payout / invoice のスナップショット定義

### 5.4 移行判断

- 既存カラム廃止の時期
- backfill 戦略
- migration の切り戻し方針
- 互換性維持の期間

---

## 6. 採用前の確認ルール

Context7 の情報を採用する場合は、必ず以下を確認する。

- [ ] 公式ドキュメントと一致しているか
- [ ] 現在固定しているバージョンで動くか
- [ ] 既存コードと schema を壊さないか
- [ ] このプロジェクトの設計方針と矛盾しないか
- [ ] セキュリティ・個人情報・会計に踏み込んでいないか

上記のいずれかが曖昧な場合、その情報は採用せず、設計書または公式 docs を正本として再確認する。

---

## 7. コード利用ルール

- Context7 由来のコードは、そのまま本番へ入れない
- 必ずローカルで動作確認し、既存実装との差分を確認する
- migration・認証・ファイルアップロード・削除処理・権限制御は特に慎重に扱う
- PR には「何を Context7 で参照し、何を公式 docs / 既存コードで確定したか」を明記する
- Context7 由来のコードは、叩き台としてのみ使用する

---

## 8. MCP 利用時の追加ルール

Context7 を MCP 経由で使う場合は、以下を守る。

- 読み取り中心で使う
- 本番 secrets に直接触れさせない
- 書き込み権限を持つ経路へ直結しない
- CI/CD や本番 deploy に自動接続しない
- 外部入力や文脈注入を前提に、常に検証を挟む
- Context7 MCP から返されたコンテンツは、別の AI エージェントへそのまま渡さず、人間または検証ロジックによる確認を経てから利用する

Context7 / MCP は便利だが、参照経路そのものにリスクがあり得るため、便利さより境界管理を優先する。
MCP サーバーから返されたコンテンツは参照情報であると同時に別エージェントへの入力経路にもなり得るため、取得した内容を無検証で中継せず、必ず内容確認または検証処理を挟む。

## 9. このプロジェクトにおける具体適用

### 9.1 使ってよい

| 用途 | 例 |
|---|---|
| FastAPI / SQLAlchemy / Pydantic の最新書き方確認 | `UploadFile`, `Form`, `Annotated` の記法 |
| React フォームやファイルアップロード UI の一般例確認 | useMutation, FormData の使い方 |
| Alembic 記法の一般例確認 | `op.add_column`, `op.create_table` |
| ライブラリの非推奨項目や版差確認 | Pydantic v1 → v2 の差分 |

### 9.2 使ってはいけない

| 用途 | 理由 |
|---|---|
| request 承認フローの最終設計 | 本プロジェクト固有の business logic |
| payout recipient モデルの最終決定 | 移行戦略・backfill・後方互換を含む |
| 個人成績・簡易 PL の算定定義 | 会計定義は正本で確定済み |
| token / PIN の安全性判断 | セキュリティ判断は正本準拠 |
| 身分証ファイルの保持・削除・監査ポリシー | GDPR / 個人情報保護法に踏み込む |
| 本プロジェクト固有の DB 制約や冪等性判断 | 既存 migration と整合が必要 |

---

## 10. 運用上の一文

> Context7 は、最新の書き方や周辺知識を引くための補助ツールとして使う。  
> ただし、設計判断・セキュリティ判断・会計定義・承認ルールの正本にはしない。
