## 登録関数

配置: `src.services.line_push_outbox.enqueue_worker_notice`

```python
enqueue_worker_notice(
    db, *, kind, worker_id, unique_key, text, expires_at,
    context, actor, not_before=None, ack_policy="auto", ack_due_at=None,
) -> EnqueuedNotice
# EnqueuedNotice: id: str, created: bool, status: str, ack_due_at: datetime | None, ack_deadline_revision: int, direct_contact_required: bool
```

- db: 呼出し元のSQLAlchemy Session。中止や回答と同じトランザクションで登録する。関数はcommit/rollbackせず、LINEへ送信しない。業務更新がロールバックされたら登録も残らない。
- kind: 初期対応は `order_cancelled` / `recipient_removed` / `reply_receipt`。通知の停止・再検証・確認要否は種類ごとの共通処理で決める。呼出し元から任意の停止ロジックを渡さない。
- worker_id: 稼働者ID。LINEの宛先IDを業務側で指定しない。送信側が有効な紐付けを検証し、解除・別の紐付けへの変更時は意図しない宛先へ送らない。
- unique_key: 同じ論理通知を識別する文字列。重複制約はkind×worker_id×unique_key。同一内容の再登録は同じid/created=Falseを返し、再送回数や確認状態を初期化しない。同じキーで別内容の登録はエラーにする。
- text: 通知文の保存用コピー。保存後に依頼書を読み直して、別の内容の通知に変えない。
- expires_at: 業務上の送信期限。タイムゾーン付き日時を必須としUTCへ正規化。LINEの再試行キーの有効期間と混同しない。具体的な期限は通知の種類の業務仕様で定める。
- not_before: 最初に送れる日時。省略時は今から。期限後になる指定は拒否する。
- ack_policy / ack_due_at: 確認期限の指定。auto / after_1h / after_2h / next_10 / specificを扱い、specificだけack_due_atを必須とする。確認対象の通知では共通処理が期限を自動設定するため、呼出し側は既定の日時計算を実装しない。受付通知には確認期限を設定しない。
- context: 下表の業務参照。送信直前・再試行時の再確認に使う。対象本人/系列/送付行の所属を登録時にも検証する。
- actor: 監査用の実行者。登録と送信試行/結果/確認を監査記録に残す。

| kind | context | 確認ボタン |
|---|---|---|
| order_cancelled | series_id, version_id, event_key。D-11追加時はcancel_scope/affected_datesも保存 | あり。中止済みを理由に通知を止めない |
| recipient_removed | series_id, version_id, event_key | あり。送付先から外れた状態を伝える |
| reply_receipt | delivery_id, outcome | なし。受諾/辞退の受付結果を伝えるだけ |

不明なkind/不足context/所属不整合/期限不正/同一キーの別内容は登録を拒否し、業務更新とともにロールバックする。

## 確認の期限と本人確認（D-10）

送信期限expires_atと確認期限ack_due_atを別々に持つ。送信の受付・本人の確認・確認期限超過・通知送信失敗を混同しない。

- 「確認しました」があるのはorder_cancelledとrecipient_removedだけ。確認対象の行はack_due_atを必ず持つ。変更版は受諾/辞退が必要なので、この確認ボタンを付けない。reply_receiptにも付けない。
- 日本時間で登録時に確認期限を計算して固定する（統合計画v1.5）。通常は登録から2時間後。0:00〜9:59は「登録から2時間後」と「当日10:00」の遅いほう、21:00〜23:59は翌日10:00。初回送信の受付・送信遅延・再送によって自動延長/再計算しない。送る人は1時間後・2時間後・翌朝10時・日時指定のボタンで明示的に変更できる。
- 中止/送付先除外の操作から対象勤務の開始まで48時間未満なら、確認期限を待たず、登録時点でdirect_contact_required（直接連絡が必要）を立てて運営へ表示する。確認期限そのものも通常の規則で保存し、直接連絡の要否と確認期限超過を別に扱う。対象勤務時刻は業務参照から共通処理で確認する。
- 48時間以上前の通知で確認期限が勤務開始にかかる場合は、開始前に早めて理由を表示・保存する。固定の30分前へ短縮するルールは撤回。既に開始した過去の勤務を期限の上限にしない。
- 期限を変えた人・日時・変更前後・指定方法を追記監査する。自動調整と本人/運営の操作は区別する。変更ごとにack_deadline_revisionを増やす。
- 本人が確認しても、参加日・適用受諾・条件への受諾は変更しない。本人以外の確認を拒否し、二度押しでも確認記録を重複させない。
- 確認期限後の操作でも本人の確認を記録する。本人が「確認しました」を押すと、運営画面の未確認・期限超過・「直接連絡が必要」の対応待ち表示を解消する。中止・除外の業務結果は変更せず、元の緊急判定や既に送信した運営への通知履歴は消さない。
- 確認に使える時間が勤務開始前に残らない場合は、通常の猶予時間を与えたように見せず「直接連絡が必要」と運営へ表示する。勝手に勤務開始後へ延長しない。

### 時刻計算と直接連絡の決定（2026-10-24、統合計画v1.5で訂正）

1. 確認期限は登録時に計算して固定。初回のLINE送信受付時刻を基準に確定し直さず、送信・再送では延長しない。
2. 0:00〜9:59はmax(登録時刻+2時間, 当日10:00)。21:00〜23:59は翌日10:00。それ以外は登録時刻+2時間。
3. 中止・除外操作時に対象勤務の開始まで48時間未満なら、登録と同時に「直接連絡が必要」として運営へ出す。48時間ちょうどはこの即時判定には含めない。確認期限は別に設定し、期限変更や再送で直接連絡の必要性を消さない。
4. 48時間以上前の通知で期限が勤務開始にかかる場合は開始前へ短縮し、希望期限・実際の期限・理由を表示/保存する。旧v0.3の30分前固定は採用しない。
5. 本人の「確認しました」を記録すると、直接連絡を含む未確認の対応待ち表示を解消する。受諾や参加日変更の処理は起こさない。
6. 運営はボタンで期限を変更でき、変更者・変更日時・変更前後・指定方法を監査する。再送や期限変更で確認済みの事実や送信履歴を初期化しない。

| 登録時刻（日本時間） | 既定の確認期限（勤務開始による調整前） |
|---|---|
| 00:00 | 当日10:00 |
| 06:00 | 当日10:00 |
| 08:00 | 当日10:00 |
| 09:30 | 当日11:30 |
| 09:59 | 当日11:59 |
| 10:00 | 当日12:00 |
| 20:59 | 当日22:59 |
| 21:00 | 翌日10:00 |
| 23:59 | 翌日10:00 |

確認に使える時間が勤務開始前に残らない場合も「直接連絡が必要」とする。確認期限を勝手に延長せず、本人への未送信と送信後の未確認を区別する。本人への自動的な繰り返し催促はしない。

## 期限超過を運営へ知らせる

- 未確認が期限を過ぎたら、運営画面で赤く表示し、運営のLINEへ知らせる。稼働者本人へ未確認を理由に自動で何度も送らない。送信失敗の再試行と、未確認者への催促を区別する。
- 運営宛ての期限超過通知も同じline_push_outboxへ登録し、宛先アダプターで運営のLINE連携を解決する。別の送信予定表は作らない。
- 登録は論理キー「元通知ID×確認期限版×期限超過」。同じ期限の同じ通知を二重登録しない。複数の運営へ送る場合も、宛先ごとの一意制約を使う。
- 送信直前・再試行時に、元通知が今も未確認か、期限版が一致するか、期限を過ぎているか、運営の権限/LINE連携が有効かを再確認する。本人確認済み・期限が更新された場合は、古い期限の未送信通知を停止する。
- 本人への送信自体が未完了/結果不明なら、運営には「本人が未確認」だけでなく「未送信/送信結果の確認が必要」として区別して示す。本人の落ち度のように表示しない。
- ④の全員通知・「自分が対応する」・10分後再通知・予定まとめは別の業務イベントとして実装し、同じoutboxと運営宛先の基盤を利用する。③-Bで④の運用処理まで追加しない。

## ③-Cの呼出し

```python
from src.services.line_push_outbox import enqueue_worker_notice
from src.services.line_worker import reply_notice_key

notice = enqueue_worker_notice(
    db,
    kind="reply_receipt",
    worker_id=worker.id,
    unique_key=reply_notice_key(delivery.id, outcome),
    text=receipt_text,
    expires_at=receipt_expires_at,
    context={"delivery_id": delivery.id, "outcome": outcome},
    actor="line-web",
)
# 受諾/辞退と同じdb.commit()で保存する。通知失敗で回答を戻さない。
```

直接送信とoutboxの両方を実行しない。切替は新しく確定する回答から行い、移行前の回答をまとめて再登録しない。
既存 `reply_notice_key(送付行ID, 結果)` のUUID5をそのまま維持する。送信側の再試行でも同じUUIDを使用する。
登録した事実、送信が受け付けられた事実、本人の「確認しました」は別に保存する。確認は新条件への受諾を起こさない。

## 共通基盤の公開条件

- 永続化→送信→再試行で、同じ論理通知を二重生成しない。
- 種類ごとに期限・停止条件を毎回再確認する。受付通知は後日の依頼変更だけを理由に別の結果へ変えない。
- 失敗/結果不明/期限切れ/紐付けなし等を、未処理のまま隠さず運営へ表示する。
- LINEへの送信失敗で業務結果は戻さない。送信側はDBロック・試行状態・同じ再試行キーで複数実行の重複を防ぐ。
- 中止/除外通知の未確認者を運営が確認できる。本人以外の確認操作と、再度押したときの重複記録を防ぐ。
- 運営宛て通知（③-D/④）は同じoutbox基盤を使う宛先アダプターを追加する。稼働者IDと運営IDを混同せず、別の送信予定表を作らない。


## D-11: 一部日程の中止は独立段階

- D-11は決定済み。③-Bの通知基盤を先に固め、その後に「一部日程中止（D-11）」を独立して実装・検証する。③-Bの既存結合試験へ操作の範囲を混ぜない。
- 中止した日は運営の確定と同じ更新で予定から外し、理由を0.51.0のキャンセル記録へ「運営都合」で保存し、中止通知を登録する。D-10の確認を付ける。新条件を受諾するまでも中止日を残すL-26の扱いにはしない。
- 日を減らすだけなら残りの日の受諾は取り直さない。条件変更がある場合は残りの日について新版の受諾を取るが、中止日をその返事待ちで復活させない。
- 開始日時の48時間前まで通常操作で中止可能。開始済みの日は選択不可。48時間を過ぎた未開始日は、責任者権限と本人の了承記録（電話日時・相手）がある場合のみ可能。全体取消の意味（L-34）は維持する。
- 責任者の判定は専用の権限ポリシーへ分離する。D-12が決まるまで、特定ロールを責任者として勝手に許可しない。例外操作は未設定なら拒否する。
- 追加試験は、48時間ちょうど/直前/直後、開始済み拒否、責任者権限/了承記録、即時予定除外、残日受諾不要/必要、運営都合記録と通知の同時保存、二重操作と再構築で復活しないこと。
- 追加確認事項: 48時間制限が一部日程中止だけに適用されるか、発注全体の取消や送付先除外にも適用されるか。別操作で制限を迂回できないよう、D-11の実装前に適用範囲を確定する。
