## 5. 機能ごとの計画

### ⑤ 運営による最終決定（①②の共通基盤）

**推奨案：案件×日付×勤務枠を基本に、募集上限と確定人数を持つ。** 本人の「参加できます」は参加申込として保存し、運営の最終決定まで確定人数へ加算しない。申込人数は上限を超えても受け付けられる。

- 画面では「参加回答あり・運営確認待ち」「参加確定」「見送り」「取消／変更確認待ち」を区別する。名称は画面・LINE・PDFで整合させる。
- 確認待ちの予定は本人にも見せるが、確定勤務と見分けられる表示にする。起床監視は確定した参加だけを対象にする案。
- 運営の確定時に、現在の上限・確定人数・本人の他案件予定・申込版を再確認する。同時操作で最後の1枠へ2人を入れない。
- 上限変更・確定解除・見送りには実行者、変更前後、理由を残す。既に参加確定した人を外す操作を、単なる申込の見送りと同じ操作にしない。
- 新規の募集から段階的に適用する案。既存の受諾済み予定を一括で確認待ちへ戻さない。

**確認が必要：** 上限の単位（日別／勤務枠別／役割別）、確定前の他案件への応募可否、運営確定後の本人による最終確認の要否、既存案件への適用方法。

### ① 別人員の確保

起床未報告の知らせ・運営の起床状況から、「本人へ連絡する」と「別人員を確保する」の両方へ進めるようにする。必要なら連絡と手配を並行できる構成にする。

1. 案件・対象日・勤務時間・不足人数を表示して手配を開始。
2. 当日に他の予定がない稼働者を候補表示し、運営が送る人を選択。
3. 案件名・日付・場所・時間・条件・回答期限を確認して個別に「この案件に参加できますか」と送る。
4. 候補者が参加可否を回答。回答だけで配置せず、⑤の運営決定へ進む。

- 「予定なし」と「出勤可能」は異なる。出勤不可の人は候補から除外し、可否未登録の人には「可否未確認」を表示する案。
- 参加確認待ちの別案件がある人も、当日の候補では区別する。候補抽出時と確定時の両方で再確認する。
- 一斉に全員へ自動送信する方式にしない。送付先の選択、同じ打診の二重送信防止、期限切れ後の回答拒否、枠が埋まった後の打診終了を用意する。
- 再送は当面、運営の明示操作を初期案とする。再送間隔・上限が未決のまま無制限の自動催促を入れない。
- 候補検索・勧誘送信・最終配置に必要な権限をAPIでも確認する。起床通知の受信権限だけで配置変更まで許可しない。

**確認が必要：** 当日予定がない人に限定するか、可否未登録も送付先に選べるか、候補に必要な担当タグ・経験、回答期限と送信可能な時間帯。

### ①⑤ 追加検討：打診時の説明と募集終了の連絡

2026-10-27の本人からの追加要望。通知の対象と基本方針は以下のとおり本人指定を反映する。画面操作・送信実装などの細則は未確定。欠員への代替募集と、通常のイベント募集の両方へ共通適用することを検討する。

目的は、打診された人を返事待ちのままにせず、「参加できます」という回答がそのまま参加確定と誤解されるのを防ぐこと。

**打診時の案内例：**

> 上記の案件に参加できるか教えてください。人数調整で見送りになる場合もあります。結果は改めて連絡しますので、少しお待ちください。

**連絡の推奨対象：**

| 相手の状態 | 運営がメンバーを最終確定し、募集を終了したとき |
|---|---|
| 選んだ人 | 対象日・案件を明示した参加確定と、引き受けへのお礼を個別連絡。確定予定も表示 |
| 「参加できます」と回答したが選ばなかった人 | 今回は参加のお願いがないこと、募集終了、お礼を個別連絡 |
| まだ回答していない人 | 募集終了とお礼、返信不要を個別連絡。回答を待ち続けさせない |
| 参加不可と回答した人（参加確定前） | 回答時に「承知しました。ご回答ありがとうございます。」と返信。募集終了時の通知は省略する |

**参加確定の文面例（選んだ人向け／急な欠員手配の場合）：**

> 参加が確定しました。急なお願いにもかかわらず、引き受けていただきありがとうございます。当日はよろしくお願いします。

通常募集では「急なお願いにもかかわらず」を外し、案件の状況に合わせる。

**募集を充足して終了した場合の文面例（選ばなかった回答者・未回答者向け）：**

> 今回は別の方で対応できることになりました。ご検討・ご協力ありがとうございました。

- 参加不可の回答には、その場で短いお礼を返信する。本人の操作への既存の返信経路を優先し、同じ回答イベントの再受信で二重返信しない。参加確定後の辞退は、初回打診への参加不可回答とは別の欠員対応として扱う。
- 参加確定通知・募集終了通知は、それぞれ対象者1人につき同じ決定で1回とする。選ばなかった参加可回答者と未回答者には終了通知を送り、参加不可回答者には送らない。
- 通知のきっかけは候補のチェックではなく、**運営がメンバーの最終決定と募集終了を確定した時点**にする。送信前に対象者と通数を表示する。
- 5人必要なうち2人だけを確定した段階では、残りの募集は継続する。必要人数未達のまま終了する場合は明示操作と理由を必要とし、「人員が確保できた」という文面は使わない。
- 1人分の枠へ2人を確定しない。必要人数を増やす場合は、上限変更を先に記録してから確定する。
- 募集終了後は元の打診の回答ボタンを終了扱いにし、遅れて押された場合も「募集は終了しました」と返す。確定人数や予定を増やさない。
- 見送り・募集終了は、既に参加確定している人の取消とは分ける。確定済みの人に誤って終了通知を送らない。
- 終了通知は「募集×対象日／枠×募集回×相手×通知種類」で重複を防ぐ。部分的な送信失敗では未送信の相手だけを再送し、メンバー決定や予定更新を巻き戻さない。
- 複数日案件は終了した日・枠を明示する。一部の日がまだ募集中なのに「この案件はすべて終了」と伝えない。
- 決定者の氏名や連絡先は他の候補者へ通知しない。辞退で枠が空いた場合は運営が再募集を判断し、終了した打診を勝手に再開しない。
- テスト時は打診・参加確定・終了通知のすべてをテスト送信制御の対象にする。既存の起床通知オフだけで、これらの送信まで止まると仮定しない。

通知文は短くしつつ、ぶっきらぼう・冷たい印象にせず、協力へのお礼を入れる（本人訂正）。案件名・日付などの案件情報は別に表示し、案内本文へ繰り返して長くしない。追加で確認すること：選定基準をどう案内するか、最終決定と募集終了を同時に行う操作の名称。

### ② 欠員・代替のスケジュール反映

| 操作・状態 | 予定・人数表示の推奨動作 |
|---|---|
| 起床未報告だけ | 元の参加を自動取消しない |
| 運営が欠員を確定 | 対象日の確定人数を減らし、不足枠を表示。元の参加状態は取消理由・履歴付きで残す |
| 代替候補へ打診中 | 欠員は残す。候補を確定人数に含めない |
| 候補が「行けます」と回答 | 運営確認待ちとして表示。欠員はまだ解消しない |
| 運営が代替を最終確定 | 元の欠員との関連を保存し、代替者の予定・確定人数・不足人数を同時更新 |

運営の参加カレンダー、稼働者別カレンダー、本人の予定、起床監視で同じ状態を参照する。複数日案件は対象日のみ変更する。過去の稼働・実績・締め済みの金額は変更せず、途中まで本人が稼働した場合は実績の事実を残す。欠勤理由や支払の扱いを欠員手配から推測して確定しない。

**確認が必要：** 元の人と連絡が取れた場合の復帰・代替取消の判断、途中交代日の人数・請求・支払、運営確定済みの参加を外す際の連絡手順。既存の開始48時間以内の中止ルールとの整合を決める。

### ④ 請求の1人日単価・曜日別単価

**計算の基本：請求対象日ごとの「1人日単価 × 請求対象人数」の合計。** 3日間の人数が異なる場合、一定人数×3日と決め打ちしない。

例：1人日20,000円で、1日目3人・2日目4人・3日目2人なら、20,000円×（3＋4＋2）＝180,000円。人数は9人日であり、実人数9人とは限らない。税の計算・丸めは既存の請求ルールを維持する。

- 基本単価に加えて月〜日の曜日別単価を設定できる入力を設ける。日付へ展開した適用単価を確認できるようにする。
- 見込み表示の人数と、最終請求に使う人数を分ける。**本人の申込数をそのまま請求人数にしない。** 最終人数を運営確定予定・確定実績・顧客との合意のどれで確定するかは要決定。
- 日付・適用曜日・人数・対象者／根拠・単価版・小計を明細として保存し、確定金額はその集計値にする。
- 当日の多少の変動条件は、本人指定どおり当面インセンティブ欄の注意書きで扱う。注意書きから金額を推測して自動加減算しない。
- 実際に請求額へ差額を含める必要がある場合は、明示金額と根拠を保存する。現在のインセンティブ金額欄は非負なので、減額を負のインセンティブへ押し込まない。減額明細が必要かは別途確認する。
- 既存の案件総額は旧方式として保持する。新方式への切替時に元の総額との比較を表示し、既存の確定金額や発行済み請求書を自動再計算しない。

**確認が必要：** 1人日の定義（半日・同日複数枠）、請求対象人数の根拠、祝日の単価、月またぎ・日付またぎ、増減額の扱い。稼働者への支払単価も変更したい場合は別要件として明示する。

### ③ テスト版から正式版へ

**推奨案：テストの履歴を保持し、関連する正式版を新しく作る。** 区分文字列だけを書き換えると、架空の参加回答や送信履歴まで正式扱いになる危険がある。

- 一覧の「正式版を作成」から、対象の日程・条件・請求単価・募集上限・参加候補・取引先をポップアップで確認する。
- コピーするのは案件内容を基本とし、サンプル人員・仮の取引先をそのまま正式へ通さない。正式マスタを確認する。
- テスト時の受諾・出欠・起床報告・代替打診・通知送信済み状態・会計確定額は自動継承しない。正式側で必要な確認を行う。
- 正式な文書番号・PDF・予定を作り、元のテストと関連を残す。正式化だけではLINEを自動送信せず、送付先・文面を確認して別操作で送る案。
- 二重クリックや再実行で同じ正式版を増やさない。テスト／正式の予定を二重計上しない表示・集計条件を定義する。

**確認が必要：** 正式版に候補者だけを引き継ぐか、正式化した元テストを通常のテスト一覧でどう表示するか、過去日や取消済みの依頼を移行対象にするか。発行・締め済みの正式帳票は変更しない。

| E前 | 1人日・祝日・同日複数枠 | 基本は1人×案件×日。例外は合意前に自動計算しない |
| F前 | 正式化の引継ぎ範囲 | 案件内容・候補まで。テストの回答・送信・会計履歴を正式へ持ち込まない |

⑥はこれらの業務判断を待たずに着手できる。

## 7. データ・監査・確認方針

実装時の最小候補は、日別募集枠、日別の参加申込／運営決定、欠員・代替の関連、個別打診と送信履歴、日別請求明細と単価版、テスト元と正式版の関連。既存テーブルの拡張で足りるかは、各段階のDDL作成前に確定する。

- 募集枠の確定処理はDBのトランザクションとロックで上限を保護する。
- 打診・回答・確定・予定の再構築は再実行しても重複させない。通知送信失敗と業務状態の確定を区別する。
- 募集上限変更、欠員登録、候補への送付、本人回答、運営確定／見送り、代替確定、正式化、単価変更、請求金額確定に、実行者・日時・理由・変更前後を残す。監査イベント名は実装段階で確定する。
- LINE専用画面にもAPI認可を設ける。閲覧・連絡・配置変更・請求金額操作をそれぞれ既存の権限設計へ対応させる。

| 機能 | 合格させる主な確認 |
|---|---|
| ⑥ | 文字とアイコンの比率、切替帯と有効な機能の押下範囲（準備中は押せない）、メニュー往復、稼働者専任への非影響 |
| ⑤ | 上限1の最後の枠への同時確定、回答の重複、古い版への返答、他案件との重複、権限剥奪 |
| ①② | 候補抽出から確定までの予定変更、複数人の参加可、欠員取消、途中交代、複数日中1日だけの交代、未回答者を含む終了連絡、参加不可への即時お礼と終了連絡省略、選定者への確定連絡、選んだ人への終了通知誤送信防止、部分確定での早すぎる募集終了防止、終了後の遅い回答、送信失敗・再送・テスト通知オフ |
| ④ | 日別人数の差、曜日別単価、同じ人の重複計上防止、単価改定前後、旧総額の保持、発行・締め後に金額が変わらないこと |
| ③ | 仮マスタの検出、テスト回答の非継承、二重正式化の防止、元PDF・履歴の保持、通知の勝手な送信・正式請求へのテスト混入の防止 |

コード変更の完成ごとに本人指定の版数規則を適用し、両アプリの版表記とCHANGELOGを同期する。⑥の表示修正はPATCH。その他は独立した新しい業務が追加されるかを実装単位で判断する。今回の計画文書だけではアプリ版数・本番配備を変更しない。
