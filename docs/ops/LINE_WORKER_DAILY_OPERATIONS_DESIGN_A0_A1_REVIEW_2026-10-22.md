## 2. 指摘

### D01 [P1] 子アクションを親機能へ対応付けないと、続きとPDFが常に拒否される

対象：設計184–195行、307–319行。

公開記録のenabled_actions例は `wk_wake / wk_orders / wk_schedule`。一方、実際の子ボタンは `wk_next:<token>` と `wk_open:<token>`。すべてのwk_をそのままenabled_actionsへ照合する319行の規則では、両方とも不一致になり、「まだご利用いただけません」と返る。

修正：受信したdataを解析し、子アクションの親機能を判定してから照合する。

| 受信data | 有効判定に使う機能 | 追加の確認 |
|---|---|---|
| wk_next:token | wk_schedule | action=schedule_next、本人、期限、範囲 |
| wk_open:token | wk_orders | action=open_order、本人、期限、対象の閲覧可否 |

トークン自体をenabled_actionsへ登録しない。別actionのトークンを流用できないよう、actionの照合も明記する。

追加試験：A1の通常設定で続きとPDFを開ける／親機能を無効にすると子ボタンも拒否／schedule_nextのトークンをopenへ流用できない。

### D02 [P1] 外された人の旧リンクを無効にする処理は、発行経路にも適用する

対象：設計247–248行、347–351行。DEC-068。

新しい版の確定時に既存PDFトークンを無効にする方針は妥当。ただし「send_oneは変更なし」では、外された人へ旧版の新しいトークンを後から発行できる。

具体例：v1の送付先Aは未回答→v2でAを外して確定→v1の送付行に対してsend_oneを実行。現行コードはv1がconfirmed・未回答・view_revokedでなければ送信でき、現在の回答受付版や最新送付先への所属を確認しない。read_shared_pdfも、修正版から外れたことを判定しないため、新しいURLで旧PDFを開ける。

同時実行でも、v2の無効化処理のあとにv1の送信処理がトークンを作れば、無効化の対象から漏れる。

修正：

- send_one・PDF再発行にも文書ロックとロック後の再照合を適用する。
- 通常送信は回答受付版の対象送付行だけに限定する。
- PDF再発行は、現在も送付先であり、閲覧可能な適用版または回答受付版である場合に限る。変更確認中の残存者が旧適用版を開ける方針は維持する。
- 既存トークンの失効に加え、読み出し側でも、現在の送付先除外・発注中止等を拒否する共通条件を検討する。URLを持つ人に毎回ログインさせる要求ではない。

追加試験：除外後の旧版送信・再発行を拒否／旧版送信と新版確定の競合で有効リンクが漏れない／残った人の旧適用版は開ける。

根拠：`src/services/line_order.py` のsend_one（248–262行付近）、read_shared_pdf（330–352行付近）。

### D03 [P1] 変更確認中の人の辞退を、回答受付版限定では記録できない

対象：設計245行、DEC-063の受諾後辞退。

v1受諾→v2確定・未回答の場合、現在の勤務はv1のchanging。本人が運営へ辞退を連絡しても、v1は回答受付版ではなく、v2はackedではない。「回答受付版でacked」という条件では、どちらの送付行でも辞退記録を作れない。

修正：運営の受諾後辞退は、その人の現在適用されている送付行・参加日状態を対象にする。回答受付版だけに限定せず、文書・本人・適用状態・現在日付・権限・理由をロック後に照合する。0日の状態を追記し、対象の旧予定をcancelledにする。未受諾の新版自体への返答をどう記録するかは区別し、後で新版を受諾した場合の動作も明記する。

追加試験：v1受諾→v2未回答の状態で運営が辞退を記録できる／v1の予定が取り消される／再構築や再送で復活しない。

### D04 [P1] 再構築を、既存予定行のactive状態に依存させない

対象：設計214–235行、A1-14。

新版が未回答の場合、手順6は古い版Pの「activeだった行をchangingへ変える」だけで、Pの参加日状態から行を作っていない。派生予定行がない場合は何も復元されず、Pの参加日が0日へ変わった場合も既存changing行を取り消せない。直近の古いackedを探すだけでは、途中で辞退・送付先除外があった履歴を無視してよいかも決まらない。

同じ依頼書・送付行・参加日状態でも、既存予定行の有無・状態で結果が変わる。これは差分処理の冪等性とは別の問題で、「派生データを元データから決定的に作り直す」という中心方針を満たさない。

修正：

- まず、文書×稼働者の適用送付行、現在の参加日状態、終了・除外・新版への返答を入力として、あるべき予定集合と状態を計算する。
- その集合と既存行を比較し、追加・状態変更・取消を行う。既存行は一意キーとidを維持するために使い、適用の根拠にはしない。
- 適用送付行を独立したポインタ等で保持するか、各版の出来事から一意に導く規則を定める。単に「一番新しいacked」だけへ戻さない。
- cancelledやsupersededを無条件で再有効化しない。現在の適用根拠を確認したうえで更新する。

追加試験：同じ元データに対して派生行なしから復元できる／すでにchangingでも同じ結果／旧適用版の参加日0日を反映／一度除外された人の古い受諾が勝手に復活しない。A1-14の繰り返し呼び出しだけでは、この性質を検証できない。

## 3. DDL・試験へ補う指摘

### D05 [P2 / A1マイグレーション前] 予定行の生成元の組合せも複合FKで保証する

対象：設計103–108、136–144行。

回答受付版・現在参加日状態・workerとの対応は複合FKで保護する案になっている。一方、予定行のdocument_id・version_id・delivery_id・source_state_idは、別々のFKだけでは互いの所属が一致する保証がない。

例えばworkerは正しくても、別文書のversion_idや別送付行のsource_state_idを指す行をDBは拒否できない。

修正：versionとdocument、deliveryとversion、source_stateとdeliveryの組合せも保証する。必要な親UNIQUEを追加するか、冗長列を減らしてJOINで導けるようにする。seqの正数、状態・sourceの許容値、offered_datesとdatesの正規化・不変性をどこで保証するかもDDLとサービスの責務へ分けて明記する。

循環参照のあるFKは、PostgreSQLでの作成順序・制約追加とSQLite試験での扱いまでマイグレーションで検証する。

### D06 [P2 / Webhook改修前] 再送の単位と、業務処理失敗時のHTTP応答を明記する

対象：設計277–294行、A1-19。

イベント単位のcommitとイベントIDの一意挿入は妥当。ただしHTTP 500で「失敗したイベントだけが再送される」とは扱わない。再送されたイベント群に処理済みが含まれても、アプリ側のイベントID記録で再処理を抑止する設計にする。

また、擬似コードはcommit失敗時の処理だけが明示されている。業務処理中のDBエラー・例外、業務上の拒否、返信失敗を分けてHTTP応答と再試行方針を決める。

- 再試行可能な処理失敗：そのイベントをrollbackし、他のイベントは継続。最終的に非2xxとして再送を受けられるようにする。
- 記録可能な業務拒否：拒否結果をcommitして返信する。恒久的に拒否される内容を500で繰り返さない。
- commit後の返信失敗：確定済み業務を巻き戻さず、再操作時に保存済み結果を返す。
- 空eventsのWebhook接続確認は、正常応答を維持する。

追加試験：複数イベントの1件目commit済み・2件目失敗→処理済みを含むイベント群を再送→1件目は重複せず2件目だけ処理される。業務処理中の例外も同じ方針で確認する。

公式仕様は、再送時の重複・順序変化、webhookEventIdでの重複検知を前提にしている。再送自体の到達保証もないため、エラーログの確認手順をRUNBOOKへ含める。[LINE公式・Webhookの受信と再送](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)

### D07 [P2 / 参加日モデルの注記] 合意日を常に提示日の部分集合にしない

対象：設計121行、DEC-065の承認済み増加。

A1の全日受諾は提示日の全部、A1+の部分受諾は提示日の部分集合でよい。ただし、本人申請による増加では、当初の個人不参加日を運営が承認して追加できる。その日も実勤務日なら有効だが、当初提示日の部分集合にはならない。

修正：全状態に共通の上限は対象版の実勤務日とし、初回受諾は提示日を上限、change_approvedは承認内容と実勤務日を上限とする。提示日スナップショットを後から広げて解決しない。A1の実装を止めるものではないが、将来使うモデルの不変条件として修正する。

### D08 [P2 / テスト公開前] テストの隔離範囲を起床報告にも定義する

対象：設計152–167、218、326–333行。

テスト予定を本人のLINEに表示する新方針はDECで確認した。一方、is_testは予定行にだけあり、wake_reportsは本番と共通のworker×日付キー。予定行の除外だけで、テスト操作による書込みまで隔離されるとは限らない。

修正：検証専用の稼働者・LINE主体を用意して通常稼働者と混ぜない方式、または起床報告にも実行区分を設ける方式等を選び、どこまで本番と共通かを明記する。同じ人に正式とテストの予定を持たせるなら、そのときの起床ボタンが本番報告として扱われるかを明示する。is_testだけで完全隔離済みとみなさない。

追加試験：テスト予定が正式の起床一覧・重複判定へ混入しない／テスト用操作が通常稼働者の報告状態を変えない。新しい業務判断が必要な場合も、全機能を増築するより検証専用アカウント方式を先に検討する。

## 4. C5・C6への回答と採用してよい点

- **C5：専用JSON列への変更に賛成。** 個人の日付を共通本文から分離でき、draft_worker_idsと並べた管理は自然。A0で列を追加するマイグレーションを用意し、管理APIの権限・確定後の編集拒否・改訂時コピー・本人以外への非表示を確認する。
- **C6：操作トークン30分・PDF7日は採用可能。** 有効期限だけで認可を代替せず、操作ごとの本人・action・文書状態を再照合する。PDFを毎回ログイン認証へ変える必要はない。
- SQLiteだけで競合合格とせず、PostgreSQL試験を分ける方針は妥当。既存の競合試験基盤を利用できる。
- テスト予定を作る変更、閲覧停止ボタン/APIの撤去、正式送付の扱いは新しいDECが根拠にあるため、以前の計画へ戻す必要はない。

## 5. 次にすべきこと

順序は次を推奨する。A0の着手とA1設計の補正は分けて進められる。

1. **A1の設計を局所修正する。** D01のアクション対応表、D02のPDF発行認可、D03の辞退対象、D04の適用元・期待集合を先に決める。D05のFKをマイグレーション案へ落とす。確定済みの業務要件を再質問しない。
2. **A0を1テーマとして実装する。** excluded_datesと共通日付展開、個人不参加日列・検証・画面を追加。下書きの未入力状態を保存できること、共通本文へ個人日付が漏れないこと、旧確定PDFが変わらないことを確認する。
3. **A1のスキーマと再構築を先に実装する。** 空の試験DBと既存試験データ入りDBへmigrationを適用。FKの不正な組合せをDBが拒否すること、E1〜E7に加えD03/D04の復元・辞退・再追加ケースを通す。LINE接続前に元データから予定が正しく得られる状態を作る。
4. **Webhookと操作を組み込む。** イベント単位commit・重複排除・返信分離、既存のコード紐付け/受諾/辞退を回帰試験。その後に起床・予定・PDFを追加し、D01/D02を含む一連の動作を確認する。
5. **PostgreSQL競合試験と画面・公開確認を完了する。** 受諾対取消、新版確定対旧版受諾、PDF発行対送付先除外、同時起床報告、同じWebhook再送を確認する。権限・staff-mobileの案内・テスト隔離も確認する。競合試験のskipを合格として扱わない。
6. **リリースを行う。** A0はZ、A1の日次業務公開はYという判定を維持し、両アプリの版・CHANGELOGを更新。AGENTS.mdのテスト→commit→push→02_app_deploy.sh→動作確認へ進む。リッチメニューの適用は、API・DB・画面が動くA1の公開工程の最後に行う。

A1全体の実装開始判定は、D01〜D04の修正と、それぞれに対応する追加試験が設計へ載った時点で行える。次のレビュー対象は計画全体ではなく、修正した処理表・DDL・再構築関数と試験結果に絞る。
