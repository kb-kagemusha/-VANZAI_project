## 0. この文書で決めること

DEC-065 で方針が決まっている「送付先ごとの参加日」のうち、A1 で作らなかった2つの経路を作る。

| 経路 | 内容 | 状態 |
|---|---|---|
| 1. 作成時の個人の不参加日 | 運営が依頼書の作成時に入力 | 実装済み（0.46.8） |
| **2. 日付を選んでの受諾** | 依頼書ごとに許可した場合、本人が参加する日を選んで受諾する。受諾した時点で確定 | **この計画** |
| **3. 受諾後の参加日の変更依頼** | 本人が公式LINEからいつでも依頼する。運営が承認・却下する | **この計画** |
| 4. 受諾後の辞退（運営の記録） | 運営が理由付きで記録 | 実装済み（0.47.0） |

§9 に、決めたこと（P-01〜P-05、2026-10-22 ユーザー回答）をまとめる。

## 1. 結論（要約）

1. 依頼書に「日付を選んで受諾できる」のチェックを追加する（初期値はオフ。全日程の参加が必要な案件があるため）。
2. チェックがオンの依頼書は、公式LINEのボタンが「全日程で受諾」「日付を選んで受諾」「辞退」の3つになる。日付を選んで受諾すると、その日だけが稼働予定になる。
3. 受諾後は、⑤受託済みの発注依頼書から「参加日の変更を依頼」できる。運営が管理画面で承認すると稼働予定が変わり、結果を本人へLINEで知らせる。承認されるまでは元の予定のまま。
4. 日付を選ぶ画面は、**依頼書の期間のカレンダーを出し、日付をタップして選ぶ**。LINEの中で開く小さなWeb画面（LIFF：LINEの中で動くWebページの仕組み）で作る（P-01）。
5. 変更依頼の受付は、運営へ公式LINEで知らせる。受け取る人は新しい権限「参加日の変更依頼の連絡受け取り」で役割ごとに決める（P-02）。
6. 運営は管理画面の **参加カレンダー** で、イベント（依頼書）ごとに、日ごとの参加OKの人数を見る（P-03）。必要人数の入力は作らない。
7. 版は、日付を選んでの受諾と参加カレンダーで **0.48.0**、変更依頼は統合計画の順番で決める（統合計画 v1.0 の③-D。番号は反映時に決める。どちらも Y）。

## 2. 前提（A1までの仕組みで使うもの）

- 送付行の **提示日**（`offered_dates`）：確定時に「実勤務日 − 個人の不参加日」で固定済み。
- **参加日の状態**（`delivery_participation_states`）：追記だけの履歴。source に `partial_accept`・`change_approved` が既に定義済み。`change_request_id` の列も用意済み。
- 稼働予定は、適用送付行と現在の参加日の状態から、再構築関数で作り直す（A1と同じ。今回も稼働予定を直接書き換えない）。
- 系列の行ロックで、受諾・承認などを直列化する（A1と同じ）。

**データの増え方は「状態の追記」と「変更依頼の表」の2つだけ**で、稼働予定の作り方は変えない。

## 3. 経路2：日付を選んでの受諾

### 3.1 依頼書の設定

| 項目 | 内容 |
|---|---|
| 画面 | 稼働時間の詳細の下に、チェック「日付を選んで受諾できる（一部の日だけの参加を認める）」 |
| 保存先 | `order_request_versions.allow_partial_accept`（真偽値、初期値 false）。確定後は変えない（修正版で変える） |
| 条件 | 提示日が2日以上ある送付先にだけ「日付を選んで受諾」を出す（1日だけなら全日程と同じ） |
| 本文・PDF | 「■受諾の方法　日付を選んで受諾できます」を表示する（共通の文面。個人の日付は載せない） |

### 3.2 公式LINEの流れ

1. 送付の Flex メッセージのボタンを「全日程で受諾」「日付を選んで受諾」「今回は辞退します」の3つにする（許可がない依頼書は今までどおり2つ）。
2. 「日付を選んで受諾」→ 日付を選ぶ画面（§5）が開く。提示日だけが選べる。
3. 1日以上選んで「この日で受諾」→ 確定。返信：「受諾しました。あなたの稼働日：11/1、11/3」。
4. 0日を選んだ状態では受諾できない（辞退は辞退ボタンで）。

### 3.3 サーバーの処理（受諾）

系列のロックの中で、A1の受諾と同じ確認（回答受付版か、本人か、未回答か）をしたうえで：

- 選んだ日が **提示日の部分集合** で1日以上 → 参加日の状態を追記（source=`partial_accept`）→ 適用送付行を更新 → 再構築。
- 全部の日を選んだ場合も `partial_accept` として記録する（本人が選んだ事実を残す）。
- **二重送信の防止（統合 R-06）**：画面が送信ごとに作る冪等キーを、（本人, 操作＝日付指定の受諾, 送付行）と選んだ日のハッシュに結び付けて保存する。同じキーの再送には最初の結果（受諾済み・稼働日）を返す。同じキーで内容が違えば拒否する。
- 許可のない依頼書に日付指定の受諾が届いたら拒否する（古い画面・不正な送信への備え）。

### 3.4 運営の画面

送付状況の表の「返事」に「受諾（一部：11/1、11/3）」と出す。依頼書の画面には、その依頼書の期間のカレンダー（§3.5 と同じ表示）を出す。

### 3.5 参加カレンダー（運営、P-03）

運営が、イベントごとに **日ごとの参加OKの人数** を一目で把握するための画面。

| 項目 | 内容 |
|---|---|
| 場所 | 管理画面の運用メニューに「参加カレンダー」を追加。依頼書の画面にも、その依頼書の期間だけの小さいカレンダーを出す |
| 表示 | 月のカレンダー。日ごとに、その日に稼働日があるイベント（依頼書）を並べ、「案件名　参加OK 3人／未回答 1人」と出す |
| 参加OK | 回答受付版で受諾済みで、その日の稼働予定がある人（一部の日だけ受諾した人は、その日を選んだ場合だけ）。**人数は「系列 × 日付 × 稼働者」で重複を除いて数える**（稼働予定は勤務グループごとの行なので、1日に2つの時間帯がある人を2人と数えない。V3-08） |
| 参加OK・変更確認待ち | 旧い版で受諾済み（適用送付行が旧い版）、新しい回答受付版はまだ未回答の人。**旧い版の参加日**で数える（統合 R-07）。参加OKとは別に表示し、足し合わせても同じ人が2回数えられない |
| 未回答 | **今有効な受諾がなく**、回答受付版の送付行が**送付済み**で回答が未回答（辞退理由の入力待ちを含む）、その日が提示日に入る人（統合 V4-02）。辞退した人・未送付の人は数えない。受諾が終了した後に新しい版を送った人は未回答に入る |
| 操作 | 日付の人数を押すと、その日の参加者の名前と、依頼書へのリンクを出す |
| 対象 | 正式の依頼書だけ（テストの依頼書は出さない）。取消・終了した依頼書は出さない |
| 権限 | 発注依頼書の閲覧権限（order_read）がある人 |
| イベントのまとまり | 1つの依頼書（変更を作成で作った依頼書は同じ系列としてまとめる）を1つのイベントとして数える。「別日で新規作成」で作った依頼書は、別のイベントとして並ぶ（同じ案件名で日付が違うものとして見える） |

必要人数は入力しない（P-03）。足りない日の警告も出さない。

## 4. 経路3：受諾後の参加日の変更依頼

### 4.1 本人の操作（公式LINE）

1. **Web確認画面（統合計画の②）** の受託済みの依頼書に「参加日の変更を依頼」ボタンを置く。トークの⑤のカードには作らない（統合計画の順番では、③の変更依頼は②のWeb画面の後に作るため。作り直しを避ける）。
   - ⑤に出す依頼書（V3-02）：(a) 今日以降の稼働予定がある依頼書、に加えて (b) **本人の受諾が適用中で、今日以降に追加できる実勤務日が残っている依頼書**（選んだ日をすべて終えたが、依頼書には先の日が残っている人も、日を増やす依頼を出せるように）、(c) **未処理の変更依頼がある依頼書**（確認と取り下げのため）。
2. 日付を選ぶ画面（§5）が、**今の参加日に印が付いた状態**で開く。依頼書の実勤務日の範囲で、今日以降の日だけ増やす・減らすを選べる。
   - **過去の日（今日より前）は、今の参加日のまま固定表示し、選択も解除もできない**（V3-01）。送る内容は「変更後の参加日の全体」で、過去の日は今の参加日と同じでなければならない。
3. 理由を入力（必須、200字まで）して送る。
4. 返信：「依頼を受け付けました。運営が承認するまでは、予定どおりの勤務です。」
   - 日を増やす依頼を含むときは「追加の希望日は、承認されるまで確定ではありません。」を添える。

### 4.2 変更依頼のデータ（新しい表 `participation_change_requests`）

| 列 | 内容 |
|---|---|
| id | |
| delivery_id / worker_id / series_id / version_id | 依頼の対象（本人の適用送付行） |
| base_state_id | 依頼した時点の参加日の状態（承認時の古さの確認に使う） |
| requested_dates | 依頼後の参加日（全体） |
| added_dates / removed_dates | 増やす日・減らす日（表示と通知用） |
| reason | 理由 |
| urgent | 当日・翌日の日を含むか |
| status | `received`（受付）／`seen`（運営が確認）／`approved`（承認）／`rejected`（却下）／`withdrawn`（本人が取り下げ）／`stale`（失効） |
| decided_by / decided_at / decision_note | 承認・却下した人・日時・メモ |
| idempotency_key | LIFF画面が送信ごとに作る冪等キー（V3-04）。同じ人・同じキーの再送は、新しい依頼を作らず同じ結果を返す。（本人, キー）で一意 |
| content_hash | 同じキーで内容が違う再送を拒否するための、内容のハッシュ（登録の LIFF と同じ方式。DEC-032） |
| request_date_jst | 依頼を受け付けた日（日本時間）。承認時の失効の判定に使う |
| seen_by / seen_at | 運営が最初に開いた人・日時（V3-03） |

### 4.3 決まりごと

| # | 決まり | 理由 |
|---|---|---|
| R-01 | **同じ系列・同じ人**で、未処理（received / seen）の依頼は1件まで（V3-04）。新しく出すと前の依頼は取り下げ扱い。DBの部分一意制約（PostgreSQL）と系列のロックの両方で守る | 運営が古い依頼を承認してしまうのを防ぐ。同時の送信でも2件にならない |
| R-02 | **過去の日は増やすことも減らすこともできない**（V3-01）。依頼の内容と今の参加日を比べ、今日より前の日に差があれば拒否する。日付は**日本時間**で判定する | 実績と食い違わないように |
| R-02b | 承認するときに、依頼で変える日（増やす・減らす日）の中に、**承認の時点で過去になった日**があれば、反映せず `stale`（失効）にして本人と運営に知らせる（「日付が過ぎたため反映できませんでした。必要なら運営へご連絡ください」） | 依頼から承認までに日付が変わった場合 |
| R-03 | 増やせるのは、その依頼書の実勤務日（休業日を除く）の範囲だけ | DEC-065 |
| R-04 | 承認時に、対象の版が本人の適用版のままか、参加日の状態が依頼時と同じかを確認する。違えば反映せず `stale`（失効）にして運営と本人に知らせる | 修正版が出た後に古い依頼を反映しないように（DEC-065 Guard） |
| R-05 | 修正版の確定・取消・受諾後の辞退の記録が起きたら、その依頼書の未処理の依頼は `stale` にする | 同上 |
| R-06 | 減らした結果、**今日以降の参加日が0日**になる依頼も受け付ける。運営の画面ではこの依頼に「承認」の代わりに **「今後の参加を終了として承認」** を出す（V3-07、統合 R-01）。押すと、**記録した時点で勤務が始まっている日を残した**（統合 §5 ⓪・D-05 の決定に従う）参加日の状態を追記（source=`ops_recorded_decline`、change_request_id 付き）・依頼を `approved` に・監査・本人への結果通知の予約を、**1つのトランザクション**で行う。受諾後の辞退の記録（0.47.8 で過去の日を残すよう修正）と同じ処理を使う | 過去に働いた日の予定・稼働日数・報酬見込みを消さないため |
| R-07 | 承認・却下・取り下げは何度押しても結果が変わらない（冪等）。状態・稼働予定・監査・**通知の予約（§4.6の送信予定表）** は1つのトランザクションで保存し、送信はcommitの後に行う | DEC-065 Guard |

### 4.4 運営の操作（管理画面）

- 発注依頼書の画面に「参加日の変更依頼」の一覧（未処理を上、至急を最上段）。
- 1件ずつ「承認」「却下」（却下はメモ必須）。0日になる依頼は「辞退として承認」（R-06）。
- **権限（V3-03）**：

| 操作 | 必要な権限 |
|---|---|
| 一覧・詳細を見る | 発注依頼書の閲覧（order_read） |
| 確認済みにする（`seen`） | 発注依頼書の閲覧（order_read）。詳細をAPIで開いたときにサーバーが付け、最初の人と日時を `seen_by`・`seen_at` に残す（2人目以降は上書きしない） |
| 承認・却下・辞退として承認 | 発注依頼書の編集（order_write）。閲覧権限も必要（既存の規則どおり） |
| LINEで知らせを受け取る | 参加日の変更依頼の連絡受け取り（participation_request_receive）。**この権限だけでは見る・操作することはできない** |
- 承認 → 参加日の状態を追記（source=`change_approved`、change_request_id 付き）→ 再構築 → 本人へ「参加日の変更が承認されました。あなたの稼働日：…」。
- 却下 → 本人へ「参加日の変更は承認されませんでした。予定どおりの勤務です。（運営からのメモ）」。

### 4.5 運営への知らせ

- 受け付けたら、権限を持つ運営スタッフ（公式LINE連携済み）へ「参加日の変更依頼：〇〇さん／依頼書番号／−11/2 +11/4／理由」。
- 当日・翌日を含む依頼は件名に【至急】を付ける。
- 知らせの送信成功を、運営の確認済みとは見なさない（確認は画面で `seen` になったとき）。

### 4.6 通知の保存と再送（V3-05）

A1の Webhook の返信は、処理中にメモリへためてcommit後に送る方式（返信用トークンを使う。失敗しても再送しない）。A1+の承認結果・運営への知らせは **プッシュ送信** で、送れなかった場合に残ると困るので、**送信予定を表に保存してから送る**。

- 既存の「登録受付の通知」（line_registration_receipts。DEC-039）が同じ形（pending / sent / failed、再試行キー、最大5回、予定時刻つきの再送）で動いている。これを **汎用の送信予定表 `line_push_outbox`** として作り直さずに、同じ形の新しい表を作る（登録受付の表は今回は変えない）。

| 列 | 内容 |
|---|---|
| id / kind | 種類（`change_request_received`＝運営への知らせ、`change_request_decided`＝本人への結果、`change_request_stale`＝失効の知らせ） |
| to_line_user_id / to_user_id | 宛先（LINEのID、運営スタッフならユーザーID） |
| messages | 送る内容（JSON） |
| retry_key | LINEの再試行キー（X-Line-Retry-Key。二重送信を防ぐ） |
| status / attempt_count / next_attempt_at / sent_at / last_http_status | 送信の状態と試行の記録 |
| source_type / source_id | 元になった変更依頼など |

- 承認などの処理と**同じトランザクション**で行を作る。commit後にすぐ1回送る。失敗・プロセス停止で送れなかった行は、既存の定期実行（受領期限の案内と同じ cron）が拾って再送する（最大5回、間隔を空ける）。
- 5回失敗したら `failed` にし、管理画面の変更依頼の一覧に「本人への通知に失敗」と出す（運営が電話などで伝える）。
- A2（起床の催促・運営への通知）でも同じ表を使う。月の通数の監視もこの表から数える。

## 5. 日付を選ぶ画面（P-01：決定 ＝ 期間のカレンダーをタップして選ぶ、LIFFで作る）

**決定した画面**：LINEの中で開くWeb画面に、依頼書の期間（最初の稼働日〜最後の稼働日）の月カレンダーを出す。

- 選べる日（提示日。変更依頼では今日以降の実勤務日）だけを濃く表示し、タップで選択・解除する。選んだ日は色を変えて✓を付ける。
- 休業日・提示日でない日・過去の日は薄く表示し、押せない。
- 期間が月をまたぐときは、月を切り替えるボタンを出す。
- 画面の下に「選んだ日：11/1、11/3（2日）」と「この日で受諾」（変更依頼では「この内容で依頼する」と理由の入力欄）を固定表示する。
- 文字は大きめにし、スマートフォンの片手操作で押しやすい大きさにする。

以下は方式を比べた表（v0.1）。A（LIFF）で進める。

| 案 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）LIFF** | LINEの中で開く小さなWeb画面。カレンダー形式でチェックを付けて「この日で受諾」 | 日数が多くても1画面で選べる。誤操作が少ない。経路2と3で同じ画面を使える | LINE Login チャネルの作成と、LIFFアプリの登録が必要（作業は運営側で数分＋設定値の受け渡し）。本人の確認にIDトークンの検証を実装する |
| B LINEのボタンだけ | 日付ボタンを並べたメッセージを送り、押すたびに✓の付いたメッセージを返し直す | 追加の設定が要らない | 押すたびにメッセージが増える。日数が多いと並びきらない（1通に置けるボタン数に上限がある）。高齢の方など、慣れない人には分かりにくい |
| C 運営が代わりに入力 | 本人は「一部だけ参加」を押し、日付は運営が電話で聞いて画面で入力 | 本人の操作が最小 | 運営の手間が残る（DEC-065の「受諾した時点で確定」と合わない） |

**推奨理由**：経路2・3の両方で同じ画面を使え、今後の販売報告（④、C1）や出勤・退勤（②③）の入力画面にも使い回せる（確信度：中）。

**既存の仕組みの再利用（v0.3で確認）**：稼働者登録で、すでに LINE Login チャネルと LIFF を使っている（DEC-032。設定は `line-registration-config.json` の LINE_LOGIN_CHANNEL_ID・LINE_LIFF_ID）。IDトークンの検証（`verify_line_id_token`）と、送信ごとの冪等キー（`line_registration_submit_keys`）の仕組みもある。A1+ はこれを使う。

- **LIFFアプリを1つ追加**する（同じ LINE Login チャネルの中。開く先のURLが登録用と違うため）。運営側の作業は LINE Developers での追加と、LIFF ID の受け渡しだけ。同じチャネルなので、本人のLINEのIDは登録時と一致する。
- **開き方（V3-06）**：LINEのメッセージには期限のあるトークンを入れない。ボタンは `https://liff.line.me/{LIFF ID}?m=accept&d={送付行のID}` の形の固定のURLにする。画面を開くと、LIFF がIDトークンを取り、サーバーが (1) IDトークンを検証、(2) 連携済みの稼働者を特定、(3) その送付行が本人のものか・回答受付版か・まだ回答できる状態か を毎回確認する。送付行のIDだけでは操作できないので、古いメッセージからでも安全に開ける。
- 回答できない状態（新しい版が出た、取消、回答済み）なら、画面に理由を出し、⑤から新しい依頼書を開くよう案内する。

## 10b. 「稼働者向けLINE Web確認画面」計画（DEC-070）との関係

同じ日に、別の計画書 `docs/ops/LINE_WORKER_WEB_PORTAL_PLAN_2026-10-22.md`（v0.1、DEC-070）が作られている。月間・直近1週間の予定と報酬見込みを、LIFFの共通Web画面で見せる構想で、⑤⑥をWeb画面へ移す案を含む。

| 重なる点 | A1+ の扱い |
|---|---|
| LIFFでの本人確認（IDトークン検証、連携済みの稼働者の照合） | **A1+ の 0.48.0 で共通の仕組みとして作り、Web確認画面でも使う**。画面ごとに別々に作らない |
| LIFFアプリ | 1つの LIFF アプリの中で、日付選択とWeb確認画面を別のページにする（LIFFアプリを画面ごとに増やさない） |
| ⑤の入口 | A1+ は⑤のトーク（カード）に「参加日の変更を依頼」を足す。Web確認画面で⑤をWeb化する場合は、変更依頼もWeb画面側へ移す。**どちらを先に公開するかで⑤の作りが変わるので、実装前に順番を決める** |
| 予定の正本 | どちらも稼働予定（DEC-063）を読むだけで、書き換えない |

推奨の順番：**A1+（0.48.0：共通のLIFF本人確認・日付選択・参加カレンダー）→ Web確認画面 → A1+の変更依頼をWeb画面の上で作る**（順番と版は統合計画 `LINE_WORKER_ROADMAP_2026-10-22.md` で管理）。変更依頼をトークのカードではなくWeb画面から出せるので、⑤の作り直しを避けられる（確信度：中）。
