# 起床未報告対応: 本人への催促から運営への通知まで

作成: 2026-10-26。状態: 要件整理・計画。自動通知の実装/本番公開は未実施。
根拠: DEC-066（2026-10-22の補記を含む）、本人のレビューへの訂正、DEC-116/117。LINE運営メニューの閲覧機能とは別工程。前稿で催促条件・通知先を未確定としていた記載を訂正した。

## 目的と確定した流れ

未報告の稼働者には先に公式LINEで報告を促し、報告がなければ運営に連絡先を届け、電話対応につなげる。

1. 当日の有効な予定と既存の起床期限ルールで、起床報告の対象者・未報告を判定する。予定なし・取消・試験データを対象へ混ぜない。
2. 起床期限を過ぎて未報告なら、本人の公式LINEへ**5分おきに3回**催促する。文言は「起床報告がありません。起床報告をお願いします」等を提案し、報告の入口を添える。報告があればその時点で催促を止める。
3. 各送信直前に最新の予定・起床報告を再確認する。3回催促しても未報告なら運営通知へ進む。DEC-066にない追加待ち時間を新たに設定する前提にはしない。
4. 有効な管理画面Userが **wake_alert_receive権限を持ち、公式LINEと有効に連携している運営** に、氏名・未報告の事実・登録電話番号を通知する。管理者は全権限を持つため既定で対象だが、LINE未連携/無効なら送信対象にしない。案件・対象日・開始時刻も識別に必要な最小限を添える案。
5. 運営が通知を見て、必要に応じてその番号へ電話する。自動発信は行わない。LINE画面での連絡記録登録は現段階の必須要件にしない。
6. 運営への未報告通知後に起床報告が来たら、運営へ**報告があった旨の追加通知**を送る。未報告を知らせた宛先と送信履歴を追跡し、有効な通知先を確認して重複なく通知する。

運営通知の文面例（形式案）:

> 起床報告の確認が取れていません。
> 対象: ○○さん／対象日: ○月○日
> 登録電話番号: 090-XXXX-XXXX
> 本人へのLINE催促後も、通知直前の確認時点で未報告です。

送信後に報告が届く可能性があるため、通知に確認時刻と最新状況へのリンクを添える案とする。「応答がない」「遅刻確定」「電話済み」と、確認していない状態を断定しない。

## 電話番号の扱い

- 本人の登録済み電話番号を、未報告対応のために運営通知へ含めることは本人指定で確定。番号未登録なら「電話番号未登録」と表示し、別番号を推測しない。
- 運営の閲覧画面にも電話番号を表示することや、telリンクを付けることは別の表示上の判断。通知が届けばよいという今回の要件に、それらを必須として足さない。
- 連絡記録の入力機能を閲覧専用画面へ追加する許可とは解釈しない。必要なら別途決める。

## DEC-066で確定済みの条件

| 論点 | 現在の扱い |
|---|---|
| 起床期限 | 勤務開始（集合）日時 − 両端の徒歩 − 駅間の概算時間 − 移動の余裕15分 − 準備60分。複数駅は徒歩を含めて最短の経路 |
| 本人への催促 | 起床期限超過から5分おきに3回。途中で報告があれば停止 |
| 運営通知 | 3回催促後も未報告なら、wake_alert_receiveを持つ有効なUserと、有効な運営スタッフ/公式LINE連携から通知先を解決する。全閲覧者への一斉送信とはしない |
| 通知後の報告 | 運営へ追加通知する。反復する未報告通知を無制限に加えない |
| 自動化の対象外 | 開始0:00〜4:59、期限が稼働日の前日になる勤務。運営確認へ回し、同日の通常勤務の監視は続ける。変更確認中は既存の旧い条件で監視 |
| 自動催促の開始条件 | 駅すぱあとAPI導入後。導入前に乗車時間の手入力で自動催促を開始しない。駅間の取得結果は保存して再利用する |
| 通数管理 | DEC-066の月5,000通想定では8割（4,000通）で運営へ警告。実契約・当月の利用上限は有効化前に確認する。送信不能のまま監視成功扱いにしない |

## 残る設計上の確認

- 本人への送信失敗・ブロック・LINE連携なしの場合、通常の「3回催促後も未報告」と分けて連絡不能を運営へ知らせる時期/文面を決める。これはDEC-066では未定義。
- 期限超過を初めて検知した時点、送信遅延や再起動からの再開を含む時刻境界をテストで固定する。5分おき3回という業務ルールを再決定する質問ではない。
- 通知の宛先はUser→VanzaiStaff→LineStaffLinkで照合する。運営全員が管理画面IDを持つ前提（DEC-117）であり、既存IDとスタッフの対応が未登録なら管理者が確認して紐付ける。氏名・電話で自動推定せず、新しい受信可否項目をスタッフ側へ追加しない。
- 受信者が0人のときの運用警告と担当者確認を設ける。DEC-066初稿の「0人ならadmin全員へ送る案」を、後続の権限方式を越えた追加送信の根拠にしない。

## 実装とテストで守ること

- 既存の起床判定・予定の正本を再利用し、通知直前にも最新状態を確認する。報告と送信の競合は記録し、最新状況を確認できる導線を付ける。
- LINEの送信受付成功を端末到達・既読と同一視しない。送信失敗を送信済みとして進めない。通常の未報告継続と送信不能の分岐を混同しない。
- 永続的な送信状態と冪等キーで再起動・定期処理の重複を防ぐ。本人の催促1/2/3回目、運営への未報告通知、報告後の追加通知を別段階として記録する。運営通知は送信時にUserの有効/削除状態・最新のwake_alert_receive・スタッフ/LINE連携を再確認し、権限剥奪後や無効化後には送らない。
- 監査本文に氏名・電話番号を複製しない。通知本文として必要な電話番号と、一般ログへの出力を区別する。
- 当日予定なし、取消、報告済み、催促後の報告、未報告継続、本人への送信失敗、運営無効化、番号未登録、再試行・二重実行をテストする。
- 正常系の受入条件は「5分おき3回、報告で停止」「未報告継続時のみ権限を持つ運営へ氏名と電話を通知」「通知後に報告なら追加通知」。User無効化/権限剥奪、駅すぱあと未導入、対象外勤務、月の通数警告も検証する。API導入条件と必要な失敗時運用が揃うまで自動通知を有効化しない。
