## 1. 結論

1. **最初に「LIFFの共通部分」（本人確認・公開の止め方・カレンダーの部品）を1回だけ作り**、日付を選んでの受諾（A1+）とWeb確認画面の両方で使う。
2. 順番は **⓪ 受諾後の辞退の不具合修正 → ① 日付を選んでの受諾＋参加カレンダー → ② Web確認画面（予定・確認事項・報酬見込み）→ ③ 参加日の変更依頼（Web画面の上）＋再送つき通知 → ④ 起床の監視（駅すぱあと次第）** を推奨する（確信度：中）。
3. 日給の数え方は「依頼書に書いた1日あたりの日給を、参加する日ごとに1回」に確定した（§4）。報酬見込みは会計B1の決定を待たずに作れるので、②に含める。
4. 並行して、数人での**試験運用**を始める。本番と同じ種類のデータベース（PostgreSQL）での**同時操作の試験に合格することを、①の公開の条件**にする（画面や部品の開発は先に進めてよい）。→ 合格済み（0.48.1）。
5. **（v0.8）正式運用（11月中）の開始は、②③④の完成を条件にしない**。初日に必要なのは §7.1 の3つ（試験運用を一通り通す・起床の目視確認の担当と手順・本番の版の確認）。②③は運用しながら加える（確信度：中）。

## 4. 決まったこと（2026-10-22 ユーザー回答）

| # | 内容 |
|---|---|
| F-01 | **日給の数え方**：依頼書に記載した1日あたりの日給を、その人が参加する日ごとに1回数える。多少の時間のずれは日給に含まれる。大幅に延びた場合は、現場管理者から運営へ連絡が入る（システムでは扱わない） |
| F-02 | 1つの依頼書の中では、勤務グループ（日付・期間）の日付は重ならない（現行の入力検証で保証）。したがって、1つの依頼書で同じ日に日給が2回数えられることはない。**別々の依頼書で同じ日に働く場合は、それぞれの日給を数える**（別の仕事のため） |

| F-05 | 運営から参加日の追加を頼むときは、LINEのトーク等で直接頼み、本人が変更依頼を出す（A1+ P-05） |
| F-06 | 日付・期間ごとの入力がない依頼書は確定できない。旧形式からの作成はできる（DEC-069） |

### ⓪ 0.47.8　受諾後の辞退の記録で、過去の日の予定を消さない（不具合修正）

| 項目 | 内容 |
|---|---|
| 不具合 | 今の「受諾後の辞退を記録」（0.47.0）は参加日を0日にするため、**すでに働いた過去の日の稼働予定まで「取消」になる**。例：10/20 に働き、10/25 を辞退すると、10/20 も取消扱いになり、②の月間日数・報酬見込み、将来の実績と合わなくなる（レビュー R-01 の指摘から確認） |
| 直し方（案） | 辞退の記録は「今後の参加を終了」とし、**記録した時点で勤務がすでに始まっている日（勤務の開始日時 ≦ 記録した日時、日本時間）は参加日として残し**、まだ始まっていない日だけ外した状態を追記する。残す日以外がすでに0日なら記録しない |
| 4つの例（V4-03） | 当日朝の欠勤連絡（開始前）→ 当日は**取り消す**／勤務開始後の連絡（早退など）→ 当日は**残す**（実際の扱いは運営が現場と調整）／勤務終了後の連絡 → 当日は**残す**／前日 22:00 開始・当日 6:00 終了の夜勤の途中 → 前日開始の分は**残す**。当日の勤務を取り消す操作になる場合は、確認画面に「本日 9:00 開始の勤務も取り消されます」と明示する |
| 未決 | この「勤務の開始時刻で分ける」案でよいか（§8 D-05） |
| 版 | Z（既存機能の不具合修正） |
