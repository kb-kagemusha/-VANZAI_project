# 日付別の発注条件と運営スタッフ（0.45.1）

## 稼働者情報の更新
稼働者登録・一覧で編集し「更新する」を押す。保存に成功した場合だけ「情報を更新しました」をポップアップ表示する。保存後の再取得が失敗した場合、保存済みであることを案内し、最新内容を読み込むまで再更新を無効にする。409の競合では成功通知を表示しない。

## 発注依頼書の日付・時間・単価
新規依頼書で「稼働日・稼働時間」を入力する。「1日ごと」または「複数日の期間」を選び、日付、開始・終了時間、備考を入れる。「稼働日・期間を追加」で条件の異なる日を分ける。日をまたぐ勤務は「終了は翌日」を選ぶ。集合時間は任意の別欄とし、開始時間から推測しない。

単価の「稼働日の設定で単価設定する」は初期値ON。勤務条件と同じ分け方にする。日付の変更は対応する単価へ追従し、同じ勤務条件の識別子に対して入力した金額を保持する。OFFでは別の日付・期間を入力できる。再びONにする場合は日付が一致しない単価を入力し直すため確認を表示する。単価は円・税抜、日給/時給を明示する。昼食代・交通費の「込み」は初期値ON。OFFの場合はそれぞれの備考を入力する。

下書きでは未記入欄を残せる。日付の重複、逆転、無効な時刻・負の金額などは保存時に拒否する。確定時には全勤務条件の時間・日付・単価と別途費用の備考、単価期間の勤務日カバーを検証する。依頼書の条件はrequest_conditionsのJSONと本文に保存し、確定版とPDFのスナップショットへ残す。これを給与・請求単価マスタへ自動転記しない。実績や締め済み金額の再計算は行わない。

既存の自由記入の依頼書はそのまま表示・編集する。日付別入力へ切り替える場合だけ確認を表示する。旧時間・単価の文面は「切替前の勤務時間・単価（参考）」とprevious_hours/previous_feeに保存する。自由文の時刻や金額から条件を推測しない。

## 所在地とGoogle Maps
「Google Mapsで所在地を検索」を押して会場を開き、「共有」→「リンクをコピー」で取得したURLを「Google Mapsの共有URL」に貼り付ける。この方式はMaps APIを呼ばず、APIキー・API利用料は不要。共有URLはrequest_conditions.maps_urlと本文・PDFの確定版へ保存する。Google MapsのHTTPS共有リンクだけを許可し、他サイト・認証情報付き・非HTTPS・異常なポートを拒否する。サーバーが短縮URLを展開したり外部サイトから住所を読み取ったりしない。会場名を変更した場合は以前のURL/地点IDを解除する。住所も依頼書へ残す場合は「所在地の登録住所」に主催者が提供した住所を別途入れる。共有URLのみから公共交通の移動時間を自動算出できるわけではない。

Google Places API (New)のText Searchをサーバー側から呼ぶ準備を追加した。環境変数名はGOOGLE_MAPS_API_KEY。キーを管理画面・チャット・Gitへ出さない。既存.env/.env20261006は閲覧・上書きしていない。未設定時は検索を無効にして理由を表示する。問い合わせは入力中ではなく「所在地を検索」を押した場合のみ、認証済みadmin/opsに許可。1APIプロセス・ユーザーあたり10検索/分に制限する（複数APIプロセスの合算上限はGoogle Cloud側のクォータでも制御する）。キーはPlaces API (New)だけに制限し、サーバーの送信元IP・課金上限を所有者側で設定する。

現在の標準画面は共有URL方式とする。API未設定時はAPI検索欄を表示しない。API検索を今後有効化する場合だけ、Google Cloudプロジェクト、課金・API利用設定、公開の利用規約・プライバシーポリシーの整備を確認する。ユーザーが今回API設定を行う必要はない。Google取得住所の自動保存は実装しない。

GoogleのPOI検索結果の住所は参照用表示だけで、候補一覧・取得住所・緯度経度をDB、PDF、監査へ複製しない。選択したplace_idのみrequest_conditions内へ保存し、会場名が変更されたら紐付けを解除する。Google Maps出典と第三者提供元を表示する。登録住所には主催者が提供した住所を別途記録する。Google取得住所の無期限保存を、ボタンで確認したという理由だけで許可扱いにしない。Googleの住所Autocompleteでユーザー提供の街路住所を選択する場合の例外は、会場名のPOI検索とは別に検討する。

- [Text Search (New)](https://developers.google.com/maps/documentation/places/web-service/text-search)

## 運営スタッフの登録・LINE紐付け
サイドバー「運営スタッフ登録・一覧」を開く。現時点の管理は既存adminに限定する。既存VANZAI担当者マスタと同じ人物を使用し、新しい稼働者やログインユーザーを自動作成しない。氏名、電話・メール、運転可否、喫煙可否、緊急連絡先、担当ロール、備考、有効状態を保存する。

5つの名称はmanagement_rolesの担当業務ラベルとして記録し、既存の報酬用role（プレイングマネージャーなど）と分ける。複数を記録できるが、実際のログイン・閲覧・操作権限にはまだ連動させない。ユーザー回答で、今回は付与・保存まで、後々に画面の表示項目・操作範囲を制御する方針を確定した。総合管理などの名称を既存admin/ops/accountingへ推測で対応付けない。運営スタッフのユーザー作成や権限付与は未実装の範囲として扱う。

保存後に「LINE紐付けコードを発行」を押す。本人が公式LINEとの個別トークへOPS-で始まるコードを送る。コードは30分・1回限りで、平文を保存しない。再発行で前の未使用コードを失効させる。署名付きWebhookから送信者を確認し、LINE表示名を取得する。グループ送信、期限切れ、再使用、無効/削除済みスタッフは拒否する。1運営スタッフに1有効LINE、1LINEに1有効運営スタッフとし、解除した行は履歴として残す。運営と稼働者は別に本人確認するため、兼務者は同じLINEを各区分へ紐付けできる。

解除は理由付きで行う。公式LINEの友だち解除Webhookでも運営の紐付けを無効にする。無効スタッフに新規コードを出さない。将来の通知宛先はis_active=true・deleted_atなし・LINE status=activeの三条件で絞る。

監査: operator_staff_created/updated、operator_line_code_issued/linked/revoked。対象スタッフID・実行者・担当ロール・版/状態・解除理由を記録し、電話・緊急連絡先・LINE ID・コード平文を監査へ複製しない。profile_revisionと行ロックで古い編集を拒否し、旧マスタ画面の更新もrevisionを上げる。409なら最新内容を読み込み直す。

## 次段階の自動化（今回の対象外）
ユーザー回答で、今回は住所・LINE連携の準備までと確定した。起床報告ボタン、公共交通の所要時間計算、起床期限、未報告のリマインド、15分などの経過後の運営通知は次段階とする。自動ジョブ・実送信は追加していない。期限は集合時刻、移動時間、起床準備の余裕時間を明示して決める必要があり、経路取得失敗を移動0分として扱わない。将来のエスカレーション文面はユーザー指定の「【イベント名】に参加予定の【稼働者名】さんから起床報告がありません。至急連絡をしてください」を使用する。宛先選択、未報告の判定、取消・不参加時の停止と重複防止を次段階で確定する。
