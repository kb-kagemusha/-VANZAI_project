# drv案件：稼働実績→支払/請求に必要な情報と計算ルール（案）

## 目的
稼働実績（actual）を正本として、以下の一覧に必要な項目を再現可能に生成できる状態を作る。

必要列（稼働実績ビュー想定）
- 管理者
- 稼働者
- 紹介者
- 本人単価
- 紹介者単価
- 現場管理報酬
- 統括管理報酬
- 合計単価
- 概算出勤日数(月)
- 支払い金額
- 備考(支払いサイト)
- 貸出物


## 現状仕様との整合（重要）
- 単価は「実績確定時に決定し、actual.applied_price_* に保存」し、締め後に変わらない（DESIGN_SPEC_v0.3 7.3）。
- 請求/支払は明細行（invoice_line / payout_line）を正本にする（DESIGN_SPEC_v0.3 6.3）。

したがって、**計算結果（支払い金額、合計単価など）を手入力のアプリで持たない**。
入力が必要なのは、計算に必要な「属性（契約ルート、紹介者、支払サイト、管理者、貸出物など）」。


## ユーザー回答に基づく業務ルール（確定情報）
### A. 外注（紹介者）単価＝下請け単価
- 基本：1日 = 16,000円
- 例外：多田さん紹介の稼働者は 1日 = 16,500円

例：多田さん派閥 5人 × 10日 = 50人工
- 50人工 × 16,500円 = 825,000円（税抜）

### B. 現場管理報酬
- 基本：現場管理者の配下の「人工」× 1,000円
  - 例：配下 5名 × 10日 × 1,000円 = 50,000円
- 変更可能性：将来的に「現場管理者1名あたり月10万円固定」へ移行する可能性あり

### C. 統括管理報酬
- 基本：全 drv 社案件の売上 8%
- 変更可能性：将来的に「固定報酬のみ」へ移行する可能性あり

### D. 支払いサイト
- 稼働者への支払い：稼働者ごと固定（基本70日、例外で60日/30日）
- drv社への請求：60日サイト（月末締→翌々月末払い）
- お金の流れ：
  - drv社 → V社 → 稼働者
  - drv社 → V社 → 下請け → 稼働者


## 未決の定義（決めないと事故る）
### 1人工（1日）の数え方（確定＋例外）
確定
- 基本（A）：1人工 = (worker_id, work_date) のユニーク数（同じ日に複数シフトがあっても1人工扱い）

例外（Wヘッダー/同一日2案件）
- 10〜12月あたりに「同一日で2案件（Wヘッダー）」が発生しうる
- その場合は、同一日でも **案件ごとに人工が立つ** 扱いが必要
  - 1人工（例外時）= (worker_id, work_date, project_id) のユニーク数

未決（追加で確定が必要）
- 同一日に「同一案件でシフト分割」された場合は 1人工=1（同一案件なので1）で良いか
- 現場管理報酬（配下人工×1,000円）は、Wヘッダー時に 2人工（案件ごと）でカウントするか、日単位で1人工のままにするか

### Wヘッダー単価（観測された例）
Wヘッダー時は「日額のWヘッダー単価（バンドル価格）」になる場合と、「案件別日額の合算」になる場合がある。

- パターン1（バンドル）
  - 請求：1日 35,000円
  - 下請けへ：1日 23,000円
- パターン2（案件別合算）
  - 商業案件：18,000円
  - 夜間飲食店巡回：25,000円
  - 合計（請求）：43,000円

未決（追加で確定が必要）
- どの条件で「バンドル」になるか（案件組合せ/期間/時間帯/担当者等）
- 下請けへの支払も、(A)案件別合算 か (B)バンドル固定 か

追加情報（2026-01-28）
- バンドル額（例: 35,000円/日）には固定値はなく、組み合わせと金額は複数パターン存在する
  - 例: 商業＋飲食巡回 / アンケート＋飲食巡回 / popup＋アンケート など

### 日額単価と時間（hours）の整合
現行の集計/支払生成は「単価×時間（hours）」前提の箇所がある。
日額（1日=16,000円）をそのまま入れる場合、以下のいずれかを選ぶ必要がある。
- 案A：日額を時給換算して actual.applied_price_outsource は時給で保存（標準1日=何分かを決める）
- 案B：payout_line の unit_type=days, quantity=人工 を採用し、支払生成ロジックを日単位に対応

補足（Wヘッダーの表現）
- バンドル価格（例: 35,000円/日）を採用する場合、案件別行だけでは表現できないことがある
  - 対応案: 「案件別行＋訂正行（差額）」で、合計がバンドル額になるように調整する（上書きではなく差分で残す）

補足（下請け＝粗利30%以上の考え方）
- 下請け稼働者の支払は「粗利30%以上」を基本にする
- 実務上は、日額（売上）→ 日額（下請け支払）へのマッピング（段階テーブル）で運用されている
  - 例（提示された対応表）:
    - 26,000 → 17,000
    - 25,000 → 16,000
    - 24,000 → 16,000
    - 23,000 → 16,000

未決（追加で確定が必要）
- 上記の対応表が「最低保証（下限）」なのか「固定（完全一致）」なのか
- 26,000/25,000/24,000/23,000 以外の金額（例: 35,000 や 43,000）をどう丸めて段階へ当てるか（例: 1,000円刻みで切り捨て/最も近い段階/別テーブル）

確定（2026-01-29）
- Wヘッダーのように同一日に複数案件がある場合、下請け支払は **案件別に個別判定して合算（B）** を採用
  - 判定単位: (worker_id, work_date, project_id)

未決（追加で確定が必要）
- 上記の判定で得られた「案件別の下請け支払（日額）」を、どこにスナップショットとして保存するか
  - 案: payout_lines（line_type=actual）に unit_type=days, quantity=1 で保存
  - 案: actual.applied_price_outsource を日額相当にする場合、時間×単価モデルとの整合をどう取るか

## 計算の出し方（ビュー作成イメージ）
### 稼働者別（直契約）
- 出勤日数：人工
- 本人単価：16,000円/人工（例外あれば上書き）
- 支払金額：人工×本人単価（＋経費/インセンティブがあれば加算）
- 備考（支払サイト）：payout_terms_days

### 紹介者（下請け）別
- 出勤日数：その紹介者に紐づく稼働者の人工合計
- 紹介者単価：16,000円/人工（多田さん派閥は16,500円/人工）
- 支払金額：人工×紹介者単価（税抜の扱いは別途定義）

### 現場管理者別
- 現場管理報酬：配下の人工×1,000円（または月10万円固定へ移行）

### 統括
- 統括管理報酬：対象期間の drv 案件売上（税抜/税込どちらかを確定）×8%（または固定へ移行）


## 次にやること（実装に入る前の確定事項）

### 暫定決定（2026-01-30）
以下の項目は、実運用開始までに確定が必要ですが、当面は **柔軟に変更可能な設計** として実装します。

#### 1. 1人工（1日）の数え方
**暫定案（A）を採用**: 1人工 = (worker_id, work_date) のユニーク数（基本）

**例外（Wヘッダー）**: 同一日に複数案件がある場合は案件ごとに人工が立つ
- 1人工（例外時）= (worker_id, work_date, project_id) のユニーク数
- 実装: `PriceRuleService.calculate_man_days()` で project_id を含めたユニーク判定

**未確定（運用開始前に決定）**:
- 同一日・同一案件でシフト分割された場合の扱い（現在は1人工として扱う）
- 現場管理報酬の配下人工はWヘッダー時に案件ごとでカウントするか、日単位で1人工のままか

#### 2. Wヘッダー単価（バンドル価格）
**確定（2026-01-30）**: バンドル価格は **都度手入力**（例外として月次で調整）

**運用方法**:
- Wヘッダー発生時は、案件別の単価を **手動で調整** する
  - 例: 商業案件 18,000円 + 夜間飲食店巡回 25,000円 → バンドル 35,000円にする場合、請求書発行前に手動で金額を調整
- 月次調整: 請求書発行前に、バンドル対象の実績を確認し、手動で単価を上書き
- `price_rules_bundle` テーブルは **不要**（都度手入力のため）

**実装への影響**:
- バンドル価格の自動判定ロジックは不要
- 請求書生成前に手動調整できるUIが必要（将来対応）
- 当面は、actual.applied_price_sales を直接編集する運用
  - 推奨: `scripts/adjust_actual_applied_prices.py` を使用し、dry-run と監査ログ（`audit_logs`）を残す

#### 3. 日額単価と時間（hours）の整合
**暫定案（B）を採用**: `payout_line` の `unit_type=days`, `quantity=人工` で日単位支払を表現

**実装**:
- `PayoutLineSchema` に `unit_type: Literal["hours", "days"]` 追加
- `PayoutService.generate_payouts()` で日額判定時は `unit_type=days` で生成
- `actual.applied_price_outsource` は時給換算せず、日額のまま保存（再計算時に unit_type で判別）

**未確定（運用開始前に決定）**:
- 日額と時給の混在運用をどう表現するか（現在は unit_type で判別）

#### 4. 下請け（紹介者）マスタ
**確定（2026-01-30）**: 下請け（紹介者）専用マスタ（**suppliers**）を追加する

**理由**: 稼働者（workers）と下請け（紹介者）は役割が異なるため、別テーブルで管理する

**実装方針**:
- `suppliers` テーブルを新規作成
  - `supplier_id` (PK), `name`, `contact_email`, `payout_terms_days`, `is_active`, `notes`
- `workers` テーブルに `introducer_supplier_id` を追加
  - 既存の `introducer_worker_id` は非推奨（deprecate）
- マイグレーション:
  - 既存の紹介者（workers）を suppliers に移行
  - workers.introducer_worker_id → workers.introducer_supplier_id に変換
- データ移行スクリプト: `scripts/migrate_introducers_to_suppliers.py`

**実装タスク**:

#### 5. 統括8%の計算対象
**確定（2026-01-30）**: **税抜売上**（invoice.amount_before_tax）を対象とし、drv案件のみ集計

**実装**:
- `IncentiveService.calculate_drv_admin_fee()` で drv案件（project_type='drv'）の税抜売上を合計し、8%を計算
- `payout_lines` に `line_type=incentive`, `description='統括管理報酬（8%）'` として保存

**計算式**:
```python
drv_sales = sum(invoice.amount_before_tax for invoice in drv_invoices)
admin_fee = drv_sales * 0.08
```
**確定（2026-01-30）**: 配下人工×1,000円（基本）で実装

**実装**:
- `IncentiveService.calculate_site_manager_fee()` で配下人工×1,000円を計算
- `payout_lines` に `line_type=incentive`, `description='現場管理報酬'` として保存

**計算式**:
```python
man_days = count(distinct (worker_id, work_date, project_id) where manager_id = current_manager)
site_manager_fee = man_days * 1000
```
