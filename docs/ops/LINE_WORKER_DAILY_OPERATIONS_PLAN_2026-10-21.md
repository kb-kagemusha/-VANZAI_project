## 0. レビュアーへ（この文書の読み方）

- この文書だけで、ここまでの経緯を知らなくても判断できるように書いています。§4に経緯、§5に決定事項、§6に過去の決定との食い違い、§14にレビュー指摘への対応をまとめています。
- ラベル：
  - **【確定】** ユーザーが明言した
  - **【推奨・未確認】** 作成者の提案で、ユーザーの明示の承認がない
  - **【設計判断】** 実装の安全性のために、設計側で決めるもの
  - **【未決】** ユーザーの回答待ち
- 用語：
  - **稼働者**：派遣されるスタッフ（`workers`）
  - **運営**：派遣元の社内スタッフ（`vanzai_staff` / `users`）
  - **発注依頼書**：運営がクライアントの依頼を清書し、稼働者へLINEで送る書面（`order_request_*`）
  - **起床報告**：稼働当日に稼働者が「起きました」と知らせる社内ルール
  - **稼働予定**：この計画で新設する表（`worker_schedule_entries`）。依頼書から作る「誰が・いつ・どこで」で、**予定の唯一の正本**
  - **アサイン**：既存の `assignments`。案件の中の「何日の何時の枠（シフト枠）に、誰をどの役割で入れるか」を表す配置データ。現行の請求・支払・staff-mobileの予定画面は、これを元にしている

## 1. 結論（要約）

1. **予定の起点は発注依頼書だけ**にする【確定】。依頼書を作らない限り、予定にも、起床の監視にも載らない。システムは運用開始前なので、既存の予定データとの移行や併存は考えなくてよい【確定】。
2. 依頼書（正式区分）を確定し、稼働者が受諾したら、その稼働者の**稼働予定**を作る。LINEの予定確認・起床報告・起床の監視は、すべて稼働予定を読む。
3. 公式LINEのリッチメニューは**6パネル**【確定】。運用を始めていないパネルは押せない状態にする（画像は運営が用意する）。
   - ①起床報告 ②出勤報告 ③退勤報告 ④販売報告 ⑤受託済みの発注依頼書 ⑥スケジュール確認
4. 既存の請求・支払は「単価 × 時間」でしか計算できない（R01）。そのため、金額に関わる部分（依頼書から案件・アサインを生成する部分、出勤・退勤を実績にする部分）は、日給の計上モデルを決めてから着手する（Track B）。
5. 段階：

| 段階 | 内容 | 金額への影響 |
|---|---|---|
| A0 | 依頼書の「期間」に**除外日（休業日）**と、**個人ごとの不参加日**を入力できるようにする | なし |
| A1 | 稼働予定の生成と版の切替（送付先ごとの提示日・合意日を反映）、①起床報告、⑤受託済みの発注依頼書、⑥スケジュール確認、当日の起床状況一覧、リッチメニュー6パネルの適用（運用前のパネルは押せない） | なし |
| A1+ | 日付を指定した受諾（依頼書ごとの許可）、受諾後の参加日の変更申請・承認・結果通知、直前の申請の至急通知、日ごとの充足状況（必要人数） | なし |
| A2 | 起床の監視・催促・運営への通知（移動時間は手動設定）、起床対象の条件設定 | なし |
| A3 | 乗換APIによる移動時間の自動計算、集合場所の最寄り駅 | なし |
| B1 | 日給の計上モデル（支払・請求） | あり |
| B2 | 稼働予定から案件・シフト枠・アサインを生成（会計用） | あり |
| B3 | ②出勤報告・③退勤報告 → 実績 | あり |
| C1 | ④販売報告 | 項目による |

## 2. 目的と背景

### 2.1 業務上の課題

| 課題 | 現状 |
|---|---|
| 起床報告 | 稼働者がLINEで手動送信し、運営が目で確認している |
| 予定確認 | 稼働者が自分の予定を知るには、届いた依頼書を探し直す必要がある |
| 二度手間 | 案件登録と依頼書作成で、同じ内容を2回入力する想定になっていた |
| 出勤・退勤 | LINEから打刻できない |

### 2.2 目的

- 稼働者の当日の確認・報告を、公式LINEのボタン操作だけで完結させる
- 運営が「誰がまだ起きていないか」「誰に電話すべきか」をシステムで把握できるようにする
- 入力の起点を発注依頼書に一本化して、二重入力と二重管理をなくす

### 2.3 運用の前提（ユーザー提供）

- **運用開始前**。当初の計画から変更されており、依頼書をすべての起点にする
- 稼働者は、公式LINEとWebのIDの連携を義務付ける
- 公共交通が原則。ほぼ都心。始発前後の集合や深夜撤収はほとんどない
- 稼働者は最寄り駅と徒歩分数を登録済み（DEC-050で複数駅にも対応）
- 報酬は日給が基本。遅刻は現場リーダーから運営へ直接報告される
- LINE公式アカウントは有料プランへ移行予定（通数増は許容）
- 依頼書の「期間」の途中に**休業日が入ることがある**

## 7. Track A の設計（金額に触れない）

### 7.1 予定の正本と、既存のアサインとの役割分担（V2-01への対応）

- **予定の唯一の正本は稼働予定**（`worker_schedule_entries`）。稼働予定は依頼書から作られる派生データで、**直接は編集できない**【確定（L-16）＋設計判断】。
- **訂正の経路は2つだけ**（V7-01）：
  - 依頼書の**共通の条件**（勤務日・時刻・場所・共通の除外日など）の変更 → 修正版の依頼書（確定と受諾）
  - **特定の人の参加日**の変更 → 本人の変更申請を運営が承認した記録（§7.13）。承認記録を根拠に、その人の参加日の状態を更新し、稼働予定を作り直す。修正版は不要（L-38）
  - どちらの場合も、稼働予定そのものを手で書き換えない
- 既存のアサインは、B2以降、**稼働予定から生成する会計用のデータ**とする。依頼書・稼働予定と関係なく、手でアサインを作る経路は、B2の導入時に例外扱いにする（または封鎖する）【推奨・未確認、Q17】。
- **staff-mobileの予定画面**（アサインを読む）は、運用開始前なので、稼働者向けにはA1の時点で**公開しない**。メニューの導線を消すだけでなく、直接URLで開いた場合の扱いも受入条件で確認する（V3レビュー §4）。LINEを稼働者の窓口にする。staff-mobileを将来も稼働者に使わせるなら、稼働予定を読むように変える【推奨・未確認、Q18】。
- 運用開始前で既存の予定データがないため、遡って生成したり、移行したりはしない。導入日以降に確定・受諾された依頼書だけが対象。

### 7.2 全体の流れ

```text
[運営] 正式区分の依頼書を確定（confirmed）
          │ 送付行を作成してLINEで送信（既存）
          ▼
[稼働者] LINEで受諾（acked）（既存）
          │ ★A1：依頼書単位のロック内・同一トランザクションで
          ▼
  稼働予定（稼働者 × 稼働日 × 勤務グループ）  ← 予定の唯一の正本
          ├─ ⑥スケジュール確認：本人の分だけを返信
          ├─ ⑤受託済みの発注依頼書：受託した依頼書の一覧とPDFリンク
          ├─ ①起床報告：wake_reports に記録し、当日の予定を添えて返信
          ├─ 起床監視（A2）：wake_watches → 論理通知 → 送信
          └─ B2：会計用の案件・シフト枠・アサインを生成
```

### 7.3 稼働日の展開と除外日（V2-05・L-29）

- 勤務日は `schedule.work_groups` だけから展開する。全体期間 `work_period` からは作らない（DEC-046）。
- 「1日ごと」は、その日だけ。
- 「期間」は、開始日〜終了日の毎日から、**共通の除外日（休業日）を除いた日**【確定】（L-29）。
  - 除外日は、その期間の範囲内であることをサーバー側で検証する
  - 本文・PDFの日付表示にも反映する
- **予備日は運用しない**【確定】（L-31）。実施が未定の日を含む依頼書は発行しない。
- 用語：
  - **実勤務日**：勤務グループから展開し、共通の除外日を除いた日。全員に共通
  - **提示日**：実勤務日から、その人の個人不参加日を除いた日（その人に依頼する日）
  - **合意日**：その人が受諾した日（全日受諾なら提示日の全部、日付指定の受諾なら選んだ日）
- 稼働予定は、その人の**現在の合意日**から作る。

**送付先ごとの参加日**（L-30・L-35・L-36・L-38。詳細は§7.13）
- 個人の不参加日、日付を指定した受諾、受諾後の変更は、すべて「その人が、実勤務日のうちどの日に参加するか」を扱う。ただし、**提示した日・合意した日・変更の申請**は意味を分けて保存する（V7-02）。1つの値を書き換えて済ませると、誰が・いつ・何に同意したかを再現できないため。
- 入口は3つ：
  1. 運営が依頼書の作成時に、個人の不参加日を入力する【A0・A1】
  2. 本人が受諾時に参加日を選ぶ（依頼書の作成時に、チェックボックスで許可した場合だけ。選んだ時点で確定）【A1+】
  3. 受諾後、本人がLINEから変更を申請し、運営が承認・却下する【A1+】
- **表示**：依頼書のPDFは版ごとに全員共通なので、個人の日付は載せない。代わりに、本人への送付文・受諾の確認・スケジュール確認・⑤で**その人の提示日**を明示する。後日の再表示では、当初の提示日と現在の参加日を区別して示す。

### 7.4 版の切替・取消・回答受付（V2-03への対応）

**基本の考え方**【設計判断】

- 依頼書ごとに、**回答受付版**を明示的に1つ持つ。最後に確定した版が回答受付版で、その版が取り消されたら「回答受付版なし」になる。**古い版に自動で戻すことはしない**。
- 稼働者ごとに、**適用版**（稼働予定がactive／変更確認中になっている版）を持つ。
- 返答（受諾・辞退）は、その送付行が回答受付版に属する場合だけ受け付ける。

**操作ごとの影響**

| 操作 | 稼働予定への影響 |
|---|---|
| draftの作成・編集・破棄・取消 | 影響なし |
| 新しい版の確定 | 回答受付版が新しい版になる。旧版で受諾済みの人の予定は「変更確認中」になり、**旧い内容を表示し続ける**（L-26）。新版の送付先から外れた人の予定は `cancelled` になる |
| 新しい版の受諾 | その人の旧い予定を `superseded` にし、新版の予定を `active` にする |
| 新しい版の辞退 | その人の旧い予定を `cancelled` にする |
| 回答受付版ではない版のボタンで返答 | 拒否し、「新しい依頼書が届いています。そちらで回答してください」と返す |
| 回答受付版ではない版の取消 | 影響なし |
| 回答受付版の取消 | その依頼書のうち、`superseded` 以外の予定をすべて `cancelled` にする（依頼書の終了として扱う）。再開するときは、新しい版を確定する |
| 受諾後の辞退（運営が記録） | 理由付きで、その人の予定を `cancelled` にする（L-28） |

**具体例**（受入試験にする）

| # | 経緯 | 結果 |
|---|---|---|
| E1 | v1受諾 → v2確定 | v1の予定は変更確認中。回答受付版はv2 |
| E2 | E1のあと、v2に未回答のままv3確定 | v2のボタンは拒否。v1の予定は変更確認中のまま。回答受付版はv3 |
| E3 | v2受諾 → v1取消 | 影響なし（v1は回答受付版ではない） |
| E4 | 改訂のdraftを取消 | 影響なし |
| E5 | v1受諾 → v2確定 → v2取消 | 回答受付版なし。v1の変更確認中の予定は `cancelled` |
| E6 | v2受諾 → v3確定 | v2の予定は変更確認中 |
| E7 | v1受諾 → v2確定（送付先から外れる） | その人のv1の予定は `cancelled` |

**取消の意味**【確定】（L-34）：確定・送付した依頼書の「取消」は、発注そのものの中止とする。修正内容の誤りは、取消ではなく、さらに修正版を出して直す。取消のあとで旧い内容に自動で戻すことはしない。

- 一意性：UNIQUE(delivery_id, work_group_id, work_date)
- 別の依頼書どうしで同じ人・同じ日・時間が重なる場合は、作成は拒否せず、運営の一覧で重複の警告を出す（同日2案件は正常なため）
- 監査：生成・状態変更を `AuditService` に記録する（稼働者ID・文書・版・状態。LINEのIDは複製しない）

### 7.5 同時実行とWebhookの処理単位（R06・V2-04への対応）【設計判断】

- 同じ依頼書に対する**確定・受諾・辞退・取消・受諾後の辞退の記録、参加日の変更申請の承認・却下・取り下げ（A1+）**は、依頼書単位のロック（`order_request_documents` の行ロック、またはPostgreSQLの依頼書IDによるadvisory lock）を取ってから処理する。ロックを取ったあとに、回答受付版と状態を読み直す。
- 業務の変更・稼働予定の生成・監査・Webhookの処理済み記録を、同じトランザクションに入れる。
- Webhookの複数のイベントは**1件ずつ独立したトランザクション**で処理する。1件が失敗しても、他のイベントは巻き戻さない。
- イベントIDの重複は、一意制約での挿入で判定する。**イベントIDの一意制約違反だけ**を「処理済み」として扱い、それ以外の制約違反は握り潰さずにエラーとして記録する。
- **commitが成功してから返信する**。返信の失敗は記録するだけにし、本人が押し直せば保存済みの結果が返る。
- 個別トーク（`source.type == "user"`）以外は処理しない。

### 7.6 リッチメニュー（L-02）

- 6パネル（2行×3列）を1つ作り、全員のデフォルトにする。設定は `scripts/line/` のスクリプトとRUNBOOKで再現できるようにする。
- ポストバックの `data`：`wk_wake` / `wk_checkin` / `wk_checkout` / `wk_sales` / `wk_orders` / `wk_schedule`。本人ID・予定IDは入れない。
- **運用前のパネルは押せない状態にする**（L-32）【確定】：
  - リッチメニューでは、運用前のパネルの位置に**ボタン領域（アクション）を定義しない**。押しても何も起きない。画像は運営が「準備中」などの表示で用意する
  - 機能を公開する段階ごとに、**画像とボタン領域の定義をまとめて差し替える**（A1：①⑤⑥が有効、②③④は押せない → B3：②③を追加 → C1：④をLIFFで追加）
  - 差し替えは `scripts/line/` の設定スクリプトで行う（メニューの作成 → 画像のアップロード → 全員のデフォルトに切り替え）。手順と、画像の寸法・領域の座標をRUNBOOKに残す
- **公開の時期**（V3-01）【設計判断】：
  - リッチメニューを全員のデフォルトに適用するのは**A1の公開時**とする。A0の時点ではメニューを適用しない
  - 端末に古いメニューが残っていた場合などに備えて、サーバーは**有効でない機能のポストバック**を受け取ったら「この機能はまだご利用いただけません」と返す（無応答にしない）
  - どの公開段階でも、押せるパネルは必ず機能が動くこと

### 7.7 ①起床報告（A1）

1. 本人を特定する（`source.userId` → 有効な `LineWorkerLink` → 有効かつ未削除の `Worker`）。できなければL-01の文言を返す。
2. **報告日の規則（A1単独で決まる）**（V2-06）：
   - 報告日 ＝ LINEイベントの発生時刻（`timestamp`）の日本時間の日付
   - サーバーの受信が発生から30分以上遅れた場合も、発生時刻の日付で記録し、「遅延受信」の印を付ける
   - 報告は事実として残す。あとで予定が変わっても、過去の報告は書き換えない
   - 開始が0:00〜4:59の勤務（運用上ほとんどない）は、起床の自動監視の対象外とし、運営の一覧で「要確認」と表示する（A2）
3. `wake_reports` に（稼働者, 報告日）で1行を保存する。既にあれば「報告済みです（HH:MM）」を返す。
4. 返信は、その日の `active` と変更確認中の予定を、開始時刻順にすべて並べる（例）：
   ```text
   〇〇さん、おはようございます。本日もよろしくお願いします。
   ■本日の予定
   10:00〜19:00　△△キャンペーン
   稼働場所：□□ホール
   集合場所：〇〇駅 東口
   よろしくお願いします。
   ```
   - 変更確認中の予定には「内容が変更されています。新しい依頼書を確認してください」と添える
   - 予定がない日は「本日の予定は登録されていません。運営へご確認ください」と返し、報告は記録する
5. 運営向けの**当日の起床状況一覧**：稼働者・案件・開始・報告時刻・状態・重複警告・変更確認中・要確認。閲覧権限を、DEC-056/057の権限セットに「起床状況の閲覧」として追加する（admin/opsに初期付与する案）。

### 7.8 ⑥スケジュール確認（A1）

- 本人の `active` と変更確認中の予定を、今日から7日分、Flex Messageのカルーセルで返す。
- 並び順は（work_date, start_time, entry_id）で固定する。
- 上限（例：10件）を超えたら、最後のカードに「続きを見る」を置く（V2-07）。
  - ポストバックには、サーバー側の**短命な操作トークン**だけを入れる。トークンは、本人・表示範囲（最初に押した時点の7日間で固定）・最後に表示した位置を持つ
  - 押されるたびに本人を再照合する
  - 期限切れのときは「もう一度スケジュール確認を押してください」と返す

### 7.9 ⑤受託済みの発注依頼書（A1）

- 本人が受託（受諾）し、適用版になっている依頼書のうち、**稼働日が今日以降に残っているもの**を一覧で返す（依頼書名・稼働期間・受諾日時）。
- 1件ずつ「依頼書を開く」ボタンを置く。ボタンには短命の操作トークンだけを入れる。
- **PDFリンクの再発行**（V3-02）【設計判断】：
  - 送信時に発行したPDFトークンは期限があり、勤務期間が長いと切れる。既存の `send_one()` は受諾済みの送付先への再送を拒否するので、それを流用しない
  - 本人の有効状態と、文書・版・送付先を確認したあとで、**新しい期限付きPDFトークンを発行する専用の処理**を設ける。受諾状態と送信状態は変更しない
  - 取消された版、送付先から外れた場合、`view_revoked`、連携解除のときは発行しない
- **閲覧できる版**：
  - 一覧に載せるのは、本人の**適用版**（受諾済み）だけ
  - 開けるのは、本人の適用版と、本人が送付先になっている**現在の回答受付版**。後者は未受諾でも開ける（変更確認中の人が新しい版を読めるようにするため）
- 変更確認中の依頼書は「新しい版の確認待ち」と表示し、新しい版も開けるようにする。
- **本人確認の範囲**：本人確認をするのはトークンの**発行時**。発行したURLは、今の方式（期限付きの秘密URL）のままなので、URLを知っている人なら期限内は開ける。PDFを開くたびの本人確認はしない（今の方式を変えない）。
- ⑥スケジュール確認との違い：⑥は**日ごとの予定**、⑤は**依頼書ごと**（条件・単価・持ち物など、依頼書の全文をPDFで確認する）。
- A1に含める【確定】（L-33）。

### 7.10 起床の監視・催促・運営への通知（A2）

**対象の条件**（L-27）：設定値で「全勤務」（初期値）／「開始が HH:MM より前の勤務だけ」を選ぶ。

**監視する勤務の選び方**（V3-03）【設計判断】：
1. その日の `active` と変更確認中の予定から、まず対象の条件に合う勤務を集める
2. 次の勤務は自動の対象から外し、`excluded`（要確認）として運営の一覧に残す
   - 開始が0:00〜4:59の勤務
   - 計算した期限が、稼働日の**前日**になる勤務（例：開始05:00・移動180分・余裕180分 → 期限は前日23:00）
3. 残った勤務のうち、最も早いものを基準に期限を決める
   - 例：02:00の勤務（除外・要確認）と10:00の勤務がある日は、10:00の勤務で通常どおり監視する
   - 除外した勤務があっても、同じ日の通常の勤務の監視はなくならない

**状態**（1日・1人につき1件、UNIQUE(worker_id, work_date)）：
`needs_setup` / `scheduled` / `reminding` / `escalated` / `reported` / `reported_after_escalation` / `cancelled` / `excluded`

- **期限**：上で選んだ基準の勤務の開始 − 移動時間 − 余裕時間（変更確認中の予定も含める。V2-02）
  - 変更確認中の予定は、旧い条件で監視を続け、運営の一覧に「変更確認中」と表示する
  - 新しい版で開始が早まっても、受諾されるまでは旧い条件を使う（新しい版は未合意のため）
  - 受諾されたら再計算する
- **移動時間**：A2では運営が手動で設定する。未設定なら `needs_setup` にして自動では催促しない。A3で自動計算を追加する
- **作成と復旧**：1日1回のジョブで当日・翌日分を作成・補完する。再起動後もDBの状態から再開する
- **再計算のきっかけ**：稼働予定の変更、移動時間の変更、設定値の変更。再計算で期限が既に過ぎていた場合は、過去の分の催促をまとめて送らず、すぐに要確認として表示する
- **送信**：
  - 論理通知として、監視 × 種別 × 回数 × 宛先の一意キーで保存してから送る
  - プッシュは、最初の試行から同じ `X-Line-Retry-Key` を使う
  - 結果は `accepted` / `failed` / `unknown` で記録し、再試行の期限を持つ
  - 送信の直前に、報告済みでないか・予定が取り消されていないかを再確認する
  - `accepted` を「到達」とは表示しない
- **運営への通知先**：設定をオンにした有効なユーザーのうち、有効な `LineStaffLink` がある人。0人ならadmin全員へ。それも送れない場合は要対応一覧に残し、RUNBOOKの電話確認に回す
- **追加通知**（L-14）は、元の通知を送った宛先へ送る
- 論理通知の作成時だけでなく、**送信・再試行のたびに**、宛先の有効状態と権限を確認する。通知の受け取り設定は、受け取る権限そのものとしては扱わない（V3レビュー §4）

### 7.11 未連携者・その他

- 未連携・解除・無効・削除済み → L-01の文言
- 未知のポストバックは `ignored`

### 7.12 詳細設計で確認すること（V3レビュー §4からの引き継ぎ）

新しい業務判断ではなく、決まった方針を実装に落とすときの確認事項。

- **除外日**：勤務日を決める**共通の展開処理**にまとめ、稼働予定・本文/PDF・単価のカバー確認のすべてで同じ結果になるようにする。重複・範囲外・全日除外・期間を変えたときに残る除外日を検証する。旧い確定版の本文とPDFは再生成しない。
- **整合性の制約**：回答受付版は、別の依頼書の版を指せないようにする。稼働予定の稼働者・送付行・版・依頼書の組み合わせを検証する。行ロックを取る順序を1つに決めて、すべての処理で守る。
- **試験データ**：「運用開始前なので移行は不要」は、既存のテストデータを物理削除するという意味ではない。A1の試験データと、公開の対象を区別できるようにする。

### 7.13 送付先ごとの参加日と変更申請（A0・A1は保存と固定だけ、申請はA1+）（V7-02〜06への対応）

**A0・A1で入れるもの**【設計判断】
- 依頼書の下書きに、送付先ごとの**個人不参加日**を持つ（作成画面で入力する）。
- 確定時に、送付行ごとの**提示日**（実勤務日 − 個人不参加日）を計算し、**送付行に固定して保存**する。確定後に下書きの不参加日を変えても、確定済みの提示日は変わらない。
- 受諾時に、**合意日**を「参加日の状態」として1件目を記録する（全日受諾なら提示日の全部）。受諾日時・対象の版・経路（LINE／運営記録）と一緒に固定する。
- 参加日の状態は**追記型**にする。新しい状態を追加し、送付行が「現在の状態」を指す。過去の状態は書き換えない。
  - A1では、通常の受諾で1件目を作る。運営が受諾後の辞退を記録したときは、**参加日0日の状態を追記する**（source=ops_recorded_decline。理由・実行者・変更前後を残す）。日付を選んだ増減の申請はA1+（V8-01）
  - 稼働予定は「現在の状態」からだけ作る。そのため、生成処理をやり直しても、辞退済みの予定は復活しない
  - 発注の中止・送付先から外れた・旧版（superseded）の場合も、過去の合意の履歴は消さず、現在の予定を作る対象から外す
- 稼働予定は、現在の参加日の状態から作る。
- 提示日が0日になる送付先は、確定時に拒否する（その人を送付先から外す）。

**A1+で入れるもの**
1. **日付を指定した受諾**（L-35）
   - 依頼書の作成時のチェックボックス「日付を指定した受諾を許可する」（初期値はオフ）
   - 許可した依頼書では、受諾の時にLIFFの画面で提示日の中から参加日を選ぶ。選んだ時点で確定する
   - 提示日以外の日（共通の休業日、範囲外、他人の日付）は選べない。サーバー側でも検証する
   - 0日の選択は入力エラーとし、「参加しない場合は辞退を選んでください」と返す
   - 許可していない依頼書の「受諾」は、**提示日の全部**への同意を意味する（全体期間の全部ではない）
2. **受諾後の変更申請**（L-36〜38）
   - 入口：⑤の一覧とは別に「参加日を変更できる依頼書」を出す。条件は「発注が有効（回答受付版がある）で、本人が受諾済みの送付先になっていて、その依頼書に今日以降の実勤務日が残っている」。**本人の今後の参加日が0日でも表示する**（V7-04。例：全10日のうち1〜3日だけ参加していた人が、8日の追加を申請できる）。取消済みの依頼や、送付先から外れた依頼は再開できない
   - 申請に保存するもの：対象の依頼書・版・送付行、**申請時の参加日の状態**、減らす日・増やす日、理由、受信日時（LINEイベントの発生時刻と、サーバーの受信時刻）
   - 申請は合意日を直接書き換えない。承認された申請だけが、新しい参加日の状態になる
   - 増やす日は、その版の**実勤務日**の範囲内だけ受け付ける（個人不参加にしていた日は含む）。実勤務日以外の日は申請できず、運営に修正版での対応を案内する
   - 本人への受付返信：「依頼を受け付けました。運営が承認するまでは、予定どおりの勤務です」。増加を含む場合は、「追加を希望した日は、承認されるまで参加確定ではありません」を添える（L-37）
3. **申請の状態**（V7-06）
   - `received`（運営未確認）→ `seen`（確認済み・承認待ち）→ `approved` / `rejected`。ほかに `withdrawn`（本人の取り下げ）、`stale`（失効）
   - 通知の送信が成功しても `seen` にはしない。運営が画面で開いたとき、または判断したときに状態を進める
4. **承認時の照合**（V7-03）【設計判断】
   - 依頼書単位のロックを取ってから処理する（§7.5の対象に、申請の承認・却下と、それに伴う稼働予定の更新を加える）
   - ロック後に「対象の版が、今も本人の適用版か」「現在の参加日の状態が、申請時と同じか」を確認する。違えば自動では反映せず `stale` にし、運営に再確認を促す（例：申請後に新しい版を受諾した、別の申請が先に承認された、発注が中止された、送付先から外れた）
   - 承認・却下・取り下げは冪等にする。同じ申請の二重承認や、逆順の承認で古い状態に上書きしない
   - 申請の状態・新しい参加日の状態・稼働予定の更新・監査・本人への結果通知の送信予定を、同じトランザクションで保存する。通知はcommitのあとに送る。通知に失敗しても承認を取り消さず、同じ通知を再試行する
   - 「いつでも受け付ける」は**受付**の方針で、反映の可否とは別。過去の勤務日の変更は受け付けない。Track Bの導入後は、会計の保護（DEC-037/053）も適用する
   - **承認のときにも、日付を再判定する**（V8-03）：承認のトランザクションの中で、承認時点の日本時間の日付・発注の有効状態・送付先の有効状態を確認する。対象日に既に過去の日が含まれる申請はそのまま承認せず、`stale` にして本人に再申請を案内する。指定された増減の一部だけを黙って反映することはしない。当日分を一律に締め切るルールは追加しない（当日の申請も、当日中の承認なら反映できる）
5. **直前の申請**（L-37）
   - 受信日時（日本時間）で、対象日に当日・翌日が含まれる申請は至急扱いにする
   - 至急の通知は、申請と同時に通知予定として保存し、日次のジョブを待たずに送る。通知先がいない・送信に失敗した場合も、申請と至急表示は残る
   - 承認前：減らす申請でも、確定済みの勤務・充足人数・起床監視は変えない。増やす申請の追加日は、参加確定・充足人数・起床監視に入れない。どちらも「申請中」として別に表示する
   - 既に起床報告済みの日は、申請を理由に催促を再開しない
   - 承認後：差分を反映し、減った勤務の未送信の催促を取り消す。増えた勤務の監視を再計算する（期限が既に過ぎていれば、§7.10の「要確認」に回す。過去分の催促をまとめて送らない）
   - 運用：直前の申請を確認する担当者と代行者、勤務開始が迫っても未確認の場合の電話確認を、RUNBOOKに定める（具体的な時間はRUNBOOK作成時に決める）
6. **日ごとの充足状況**（V7-05）
   - 依頼書の勤務グループ（必要なら日ごと）に**必要人数**を持たせる。送付人数を必要人数とみなさない
   - 表示：確定した参加・未回答・変更申請中を分けて数え、同じ人を重複して数えない
   - 満員でも受諾は拒否しない（現時点の決定は「許可した依頼書では即確定」）。まずは不足と超過を見えるようにする
7. **通知の共通機構**（V8-02）【設計判断】：至急通知と承認結果の通知はA1+で必要になる。そのため、論理通知・送信試行・宛先（ユーザーの通知設定）の仕組みは、A2の起床監視専用ではなく**共通の通知機構**として、A1+の前提の工程で先に作る。A2はこれを再利用する。A2が未導入の環境でも、至急表示・即時通知・結果通知が動くことをA1+で確認する。起床の催促の停止や再計算はA2との結合試験に分ける
8. **運営から追加を提案する場合**（Q24）：本人の同意を得る方式は、A1+の設計時に決める。決まるまでは修正版で対応する。

## 8. Track B の方針（会計への接続。着手前に改訂）

### 8.1 B1：日給の計上モデル（R01）

- 現行の支払・請求は「単価 × 時間」だけなので、計上の単位（日／時間）と数量の算定方法を明示的に持つ。日給を推測で時給換算しない（DEC-045）。
- 依頼書の合意条件、実績に適用した単価・計算結果、帳票明細のスナップショットの責務を分ける。
- 決めること：同じ人・同じ日に枠が2つある場合の日給の回数（Q4）、請求単価の入力時期（Q5）、退勤の押し忘れ時の支払。

### 8.2 B2：稼働予定から案件・シフト枠・アサインを生成（R02・R04）

- 入力は稼働予定（§7.1）。生成元は対応表（`order_request_materializations`：文書 ↔ 案件、稼働予定 ↔ シフト枠・アサイン）で持つ。1つの案件に複数の依頼書を追加できる形にする。
- 取消・訂正の保護は4区分（実績なし／activeな実績あり／確定帳票に使用済み／締め済み）。旧日付・新日付の両方を判定し、案件ロック（DEC-037/053）を使う。稼働予定の変更が会計側に反映できないときは、要対応一覧に出す。
- 依頼書のクライアントを、生成の時点で必須にする。
- 現場リーダー（Q6）、1案件に複数の会場（Q8）、手作業のアサインの扱い（Q17）を決める。

### 8.3 B3：②出勤報告・③退勤報告 → 実績

- 打刻の事実（`attendance_events`）と計算用の時刻を分ける（Q15）。
- LINEとstaff-mobileで共通のサービスを使う。既存のcheck-in APIはそのままでは再利用しない。
- 複数の予定から選ぶ確認操作には、短命な操作トークンを使い、最終確定時に再照合する。
- GPS判定の要否（Q7）。

### 8.4 C1：④販売報告

- LIFFフォーム（IDトークンをサーバーで検証）。項目（色・台数など）とPAYGATEとの関係（Q9）を決めてから設計する。

## 10. 受入条件

### A0

A0は依頼書の入力だけ（稼働予定の生成はA1で確認する）。
- 期間に除外日を入力でき、範囲外・重複の日付は拒否される。全日を除外した期間は確定できない。期間を変えたとき、範囲外に残った除外日を検出する。本文・PDFに反映される。旧データ（除外日なし）はそのまま読める。旧い確定版の本文・PDFは再生成しない
- 送付先ごとの個人不参加日を入力できる。実勤務日以外の日は指定できない
- 除外日の展開は共通の処理にまとめ、本文・PDF・単価のカバー確認で同じ結果になる
