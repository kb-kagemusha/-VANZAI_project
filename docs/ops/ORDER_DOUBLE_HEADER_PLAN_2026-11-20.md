## 1. 方針（おすすめ）

**2件の依頼書をそのまま作り、「ダブルヘッダー」という束でつなぐ。**

- 1件目・2件目はそれぞれふつうの依頼書（番号・版・PDF・依頼元・請求）として保存する。今の依頼書・請求書・支払明細の作りは変えない。
- 新しい表で2件を束ね、送付・返事・取消のときだけ2件を一緒に扱う。
- すでにある依頼書のデータには触れない（新しい表への追加だけ。既存の列の意味や値は変えない）。

1枚の依頼書に2案件を入れる作り方は、場所・依頼元・請求の明細・日程の重複チェックをすべて作り直すことになり、「今の依頼書・請求書・支払明細の動きは変えない」に反するため採らない。

## 3. それぞれの扱い

### 3.1 依頼書の作成と保存・送付
- 作成画面の上部に「ダブルヘッダー」のチェック。入れると「1件目」「2件目」の欄が並ぶ（スマホ幅では縦に並ぶ）。
- 共通の欄：区分（正式／テスト）、日付、送付先、回答の期限、追跡担当、作成のしかた（保存のみ／作成して送付）。
- 案件ごとの欄：案件名・カテゴリ、依頼元・担当者、場所・集合場所・最寄り駅、集合時間・開始・終了、仕事内容・持ち物、単価（日給／時給）・昼食・交通費・インセンティブ・備考。
- 「保存」で2件の下書きと束を同じ取引で作る（片方だけ保存されることはない）。依頼書番号は2件それぞれに付く。
- 「送付へ進む」で2件を同時に確定（PDF・送付先・版の固定）し、同じ送付先へ同時に送る。片方のPDF作成に失敗したら両方とも確定しない。
- 監査ログ：order_request_bundle_created、order_request_bundle_confirmed（2件の版ID・送付先数）。各依頼書の既存の確定・送信の監査はそのまま出す。

### 3.2 稼働者の受諾と予定表
- LINEには1通で届く。「ダブルヘッダー（2件）」の見出し、日付、1件目・2件目の時間と場所、移動の間隔、報酬の合計、PDF 2通へのリンク、ボタンは「2件とも受ける」「2件とも断る」の2つ。
- 返事は2件の送付行に同じ取引で記録する（2つの系列を決まった順にロックして、同時操作でも食い違わない）。辞退理由は1回入力で両方に記録。
- 束に入っている送付行に、1件ずつの古いボタン・Web画面から返事が来たら受け付けず「2件まとめて回答してください」と返す。
- Web確認画面（LIFF）も同じく1件の依頼として表示し、まとめて返事する。
- 予定表は、その日に2行（時間順）並び、「W」の印と相方の案件名を出す。稼働日数は1日のまま。
- 回答の催促（send_due_reminders）は束で1通にする。
- 監査ログ：order_request_bundle_acked / order_request_bundle_declined（束ID・2件の送付行ID）。各送付行の order_request_acked / declined も残す。

### 3.3 当日の起床確認
- 今の仕組み（人×日で、その日最初の開始時刻の3時間前が期限）のままで、1件目の開始時刻が基準になる。変更は表示だけ。
- 起床状況の画面と運営への知らせで、1件目の案件名に「ほか1件（W）」を添える。

### 3.4 実績
- 実績は今どおり案件ごとに入る（CSV取り込み・確認）。同じ人・同じ日に2案件の実績があってよい。
- 束の情報から「ダブルヘッダーなのに片方の実績しかない」日を一覧で知らせる（売上漏れ・支払漏れの防止）。実績は自動で作らない・変えない。

### 3.5 報酬（2つの合計の出し方）
- 依頼書・LINE・報酬見込みの「合計」は、1件目の単価＋2件目の単価（どちらも日給のとき）。片方でも時給なら「時給分は実績で決まります」と出し、合計の金額は出さない（今の見込みの決まりと同じ）。
- 実際の支払は今どおり実績×案件ごとの単価で、支払明細に2行出て合計される。支払の計算は変えない。
- まとめ価格（2件で1日いくら）を使うかは Q2 で決める。使う場合は、合計との差を調整行として明細に残す設計を別に出す。

### 3.6 請求
- 変更なし。2件はそれぞれの依頼元へ、それぞれの依頼書の金額確定・月次請求（DEC-074・DEC-136）で請求する。同じ依頼元なら同じ請求書に明細が2行並ぶ。
- 請求の1人日は「同じ人・同じ案件・同じ日」（DEC-135）のままで、ダブルヘッダーは案件ごとに1人日ずつになる。

### 3.7 PDF
- 案件ごとのPDF（今のPDF）を2通作る。それぞれの右上などに「ダブルヘッダー 1/2（相方：依頼書番号）」を1行足す。本文・様式は変えない。
- すでに作ったPDFは作り直さない。

### 3.8 一覧での見え方
- 依頼書一覧は2行のままで、「W」の印、相方の依頼書番号へのリンク、2行をつなぐ縁取りを付ける。絞り込みに「ダブルヘッダーのみ」を追加。
- 返事の一覧（送付先ごと）は束で1つにまとめ、「2件とも受諾」「2件とも辞退」と出す。
- 参加カレンダーは同じ日に2案件として出す（今の系列×日付×人の数え方のまま）。

### 3.9 テスト用と正式用の区別
- 2件は必ず同じ区分。混ぜると保存できない。区分は確定後に変えない（今の決まりのまま）。
- テストの通知は今の期限付きテスト通知スイッチに従う。
- テストから正式への切り替え（DEC-137）は束ごとに2件まとめて行う。1件だけの切り替えはできないようにする。
- 同じ日の予定の重複チェックは、今どおり正式とテストで分ける。

## 4. 時間が重なる場合・移動時間が足りない場合

- 判定に使う時刻：1件目の終了（翌日終了を含む）と、2件目の集合時間（無ければ開始時間）。
- **重なり**（2件目の集合・開始が1件目の終了より前）：保存はできる（下書き）が、確定・送付はできない。画面とサーバーの両方で止める。
- **移動時間の不足**：束に「移動に必要な時間（分）」を持ち、1件目の終了から2件目の集合・開始までがそれより短ければ警告。送付するには「確認した」のチェックと理由が必要で、理由は監査ログ（order_request_bundle_gap_acknowledged）に残す。分数の決め方は Q5。
- 送付先の人に、同じ日に束の外の別の予定がすでにある場合は、送付の設定で警告（送付は可能）。運営決定方式の確定時の「同じ日に別案件」チェックは、相方の案件だけを例外にする。
- 1件目・2件目の変更版を作ったときも同じ確認をやり直す。

### 追加する試験（予定）
- 2件の保存・確定が片方だけ成功しないこと、区分の混在を拒否すること
- 時間の重なりで確定・送付できないこと、移動時間不足は確認と理由が無いと送れないこと
- まとめた受諾・辞退で2つの送付行と予定が同時に変わり、片方だけの返事は拒否されること
- 運営決定方式で相方の案件が同日チェックに引っかからず、束の外の予定は今どおり止まること
- 報酬見込みが2件の合計になり、稼働日数が1日であること
- 2件の請求が別々の明細になり、二重請求・請求漏れが起きないこと（今の請求の試験が変わらず通ること）
- 既存の依頼書（束なし）の保存・送付・返事・PDF・請求・支払の試験がすべて変わらず通ること
