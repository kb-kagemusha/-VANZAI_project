# 同じ公式LINEで運営・稼働者メニューを使い分ける実装計画

作成・更新: 2026-10-26。状態: 0.53.0の実装・検証済み。配備と本人の実機確認は別に記録する。設計の経緯として本計画を残し、実際の操作と今回の範囲は [運用手順](LINE_OPERATOR_PORTAL_RUNBOOK.md)、実装での確定事項はDEC-119を参照。第三者AI向けの [レビュー資料](LINE_OPERATOR_MENU_REVIEW_BRIEF_2026-10-26.md) も実装差分の入口として維持する。

実装時の確定: 運営専任者は3項目の専用画像、兼務者は運営4項目と既存稼働者メニューの往復。Userの管理ロール判定を必須にし、既存の全員向け出勤可否カレンダーにも同じ管理ロール制限を追加した。自動催促/運営通知は別工程のままで、今回有効化しない。

## 目的と前提

同じLINEで稼働者と運営スタッフの両方に承認された人が、必要なメニューへ往復できるようにする。運営専任者には運営メニューを表示し、一般の稼働者の既存6項目は維持する。

- 運営申請・承認と稼働者登録は実機で通った。承認済みでも現状は共通の稼働者用メニューが表示される。登録をやり直す必要はない。
- 運営スタッフは全員が管理画面Userを持つ（DEC-117）。LINE本人→有効な運営連携→スタッフ→対応する有効なUserを確認する。兼務かどうかは同じLINEの有効な稼働者連携で判定し、Userのworker_id/vanzai_staff_idの両方を要求しない。氏名や電話でIDを自動推定しない。
- 既存の `scripts/line/rich_menu.py apply` は全員の既定メニューを変更するため、運営メニューの配布には使わない。既存の `line_rich_menu_releases.enabled_actions` は稼働者機能の公開判定に使われており、運営用メニューの記録で置き換えない。
- 仕様根拠: `docs/spec/DESIGN_SPEC_v0.3.md` §5.1、§6.1、§14、§16、`docs/decisions/DECISION_LOG.md` DEC-056、DEC-066（補記を含む）、DEC-110〜118。

## 利用者に見える完成形

| LINEの有効な登録 | 表示するメニュー | 切替 |
|---|---|---|
| 稼働者のみ | 現行の稼働者用6項目 | なし |
| 運営のみ | 運営用4項目 | 「稼働者用への切替」を押すと登録がない旨を案内し、切り替えない |
| 両方 | 運営用4項目、または稼働者用6項目＋「運営用へ」 | 双方向に1操作で切替。最後に本人が選んだ側を保持 |
| いずれも無効 | 公式LINEの既定表示 | 利用できる機能はない |

初回の個別割当は、承認済み運営本人に**運営用**を提案する。兼務者の稼働者用画面は既存6機能を維持し、「運営用へ」を追加した個人別の派生メニューにする。一般の稼働者にこの派生メニューを配らない。既定メニューが稼働者用のままでも、有効な運営連携がない人が業務情報にアクセスできないよう各APIで判定する。

運営用の「起床状況」「カレンダー」は、LINE内のスマートフォン向け専用画面で開く。**有効な運営スタッフ全員が、担当制限なしで全案件・全稼働者の予定と起床状況を閲覧できる**。LINE本人確認を利用し、毎回の管理画面ID・パスワード入力は要求しない。ただし運営スタッフは全員が対応する管理画面Userを持つ前提とし、各APIでUser・スタッフ・LINE連携の有効状態を確認する。既存IDとスタッフの対応が未登録なら管理者が確認して紐付け、LINEだけの運営アカウントを作らない。稼働者としての連携は運営閲覧の必須条件にしない。全件閲覧と未報告通知の受信は別で、通知は既存のwake_alert_receiveで選別する。

**閲覧の認可は管理画面と共通の既存権限を利用する**（DEC-118）。起床状況はwake_status_read、出勤可能日/配置カレンダーはavailability_read、依頼書/参加日のカレンダーはorder_readを、各APIの最新User権限で確認する。カレンダー入口にどちらかの権限があっても、権限のない側のデータを混ぜて返さない。案件/稼働者検索も呼出元の閲覧権限と表示に必要な項目に限定する。「全運営が全件を見られる」は、対象の運営役割へ必要な既存閲覧権限を設定して実現し、権限を無視する例外は作らない。既存役割を共有する他の人への影響を確認し、必要なら既存の独自役割管理を利用する。今回の文書更新で実際の権限を付与した意味ではない。

site_managerはDEC-056と現行can_access_projectで**全案件参照**、CSV提出は担当分だけ。ROLE_PERMISSIONS内の「担当案件のみ」という古いコメントを新仕様の根拠にしない。LINE側にも独自の担当制限を追加せず、管理画面と同じ閲覧範囲にする。将来の担当範囲制限は既存の権限チェックボックスだけで実現できるとは断定せず、範囲モデルと両画面の仕様変更を別途検討する。

閲覧対象は案件名・日付・予定時刻・稼働者名・参加/予定の状態・起床報告の有無と時刻など、カレンダーと起床状況の確認に必要な項目。単価・請求・支払・口座・住所・生年月日・緊急連絡先は返さない。電話番号の一律除外は本人指定ではなく初期設計の制約だったため撤回し、**本人へのLINE催促後も未報告の場合、運営への通知に当該稼働者の氏名・登録電話番号を含める**（DEC-116）。一覧画面にも電話番号を載せるかは別の表示上の選択で、今回の必須要件にはしない。業務画面からの編集、代理報告、連絡記録の登録、手動LINE送信はこの段階の対象外。自動通知は後述の別工程で設計する。

カレンダーは月表示・日付別詳細、起床状況は当日を初期表示として日付を選べる形を提案する。全案件・全稼働者を検索・絞り込めることと、その日の予定がない人を起床未報告として扱うことは別。未報告の対象・予定/変更中/取消/試験データの扱いは既存の予定・起床判定に合わせ、二重の判定ロジックを作らない。未報告の全員を遅刻と断定しない。

「自分の登録情報」は運営用LIFF `2011980694-65RRy7fo` の画面を再利用し、招待申請とは別の表示モードを設ける。LINEのIDトークンをサーバーで検証し、運営連携とスタッフ有効状態を毎回確かめ、**本人の氏名・電話番号だけを読み取り専用で表示**する。招待URLや招待トークンなしでも承認済み本人は開けるようにする。他人のID指定・登録情報の編集・管理者操作は提供しない。

## 実装順序と確認条件

| 順 | 作業 | 完了の判断 |
|---|---|---|
| 1 | 有効な運営・稼働者連携をLINEユーザーIDで照合し、停止・ブロック・再連携時の状態を整理する。メニュー種別と本人の希望側を永続化する | 未承認、無効、運営のみ、稼働者のみ、兼務の判定が再現できる |
| 2 | 運営専任用・兼務運営用・兼務稼働者用の個人別メニュー画像と押下領域を作る。兼務稼働者用には既存6機能と戻り口を収める。作成・画像登録は既定メニュー設定と分離する | 押下先、文字、スマホでの視認性を確認でき、全員向け既定メニューは不変 |
| 3 | 兼務者の往復にLINE標準のrichmenuswitchとエイリアスを用いる。通常の切替ごとにサーバーから再割当しない。切替後のWebhookは結果の補助記録に使う | 有効な兼務者が往復でき、Webhook記録の失敗で切替を妨げない。古い表示から操作されても各業務APIで権限を確認する |
| 4 | 承認・連携解除・有効/無効変更時に本人のメニュー種別を同期する。unfollow時に運営連携を失効させ個人別割当の解除を試み、follow時に現在の有効な連携から再判定する | 再友だち追加だけで運営連携は復活しない。解除失敗は記録・再試行し、follow時にも古い運営表示を修正する |
| 5 | LINE本人確認による運営専用セッション、既存権限で認可するカレンダー/起床状況の読取APIと画面、本人情報画面を追加する。既存の予定・起床集計を共通化する | 毎回のパスワード入力なしで、対応する有効な管理画面Userと必要な最新閲覧権限を確認して表示する。全運営へ必要権限を設定した運用で全範囲を閲覧でき、無権限・無効・未承認は拒否 |
| 6 | 自動テスト、検証環境、本人1名の実機で段階公開し、最後に対象者へ順次適用する | 下の受入条件を満たしてから全対象者へ展開 |

**外部API失敗への備え:** 通常の往復はLINEに任せ、切替ごとの希望世代・直列化・割当ジョブは作らない。DB管理は承認/解除等に伴う割当対象・適用結果・失敗/再試行に絞る。承認成功後の割当失敗で登録結果を取り消さない。承認/解除の再同期時には現在の連携を読み直し、古い承認ジョブが無効者へ運営メニューを再配布しない。切替Webhookの到着順だけで現在の表示側を断定せず、再配備で有効な本人の選択を不要に上書きしない。LINEの現在の割当取得も利用して整合を取る。秘密トークンや生のLINE IDを監査本文へ複製しない。

**安全な戻し方:** 新しい個人別メニュー割当だけを対象者単位で解除し、既定の稼働者用メニューへ戻す。登録・承認・既存の稼働者向け公開記録は取り消さない。配布中のメニューIDを先に削除しない。連携解除後はメニュー表示が残ってもAPIで利用を拒否する。

## 受入テスト

1. 同じLINEで両方が有効な本人は運営4項目を確認し、稼働者用へ切替えて既存6機能を使い、運営用へ戻れる。アプリ再起動後も最後の選択が残る。
2. 運営専任者は運営情報を表示でき、稼働者機能・切替を使えない。稼働者専任者のメニューと既存機能は変わらない。
3. 招待発行中・申請待ち・却下・無効・ブロック・連携解除では、該当する運営APIを使えない。unfollow後の解除失敗と、follow時の表示修正を検証する。解除とLINE側切替が競合しても業務情報を返さず、再同期で適切な表示へ戻す。
4. 自分の登録情報は本人分のみ。改変したLINE ID、他人のスタッフID、期限切れ認証では取得できない。氏名・電話の編集はできない。
5. 必要な既存閲覧権限を持つ管理画面Userと連携した運営専任者が、LINE内で毎回パスワードを入力せず全案件・全稼働者を閲覧できる。必要権限なし、User未紐付け/停止/削除、稼働者専任者、未承認者、無効者、期限切れは当該データの専用APIを使えない。全件閲覧できてもwake_alert_receiveがなければ未報告通知を受け取らない。
6. 通常の連続切替ではサーバー再割当を実行しない。切替Webhookの欠落/重複/遅延とアプリ再起動でもLINEの切替が成立することを確認する。承認/解除の割当API失敗は再試行でき、古いジョブで解除済みの運営表示を復活させない。
7. 実機で友だち追加済みの兼務者1名を先行適用し、別の稼働者端末で既定6項目が変わらないことを確認してから順次公開する。
8. 有効なセッションを保ったままwake_status_readを外すと次の起床APIから403になる。availability_read/order_readの片方だけを許可した場合に、許可した側だけが表示される。両方なければカレンダーのデータを返さない。管理画面とLINEで同じUserの権限/閲覧範囲が一致する。画面に取得済みの値も権限エラー後に残さず案内へ切り替える。

## 利用者側で必要なこと／決めること

- **実機確認:** 兼務登録済みのLINE端末を1台、先行テストに使う。新しい登録・LIFF作成は原則不要。
- **閲覧範囲は決定済み:** 全運営スタッフが全案件・全稼働者を閲覧できるよう、管理画面Userの対象役割に必要な既存閲覧権限を設定する。既存IDとスタッフの対応・対象役割・変更の影響を公開前に確認する。LINE内の毎回のパスワード入力は不要。未報告通知の受信は別権限のwake_alert_receiveで設定する。
- **確認したい運用上の選択:** 初回は運営用を表示し、その後は最後の選択を保持する案を採る。運営専任者の4番目は表示し、押した場合は稼働者登録がない旨を案内する。別の表示を希望する場合は画像制作前に決める。

起床未報告対応はDEC-066/116/117に従い、**起床期限後に5分おき3回本人へLINE催促 → 未報告ならwake_alert_receiveを持つ運営へ氏名・登録電話番号をLINE通知 → 必要に応じ電話 → 後から報告があれば運営へ追加通知**とする。詳細は [起床未報告対応の計画](LINE_WAKE_ESCALATION_PLAN_2026-10-26.md) を参照。時刻・回数・通知先を未確定へ戻さない。駅すぱあとAPI導入前は自動催促を開始しない。メニュー完成を自動通知公開の意味にしない。

## 実装レビューのための設計案（名称は仮）

- 公開画面: 同じ運営用LIFFを利用するが、登録用ページは招待専用のままとし、認証後の閲覧は別ページ/ルートへ分離する。LIFF入口は招待解析前に画面種別を振り分け、閲覧で招待なしエラーに落とさない。既存招待の `liff.state` 復元と閲覧への遷移を実機確認する。LIFF追加が必要になった場合は理由と設定を提示する。
- 運営セッション: `POST /api/line/operator/session` で生のIDトークンをサーバー検証し、有効なLineStaffLink・VanzaiStaff・対応するUserを解決する。旧OPSコード方式も同じ有効性/対応確認を必要とする。`LineWorkerSession` の30分・ハッシュ保存方式を参考に、用途を分離した `LineOperatorSession` を追加する。管理者JWTや稼働者セッションを代用しない。
- セッション行にはトークンハッシュ・LINE本人・スタッフID・連携ID・対応User ID・期限を保持する案。各要求で同じ連携・スタッフ・対応Userの有効性/対応関係と当該APIの最新権限を再確認する。セッション発行時の権限を固定保存して認可に使わない。解除後の再連携やUser変更で古いセッションを復活させない。トークンをURLへ付けず、画面側の保持はメモリを基本とする。Userの対応がない/曖昧なら管理者確認へ案内する。
- 読取API案: `GET /api/line/operator/me`、`GET /api/line/operator/calendar`、`GET /api/line/operator/wake-status`、必要項目だけの案件/稼働者検索。日付範囲・件数上限・ページングを設け、全期間・全件の無制限取得を避ける。JSTの日付境界、予定なし、取消、試験データを検証する。
- 既存の `src/api/line_daily_routes.py` の管理者認証を外す変更は行わない。共通の集計サービスに管理画面用・LINE閲覧用の別の認証入口と返却項目を接続する。共通化の前後で既存画面の値が変わらないことを検証する。
- DB追加案: 運営セッション、承認/解除等の個人別メニュー適用状態（LINE本人単位の一意性、対象種別、失敗・再試行）、運営用メニュー/エイリアス定義と公開状態。通常の切替のための反映世代やキューは不要。承認/解除等の再試行基盤は既存基盤の適合を確認する。DDLは実装前に確定する。画像登録と本番有効化を分離し、準備中は承認後の自動配布を開始しない。
- 監査案: 運営セッション発行、メニュー希望変更・反映成功/失敗・再同期と公開操作。スタッフID等を対象にし、LINE IDやトークンは監査本文へ出さない。業務データの読取アクセスは本人・日時・操作・結果の最小記録とし、一覧本文を複製しない。
- スマホで読める文字・日付移動・読み込み/空/エラー/認証期限切れの表示を確認する。起床状況は更新ボタンと最終取得時刻を用意し、古い表示のまま現在の状態と誤認させない。
- 実装順序は「認証・読取API・画面 → 個人別割当の結合確認 → 実機1名 → 段階公開」を守る。上の作業表1〜5を準備しても、画面が未完成のメニューを先行配布しない。

## LINE公式仕様

- [ユーザー単位のリッチメニュー](https://developers.line.biz/ja/docs/messaging-api/use-per-user-rich-menus/): 本人別に割り当て、解除すると既定メニューに戻る。
- [リッチメニューの概要](https://developers.line.biz/ja/docs/messaging-api/rich-menus-overview/): 利用には公式アカウントとの友だち関係などの条件がある。
- [リッチメニューの切替](https://developers.line.biz/ja/docs/messaging-api/switch-rich-menus/): richmenuswitchとエイリアスによるLINE側の往復を利用する。公式例にある全員向け既定メニュー変更は今回の配布に流用しない。
