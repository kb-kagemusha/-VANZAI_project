# Googleフォーム連携（App311/App312 → App165）運用設計案

更新日: 2026-02-12

## 1. 結論（方針評価）
提示された方針は妥当です。特に以下4点は事故防止に有効です。

1. worker_id はフォーム入力させない
2. 重複防止キーで登録前チェック
3. 初回は無効、承認時に有効化 + WRK4桁採番
4. 失敗/更新/承認を監査ログ化

## 2. アプリ役割（推奨）
- App312（個人Googleフォーム連携）: 申請受付・審査用（正本ではない）
- App311（法人Googleフォーム連携）: 法人申請受付（workersではなく suppliers 系に連携）
- App165（workers）: 稼働者マスタ正本

## 3. フィールドマッピング（App312 → App165）
App312（ラベル） -> App165（フィールドコード）

- 氏名(姓) -> last_name
- 氏名(名) -> first_name
- 姓(フリガナ) -> lastname_furigana
- 名(フリガナ) -> firstname_furigana
- 個人事業主屋号 -> bussiness_name
- 紹介者/下請け -> introducer_supplier
- メールアドレス -> email
- 携帯電話番号 -> phone
- 郵便番号 -> zipcode
- 都道府県 -> pref
- 市区町村以下 -> city_etc
- 建物名･部屋番号 -> name_of_building
- 性別 -> sex
- 備考 -> memos
- 経由先 -> group

注意:
- App312 の「稼働者ID」は入力されていても App165 反映時は使用しない（無視）
- App165 の `worker_id` は承認時に採番して設定する

## 4. App311（法人）について
App311 は法人情報のため、原則 App165 ではなく紹介者/下請けマスタ（App199/187系）連携が自然です。

App311 を workers に入れると、個人と法人の意味が混在し、将来の支払・請求ロジックで破綻しやすくなります。

## 5. 重複判定ルール（推奨）
主キー候補（正規化後）:
- 第1候補: 氏名(姓)+氏名(名)+姓(フリガナ)+名(フリガナ)+携帯電話番号

補助キー:
- メールアドレス一致
- 氏名+フリガナ一致（電話欠損時）

正規化:
- 全角/半角統一
- 空白除去
- 電話番号のハイフン除去
- カナの表記ゆれを可能な範囲で吸収

## 6. 承認・採番フロー（推奨）
1. フォーム送信 -> App312 登録
2. 管理者が App312 を審査
3. 承認時（操作トリガ）:
   - 重複チェック
   - 重複なし: App165 に登録（is_active=有効, worker_id=WRK+4桁）
   - 重複あり: 差戻し/要確認ステータスへ
4. 監査ログを記録

採番仕様:
- App165 の `worker_id like "WRK%"` 最大値 + 1
- フォーマット: `WRK` + 4桁ゼロ埋め
- 例: 最新 WRK0059 -> 次 WRK0060

同時承認対策:
- worker_id をユニーク制約
- 採番衝突時は再取得して再試行

## 7. 監査ログ必須項目
最低限記録する項目:
- action（create/update/approve/reject/error）
- actor（実行者）
- at（日時）
- source_app / source_record_id（311/312の元レコード）
- target_app / target_record_id（165の対象）
- dedupe_key
- before_json / after_json
- result（success/skip/error）
- reason（差戻し理由など）

## 8. 実装オプション
A. KintoneカスタマイズJS（承認ボタン連動）
- メリット: UI一体化
- デメリット: 競合制御・監査処理が複雑

B. サーバースクリプト（推奨）
- メリット: 採番・重複判定・監査を厳密実装しやすい
- デメリット: 定期実行/運用設定が必要

## 9. 今回の推奨結論
- 方針は採用して問題ありません
- ただし App311 は workers に直接入れず、法人（supplier）系に流すのが安全です
- App312 -> App165 は承認時採番・監査ログ付きで実装するのが最も堅牢です
