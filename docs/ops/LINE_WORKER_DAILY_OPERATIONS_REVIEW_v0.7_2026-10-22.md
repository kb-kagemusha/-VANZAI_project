## 1. 結論と前提

前回のV3-01〜03は計画に反映され、DEC-063〜066への記録も確認した。運用開始前、依頼書を予定の起点にすること、会計接続を後段に分けることは引き続き前提にする。

今回の主要な確認対象は、新しく増えた「個人ごとの参加日」「日付指定の受諾」「受諾後の増減依頼」。**本人の依頼を運営が承認し、既存の依頼書の実勤務日の範囲であれば、修正版なしで参加日を増やす設計は妥当**である。直前依頼を至急通知し、未承認の間は確定済みの勤務と監視を維持する案も支持する。

残る指摘は、この方針の否定ではなく、本文に残る旧案の整理と、申請・合意・承認履歴・改訂との整合性である。本文を直近のユーザー説明・DECへそろえ、その状態モデルを決めてからDDLへ進むべきである。

A0・A1の詳細設計に進むこと自体を止める必要はない。A1+の全機能を前倒し実装する必要もない。ただし、作成時の個人不参加日はA0・A1から必要なので、その保存と受諾時の固定だけは最初のモデルへ含める。

本レビューは静的照合で、コードの変更・実行テスト・本番確認はしていない。計画・DECに加え、このチャットでの2026-10-22のユーザー説明を根拠に更新した。別の対話の原文を検証したものではない。原計画書・DECISION_LOGは変更していない。

優先度：P1＝該当工程の設計・実装前に解消、P2＝該当工程の仕様・受入条件へ追加。

## 2. 今回の説明を踏まえた評価

目的は、「変更依頼を送っただけで勤務が変更された」と本人が誤認することを防ぎ、運営が欠員を把握・判断できるようにすること。申請の受付と勤務変更の確定を分ける設計で達成する。

| 方針 | レビュー評価・実装上の意味 |
|---|---|
| 変更依頼はいつでも受け付ける | 妥当。送信だけで勤務予定を変えず、承認待ちとして記録する。電話への切替を理由にLINE受付を閉じない |
| 当日・翌日分は即時通知・至急表示 | 妥当。依頼の受信日時をJSTで判定し、変更対象日に当日・翌日が含まれる場合に至急扱いとする。通知の見落としに対する運用はV7-06で補う |
| 承認までは起床監視を続ける | 妥当。現在確定している勤務を通常どおり監視し、運営への起床通知には「変更依頼中」と添える。既に起床報告済みなら通常の規則どおり催促は止める |
| 本人へ未承認の意味を明示する | 必須の受入条件にする。受付返信は「依頼を受け付けました。**運営が承認するまでは、予定どおりの勤務です**」とする |
| 本人の増加依頼を、運営承認後に修正版なしで反映する | 妥当。申請が対象としていた版・勤務条件を固定し、その依頼書の実勤務日に限って反映する。本人が依頼していない別日や別条件まで同意済みと扱わない |
| 運営が本人に参加日の増加を提案する | 本人からの増加依頼とは別の経路。本人同意を得る方法は引き続き別途定義する |

増加依頼の場合は、受付返信に「追加を希望した日は、承認されるまで参加確定ではありません」も添えると、増加側の誤認も防げる。

「範囲内」は日付の開始〜終了の間という意味ではなく、work_groupsから共通の除外日を除いた実際の勤務日を意味する。共通休業日や、依頼書にない勤務日の追加・時刻や場所等の共通条件変更には修正版が必要。作成時にその人だけ不参加とした日については、共通の実勤務日であり、本人の追加依頼を運営が承認した場合に個人の参加日を更新する。

このレビューは設計案を技術・運用面から支持するもの。計画・DEC-065に残るPendingの記載は、今回説明された採用方針と、運営発の追加提案・LIFF方式など未確定の詳細に分けて整理する。

冒頭ではA0・A1の業務判断がすべて確定済みとされているが、実装者が読む本文には逆の提案が残っている。

| 内容 | 正本・新しい決定 | 残っている記述 |

| 変更依頼の増減 | L-36 / DEC-065：減少・増加の両方を受け付け、運営判断 | Q22d：減少だけ、増加は修正版 |
| 日付指定受諾 | L-35 / DEC-065：依頼書ごとに許可し、許可時は即確定 | §11ではQ22a/bが回答待ちとして残る |
| 除外日・発注中止 | L-29/L-34、DEC-063/065で確定 | §7.3・§7.4に未確認・未決のラベルが残る |

さらに、§7.1 / DEC-063の「予定訂正は必ず修正版」という原則と、DEC-065の承認済み個人参加日変更の関係を明記する。共通の勤務条件変更は修正版、本人申請に対する個人の参加日変更は承認記録を根拠に派生予定を更新する、と適用範囲を分ける。直近の説明に従い、条件を満たす本人の増加依頼について修正版を不要とする方針へそろえる。旧案である「増加はすべて修正版」を実装根拠にしない。

### V7-02 [P1 / A0・A1のモデル] 個人に提示した日・合意した日・変更申請を区別して保存する

対象：計画248–271行、§9、§10。DEC-065。

「送付先ごとの参加日」という共通概念にまとめる方針は妥当。ただし、提示内容、現在の合意、未承認の申請を1つの可変値として扱うと、誰がいつ何に同意したかを再現できなくなる。§9には現在、個人参加日・受諾可能日・部分受諾許可の保存先が記載されていない。

最低限、次の責務を分けて詳細設計する必要がある。

- 依頼書の共通勤務日：work_groupsから全体の除外日を除いた日。
- その人へ提示した日：上記から作成時の個人不参加日を除いた日。送付行に対応する確定時点の内容として保持する。
- その人が合意した日：提示日の全部、または部分受諾が許可されている場合に本人が選んだ日。受諾日時・対象版・経路と一緒に固定する。
- 受諾後の変更申請：現在の合意を直接書き換えず、申請内容と審査状態を保持する。承認した変更だけを新しい合意状態として反映し、申請・承認・変更前後の履歴を残す。

これは4つの新規テーブルを必須にする要求ではない。列・JSON・履歴表の選び方は詳細設計で決めてよいが、意味を区別する必要がある。

PDFが全員共通で個人の日付を載せないなら、本人への送付文と受諾確認には個人の提示日を明示する。後日の再表示では、当初の提示と現在の参加日を区別できるようにする。

初期段階から追加する受入例：

- Aさんだけ2日目が不参加でも、Bさんの提示・予定・受諾に影響しない。
- 部分受諾が不許可の場合、「全日」は全体期間ではなく本人へ提示した全勤務日を意味することを明記する。
- 範囲外・共通休業日・他人の送付行の日付を指定しても受諾できない。
- 参加日が0日の選択を、受諾・辞退・入力エラーのどれとして扱うかを固定する。
- 確定後の個人不参加日を上書きして、過去の受諾内容を変えない。

根拠：現行OrderRequestVersionはdraft_worker_idsを持ち、OrderRequestDeliveryはack_statusとacked_atを持つが、個人日付の合意履歴はない。通常受諾のackedだけでは、その人がどの日を受諾したかを表現できない。

### V7-03 [P1 / A1+前] 改訂・取消・別申請の処理後に、古い変更申請を承認しない

対象：計画253–258、273–318行。DEC-065。

例：v1の参加日について変更申請→v2の依頼書を受諾して勤務条件が変わる→運営がv1に対する古い申請を承認。このとき日付だけを反映すると、旧条件に対する依頼で新条件の予定を変更してしまう。

既存の文書ロックは同時実行の順序をそろえるが、後から処理される古い申請の有効性までは保証しない。

修正案：

- 申請に対象の文書・版・送付行・申請時の参加日状態の版を結び付ける。申請の変更前・希望後の日付と実行者を保存する。
- 承認時に文書ロックを取り、対象版・参加日状態が申請時から変わっていないか再確認する。異なれば自動適用せず、失効・再確認等の明示した状態へ回す。
- 承認・却下・申請取消・二重押しを冪等にする。別の申請の承認後に古い状態で上書きしない。
- §7.5の共通ロック対象に、個人参加日の変更申請の承認と、それに伴う予定更新も加える。
- 承認状態・参加日更新・派生予定更新・監査・結果通知の送信予定を同一トランザクションで保存し、通知はcommit後に送る。通知失敗で未承認へ戻したり、成功通知だけ残したりしない。

「いつでも依頼できる」は受付の方針。過去の勤務や将来の会計確定済みデータを無条件に上書きできる意味にはしない。受付と適用可否を分け、Track B導入後は既定の会計保護も適用する。

受入例：申請後の新版確定・新版受諾・発注中止・送付先除外／同じ申請を同時承認／2件の申請を逆順に承認／通知失敗後の再試行。

この項目の詳細はA1+前でよい。A0・A1を止める理由にはしないが、最初の参加日モデルに将来の履歴・競合判定を妨げる上書き方式を採らない。

### V7-04 [P2 / A1+前] 将来の参加日がない人にも、増加依頼の入口を残す

対象：計画253、367、374行。

⑤の一覧は「受諾済みで、稼働日が今日以降に残っているもの」に限定されている。一方、今後の日を増やす依頼は⑤から行う。

例：依頼書全体は1〜10日、本人は1〜3日だけ参加。4日に8日の参加を追加したくても、一覧が本人の将来参加日を基準にしていれば依頼書が表示されず、変更を依頼できない。

修正案：稼働予定を確認する一覧と、参加日を変更できる依頼書の検索条件を分ける。発注が有効で本人の受諾・送付先情報がある依頼書へ、履歴等から到達できるようにする。全日を不参加へ変更した場合も扱いを定める。取消済みや送付先除外済みの依頼を再開できるようにする要求ではない。

### V7-05 [P2 / 日付指定受諾の公開前] 日ごとの充足状況の「必要人数」をどこに持つかを決める

対象：計画260–261行、§9、§10。

日ごとの充足状況は部分受諾を即確定する運用の確認手段だが、依頼書モデルには必要人数の定義がない。既存のrequired_countはShiftSlot側にあり、シフト枠はB2まで生成しないため、A1+ではそのまま利用できない。

修正案：まず依頼書・勤務日（必要なら勤務グループ）ごとに必要人数を保存する場所を決める。送付人数を必要人数と推測しない。確定参加・未回答・変更申請中を分けて表示し、同じ人を重複計上しない。

満員でも受諾を拒否するかどうかは、現時点の「許可時は即確定」という決定とは別のルールである。今回の設計だけを理由に拒否を追加せず、まず不足・超過を見えるようにする。

A1+を正式な工程として段階表に加え、部分受諾の許可設定、選択受諾、変更申請・承認・通知、充足表示のモデルと受入条件を対応付ける。作成時の個人不参加日だけを実装するA0・A1と混ぜない。

### V7-06 [P2 / 変更依頼の公開前] 至急通知に加え、未確認・未承認の状態を運用で追えるようにする

対象：計画254–258行、今回のユーザー説明、DEC-065。

朝6時に当日の欠勤希望が届いた場合、即時通知と明確な受付返信は必要。ただし、通知を送っただけでは運営が確認したことにならず、欠員の可能性がなくなるわけでもない。

設計上必要な扱い：

- 受付後は、申請内容・対象日・増減・理由・受付時刻と、現在の確定予定を運営が確認できるようにする。
- 「運営未確認」「確認済み・承認待ち」「承認／却下」を区別する。通知のAPI受付を運営の確認済み状態として扱わない。
- 当日・翌日分は送信予定を申請と同時に保存し、日次ジョブを待たずに通知する。通知先不在・送信失敗でも、申請と至急表示は残す。
- 承認前の減少申請では、既存の勤務日・充足人数・通常の起床監視を変えない。未承認の増加申請では、追加日を参加確定・充足人数・通常の起床監視へ入れない。どちらも申請中として別表示する。
- 承認後は差分を反映し、減った勤務の不要な未送信催促を取り消し、追加勤務の監視を再計算する。他の勤務の監視を止めない。追加日が既に期限を過ぎていた場合は、既定の要確認処理へ回し、過去分の催促を一斉送信しない。
- 承認・却下の結果を本人へ通知し、通知失敗を記録・再試行する。本人に結果が伝わっていない案件を運営が追えるようにする。

運用上の提案：直前分を確認する担当者・代行者と、勤務開始が迫っても未確認の場合の電話確認・エスカレーションをRUNBOOKへ定める。これはレビュー側の提案であり、具体的な待ち時間や電話の義務をユーザー決定として追加するものではない。「通知が来るので誰かが見るはず」という運用にしない。

### 追加する受入試験

| 場面 | 期待する結果 |
|---|---|
| 当日6時に当日欠勤を申請 | 即時通知の対象・至急表示。本人へ受付と未承認の意味を返信。確定予定と通常の監視は維持 |
| その日が起床報告済み | 変更申請を理由に起床催促を再開しない |
| 翌日を含む複数日の増減申請 | 増減の両方を保存し、至急対象日があると分かる。承認前は確定日を変えない |
| 本人が追加日を申請し、運営が承認 | 対象版・現在状態・実勤務日を再確認。修正版を発行せず、本人だけの参加日・派生予定を更新。承認履歴と結果通知を残す |
| 追加日が共通休業日・勤務範囲外 | 個人参加日の通常承認では反映しない。共通条件を変更する修正版の経路へ回す |
| 申請後に新版受諾・別申請承認・発注中止 | 古い条件の申請を現在の予定へ無条件に適用しない |
| 至急通知の宛先なし・送信失敗 | 申請と至急表示が残る。通知済み・確認済みとは扱わない |
| 減少承認と催促送信が競合 | 送信前の再確認で、不要になった催促を抑止。他の勤務への監視は継続 |
| 承認結果通知の送信に失敗 | 承認・参加日変更を二重実行せず、同じ結果通知を再試行できる |
