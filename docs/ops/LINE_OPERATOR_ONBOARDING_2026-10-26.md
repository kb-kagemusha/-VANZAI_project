# 運営スタッフの公式LINE登録・メニュー切替の進め方

更新: 2026-10-26。対象: 同じ公式LINEを使う運営スタッフ。

## 現在の準備状況

段階1の招待発行・失効、2項目の本人申請、共通確認待ちでの承認・却下を0.52.7として実装し、0.52.8で本番反映済み。2026-10-26、本人提供の運営用LIFF `2011980694-65RRy7fo` を専用設定へ新規保存し、API再起動後の公開入口でenabled=trueを確認した。招待は管理者が個別発行できる状態。本人のスマホでの登録・承認の通し確認はこれから行う。段階2〜4は未公開で、現在の6つのメニューや通知動作は変えない。

検証: 新規運営申請・設定21件、既存の運営LINE連携/稼働者申請50件、画面16件、両画面ビルドに成功。今回のマイグレーションについて、試験用SQLiteで既存行の保持・追加DDL・空状態の差し戻し・履歴ありの差し戻し拒否を確認した。過去のPostgreSQL専用マイグレーションをSQLiteで通したという意味ではない。実LINE・PostgreSQLでの同時操作と通知到達は、有効化前の実機確認に残る。

## 決まっていること

- 本人の入力は氏名・電話番号の2項目。住所・最寄り駅・生年月日は求めない。
- 管理者が招待し、本人がLINEで申請、管理者が内容を確認して承認する。
- サイドバーは共通の「登録確認待ち」1つ。区分「稼働者」「運営スタッフ」で見分け、件数は合算する。
- 承認前に運営スタッフや通知先を自動作成しない。LINE連携で管理画面のID・権限を付けない。
- 稼働者と運営を兼ねる人は同じLINEを両方へ紐付ける。人物を氏名・電話だけで自動統合しない。
- メニューは運営として承認・連携済みの本人だけを切り替える。全員向けの既定メニューを運営用に変更しない。

## 段階と完了条件

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 1 登録と承認 | 期限付き・1申請限りの招待、LINE本人確認、2項目の申請、共通確認待ちで承認・却下 | 承認までマスタ不変、二重申請/二重承認を防止、既存スタッフへ紐付けても既存プロフィールは上書きしない |
| 2 個人別メニュー | 運営用の画像・押す場所・遷移先、本人ごとの切替、兼務者の戻り導線 | 運営の1名だけで切替・解除・兼務切替を実機確認。他の稼働者の6メニューが変わらない |
| 3 通知の到達確認 | 本人への試験通知、ブロック時の扱い・代替連絡 | 送信受付と実機到達を分けて確認。失敗したまま運用開始扱いにしない |
| 4 起床未報告の自動通知 | 未報告の判定、通知先、対応者・再通知、重複防止 | 既存ロードマップの起床期限等を決定してから実装。登録・メニューの完成だけでは提供済みとしない |

## 利用者にお願いすること

### いま必要な設定: 運営用LIFFを1つ追加

同じ公式LINEの本人確認に使っている、既存のLINE Loginチャネルで作業する。新しい公式LINE、Messaging APIチャネル、プロバイダー、シークレット、アクセストークンは不要。

1. [LINE Developers](https://developers.line.biz/console/)へログインする。
2. 現在の稼働者登録用LIFFがあるLINE Loginチャネルを開く。別のプロバイダーへ作らない。
3. LIFFタブで「追加」。既存のLIFFは編集しない。

| 設定 | 値 |
|---|---|
| アプリ名 | VANZAI 運営スタッフ登録 |
| サイズ | Full |
| エンドポイントURL | https://vanzai-portal.com/public/line-operator-registration |
| Scope | openid |
| ボットリンク機能 | On (Normal)、現在使っている同じ公式LINEを紐付ける |
| Scan QR / モジュールモード | オフ |

4. 発行された **LIFF ID**（数字-英数字）と「稼働者登録用と同じLINE Loginチャネルに作った」ことを開発へ知らせる。IDは公開識別子で、パスワードではない。
5. チャネルが開発中なら利用対象を確認する。試験参加者全員が開けるか実機で確認する。

チャネルシークレット、アクセストークン、パスワードをチャットに貼らない。管理画面のIDや役割は必要な人に別途設定する。

### 設定後の確認

1. 本人が公式LINEを友だち追加する。
2. 管理者が「運営スタッフ登録・一覧」→「LINE登録の招待リンク」を開き、招待リンクを発行して本人へ個別に渡す。準備中の案内が出る場合は運営用LIFFの設定を先に行う。
3. 本人がLINEから開き、氏名・電話番号を入力し、確認して申請する。
4. 「登録確認待ち」の区分が「運営スタッフ」であること、赤い件数に含まれることを確認する。
5. 管理者が申請の氏名・電話と本人を照合し、新規作成か既存スタッフへのLINE紐付けかを明示して承認する。
6. 運営スタッフ一覧にLINE連携済みで表示されることを確認する。
7. メニュー公開は段階2の実装・実機確認の後に行う。段階1だけではメニューは変わらない。

既存の稼働者登録や生年月日の入力を、運営の登録のためにやり直す必要はない。既に登録した「運営太郎」の稼働者申請を運営へ自動変換しない。残す/却下する判断は管理者が行う。

## 開発側が行うこと

- 既存の登録申請ヘッダを再利用し、運営申請の本文・LINE本人・招待失効状態だけを1表へ追加する。マイグレーションは既存データを書き換えない。
- 招待は推測困難なトークンを使用し、DBにはハッシュだけを保存。公開URLは発行時にだけ返す。失効操作を提供する。
- 暫定運用案として招待の期限は24時間。1リンクで1申請。期限後の未申請・失効済みリンクは拒否する。申請済み内容は固定し、同じ本人・同じ内容の再送は同じ受付結果へ戻す。
- LINEの生のIDトークンをサーバーで検証し、クライアントからのユーザーID・表示名を本人確認には使わない。
- LINE公式アカウント側のプロフィール取得も確認し、照合できない場合は友だち追加/ブロック/チャネル設定を案内して停止する。成功だけで今後の通知到達を保証しない。
- 承認は管理者限定、申請行と既存スタッフ行をロック。LINE紐付けの一意制約で同時操作の二重登録を防ぐ。既存スタッフの氏名・電話・担当ロールは自動更新しない。
- 招待発行/失効、申請、承認/却下、LINE紐付けを監査する。トークン、LINE ID、氏名・電話を監査本文へ複製しない。
- LINE設定は秘密情報を含まない専用JSONに分離し、既存.env/.env20261006は閲覧・変更しない。LIFF ID未設定時は登録入口と招待発行を無効にする。

### 専用設定の反映（開発側）

`line-operator-config.example.json`を雛形とする。実ファイル名はGit管理外の`line-operator-config.json`。`enabled`と`liff_id`だけを保存し、既存のLINE LoginチャネルIDは従来設定を参照する。新規作成前に実ファイルの存在を確認し、存在する場合は上書きせず現在の設定と変更内容を確認する。利用者がLIFF IDを渡した後、同じチャネル・同じ公式LINEであることを実機確認し、有効化する。新しい秘密情報は不要。

APIは`POST /api/operator-registration/invitations`、公開受付は`POST /api/line/operator-registration/submissions`。共通確認待ちは既存`GET /api/registration-requests?line_only=true&status=pending`で両区分を取得する。既存の稼働者審査APIへ運営申請を渡しても承認できない。管理者向けの申請本文は専用APIに限定し、LINEのユーザーIDは返さない。

## 運営用メニュー（2026-10-26 本人の選択で確定）

| 項目 | 動作・表示範囲 |
|---|---|
| 起床状況 | 起床報告の確認画面への入口。業務情報を見る権限はメニューの表示だけで付与しない |
| カレンダー | 稼働予定を確認する画面への入口。既存の閲覧権限に従う |
| 自分の登録情報 | LINEで本人を確認し、自分の運営スタッフ登録情報だけを表示する。他のスタッフの氏名・電話等は返さない |
| 稼働者用への切替 | 同じLINEが稼働者としても有効に連携済みの人だけ、稼働者用メニューへ切り替える。運営専任者には利用できないことを案内する |

LINEの友だち追加・運営申請の承認だけでは、管理画面のID・操作権限は付与しない。起床状況とカレンダーは、既存管理画面を開く方式ならログインIDと必要な権限を別途設定する。LINEだけで閲覧できる運営専用画面を新設する場合は、閲覧範囲の承認を別途決める。今回の4項目の選択を、全運営スタッフへ業務情報の閲覧権限を自動付与する許可とは解釈しない。

4項目の名称は確定したが、個人別メニューの切替・本人情報の表示・兼務者の往復導線は段階2の未実装部分。稼働者側から運営用へ戻れる導線も作り、失効・無効化された運営スタッフは運営メニューを使えないようにする。全員向けの既定メニューは変更せず、実機確認後に承認済みの運営本人へ個別適用する。

## 公式仕様の根拠

- [ユーザー単位のリッチメニュー](https://developers.line.biz/ja/docs/messaging-api/use-per-user-rich-menus/): 個人別メニューを既定メニューより優先して表示できる。
- [リッチメニューの概要](https://developers.line.biz/ja/docs/messaging-api/rich-menus-overview/): 個人別のリンクには公式LINEの友だちであることが必要。
- [LINEのトークンをサーバーで確認する](https://developers.line.biz/ja/docs/liff/using-user-profile/): 本人のLINE IDをクライアントの自己申告で信用しない。
