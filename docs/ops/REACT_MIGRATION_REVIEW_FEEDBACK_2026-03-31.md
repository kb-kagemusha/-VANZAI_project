# React前提 Kintone全面移行計画 レビュー反映メモ

更新日: 2026-03-31

## 1. 位置づけ
この文書は、外部 AI から受けた計画レビューを、実行可能な差分として整理したメモです。

元の相談用文書は [docs/ops/REACT_MIGRATION_REVIEW_REQUEST_2026-03-31.md](docs/ops/REACT_MIGRATION_REVIEW_REQUEST_2026-03-31.md) とし、本書ではそのレビュー結果をもとに、計画へ追加すべき論点と修正方針をまとめます。

## 2. 総評
レビューの結論は、計画の骨格自体は妥当であり、特に以下が評価されています。

1. 既存 FastAPI + PostgreSQL 資産を再利用し、画面層を置き換える方針は正しい
2. Phase 分割は論理的で、Phase 1 を参照系に絞る判断も妥当
3. Sprint 1 から Sprint 3 の順序はおおむね合理的
4. 過剰設計にはなっていない

一方で、Sprint 1 に着手する前に確定しておくべき設計詳細がいくつか残っています。

## 3. 主要指摘と反映方針

### 3.1 Phase 1 の期間と Phase 2 着手条件が弱い
指摘:
- Phase 1 は安全だが、参照のみの期間が長引くと Kintone での書き込み運用が残り、二重運用の負荷が常態化する
- Phase 1 の想定期間と、Phase 2 に進む判断基準を明示すべき

反映方針:
1. Phase 1 の想定期間を Sprint 1 から Sprint 3 までの 3 スプリントと明記する
2. Phase 2 着手条件に、受入基準達成に加えて運用担当レビュー完了を入れる
3. Kintone の参照専用化または継続利用の判断ポイントを追加する

### 3.2 blocker の定義を整理すべき
指摘:
- 一覧系 API 不足は blocker ではなく、新規開発タスクに近い
- 既存コードの不整合と未実装機能を同列に置くと、計画上の意味がぶれる

反映方針:
1. blocker は既存不整合に限定する
2. 一覧系 API 不足は Sprint 1 以降の backend task として扱う

### 3.3 API 共通仕様に不足がある
指摘:
- エラーレスポンス形式が未定義
- search の意味が曖昧
- sort_by の許可カラム制約がない
- limit の上限値がない

反映方針:
1. 400、401、403、404、500 の共通エラーレスポンス形式を定義する
2. search は API ごとに対象カラムを明示する
3. sort_by は許可リスト方式にする
4. limit のデフォルト値と最大値を決める

### 3.4 site_manager の実装前提が未確定
指摘:
- 担当案件に限定する方針は妥当だが、site_manager と案件の紐付けをどのモデルで持つかが不明
- Sprint 1 の時点で設計判断が必要なのか、単なる修正なのかが読み取れない

反映方針:
1. Phase A で site_manager の案件紐付け正本を確定する
2. 第一候補は Project.primary_manager_id / secondary_manager_id とする
3. これで不足する運用要件がある場合のみ中間テーブル案を検討する
4. Sprint 1 着手前に一覧 API のフィルタ戦略まで明文化する

### 3.5 route / role / permission 周辺に未定義事項がある
指摘:
- トークンリフレッシュ戦略が未記載
- CORS 設定が未記載
- CSRF の扱いが未記載
- accounting に監査ログ閲覧権限を与えるか再確認が必要

反映方針:
1. 認証方式を Bearer token 前提で固定する
2. 初期方針としては silent refresh を必須にせず、期限切れ時は再ログインへ戻す方式を候補にする
3. Nginx リバースプロキシで /api を同一オリジン配下に寄せる前提を明記する
4. Cookie セッションを使わない限り CSRF 対策は不要と整理する
5. accounting の audit log 閲覧可否を別途確認事項として残す

### 3.6 Sprint 2 の監査ログ前提確認が必要
指摘:
- 既存の POST /api/audit/search が actor、action、date range、period_key を十分にサポートするか事前確認が必要

反映方針:
1. Sprint 2 開始前の確認項目として既存 audit search の対応条件を明示する
2. 足りない場合は Sprint 2 で request schema と query service を補強する

### 3.7 受入基準を数値化すべき
指摘:
- 主要件数一致の判定が曖昧
- Sprint 1、Sprint 2 にも同様の受入手順を入れるべき
- パフォーマンス基準がない
- 対応ブラウザ / デバイスが未定義

反映方針:
1. 参照一致は原則完全一致とする
2. Sprint 1 から Sprint 3 の各完了条件に件数比較、代表データ比較、権限確認を入れる
3. Phase 1 の最低性能目標を定める
4. 対応環境を管理画面は PC + Chrome 最新版を標準と明記する

### 3.8 Phase 2 着手前提に運用面の条件が不足している
指摘:
- Kintone の参照専用化判断基準がない
- Phase 2 以降はデータ変更が入るため、バックアップ / リストアとステージング環境が必要

反映方針:
1. Phase 2 開始条件にバックアップ / リストア手順確認を追加する
2. Phase 2 開始条件にステージング環境の確保を追加する
3. Kintone 停止範囲の判断ポイントを段階的に整理する

## 4. 計画書へ追加すべき項目

### 4.1 Phase A に追加
1. 認証方式の確定
2. トークン更新方針の確定
3. 同一オリジン構成と CORS 方針の確定
4. site_manager 紐付けモデルの確定
5. 共通エラーレスポンス形式の確定
6. sort_by 許可カラム方式の確定
7. limit のデフォルト値と最大値の確定

### 4.2 Phase 1 受入基準に追加
1. 件数比較は原則完全一致
2. Sprint 単位で件数比較と代表データ比較を行う
3. 初期表示と一覧応答の性能目標を追加する
4. 対応ブラウザを明示する

### 4.3 Phase 2 着手条件に追加
1. バックアップ / リストア手順の確認完了
2. ステージング環境の準備完了
3. Kintone の参照専用化判断ポイントの明文化

## 5. 優先対応順
1. blocker 定義の整理
2. site_manager 紐付け方針の確定
3. API 共通仕様の不足補完
4. 認証周辺の未定義事項整理
5. Sprint 受入基準の数値化
6. Phase 2 着手条件の補強
