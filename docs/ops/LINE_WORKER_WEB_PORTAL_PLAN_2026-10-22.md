## 1. 目的と成功条件

トークの返信をたどらず、稼働者が次の3点を開いてすぐ把握できる状態にする。

1. いつ働くか: 月全体の予定日、直近7日の仕事の詳細。
2. いくらになりそうか: 受諾済みの仕事に基づく月間報酬見込みと稼働日数。
3. 何を確認すべきか: 未回答の依頼・変更確認待ちと、確認先への導線。

成功条件は、メニューから目的の画面に入り、月間と直近7日をその場で切り替えられ、確認待ちから該当依頼書へ進めること。操作回数・開くまでの所要時間は試作時に実機で確認する。情報量を増やすこと自体を目的にしない。

## 5. 画面構成案

```text
稼働予定                          2026年10月
確認が必要です  2件                 ［確認する］
報酬見込み  約120,000円    稼働 8日
受諾済みの予定に基づく目安・インセンティブ除外

［月間］［直近7日］
  月間: ［前月］2026年10月［翌月］
        予定日に●。日付選択でその日の仕事を表示
  直近7日: 対象期間を明示し、仕事を日付順のカードで表示

［受託済みの発注依頼書を見る］
最終取得日時
```

上記の金額・件数は説明用の架空値。画面デザインの確定版ではない。

### 5.1 月間

- 月初〜月末を表示。仕事のある日に●、予定なしは印なし。空欄を「稼働可能」とは扱わない。
- 同日複数件でも●は1つ。日付を開くと全件表示。稼働日数は重複を除いた日付数。
- 変更確認中は色だけに頼らない印と凡例を用意する。日付詳細には状態を文章で示す。
- 共通除外日・本人不参加日・承認済み参加日を、既存の稼働予定へ反映された結果に従う。
- 月を移動したら報酬・稼働日数も同じ月へ更新する。

### 5.2 直近7日

- 日本時間の今日〜6日後。月間で選んだ月とは独立して「10/29〜11/4」のように期間を表示。
- 日付・案件・開始終了時刻・稼働場所・集合場所（登録がある場合）・変更状態・依頼書導線を表示。
- 報酬見込みは「2026年10月の報酬見込み」のように月を常時明示し、7日間の合計と誤解させない。
- 日をまたぐ仕事は開始日を所属日とし、終了時刻に「翌日」を表示する案（要レビュー）。

### 5.3 確認事項と依頼書

- 未回答: 本人宛てに送付済みで、現在回答可能な系列の受付版に対する依頼。下書き・未送付・取消・送付先除外・旧版・回答済みを含めない。今有効な受諾がないこと（受諾が終了した後に新しい版が送られた場合は未回答に入る）。運営の参加カレンダー（統合計画 D-07）と同じ判定を使う。
- 変更確認待ち: 旧版を受諾しており、新しい回答受付版の確認が必要なもの。同じ系列の「未回答」と二重に件数を数えない。
- 件数は確認対象の依頼（系列）数とし、勤務日数・カード数ではない。
- 期限超過の分類・回答可能性は既存サーバーの判定と一致させる。回答できないものを「回答してください」と表示しない。
- 「確認する」で対象一覧→依頼書詳細/PDFまたは既存の回答経路へ進める。開いただけで受諾・確認済み・既読にしない。
- 0件は小さく「確認待ちはありません」。取得失敗を0件に置き換えない。
- ⑤は受諾済みの適用版を一覧表示し、新版の確認導線は受託済みと混同しない。過去の依頼書をどこまで出すかは未決（P-08）。
- 統合計画 ③ で、受託済みの依頼書に「参加日の変更を依頼」「依頼を取り下げる」を置く。今日以降に追加できる実勤務日が残る依頼書・未処理の依頼がある依頼書も一覧に出す（A1+ 計画 §4.1）。

## 6. 報酬見込みの計算提案と未決条件

### 6.1 基本方針

「選択月の受諾済み予定から求めた基本報酬の概算」。過去日と未来日を含むその月全体の予定額とする案。実績済み金額への置換は行わない。支払予定額・手取り額・確定報酬とは呼ばない。

インセンティブを除外し、依頼書の単価に含まれる交通費・昼食代は再加算しない。別途支給の交通費・昼食代・立替経費については、備考から金額を推測せず今回の概算には追加しない案。該当時のみ短く「別途精算分は含みません」と表示する。これはU-05から自動確定した仕様ではなく、レビュー・決定対象である。

### 6.1b 決定事項（2026-10-22 ユーザー回答。統合計画 F-01・F-02・D-02・D-06）

| 項目 | 決定 |
|---|---|
| 日給 | 依頼書に記載した1日あたりの日給を、本人が参加する日ごとに1回数える。多少の時間のずれは日給に含まれる。大幅に延びた場合は現場管理者から運営へ連絡が入る（システムでは扱わない） |
| 同じ日の複数勤務 | 1つの依頼書の中では勤務グループの日付が重ならない（入力検証で保証）ので、同じ依頼書で同じ日に2回数えることはない。別々の依頼書で同じ日に働く場合は、それぞれの日給を数える。稼働日数は日付で数える（1日） |
| 時給 | 見込みの対象外とし、対象外の件数を表示する |
| 税 | 依頼書の記載金額をそのまま表示し、税は加減しない |
| 日をまたぐ勤務 | 勤務の開始日の月に数える |
| 端数（D-08、決定） | 入力は日給にも小数点以下2桁まで許している。合計は小数のまま計算し、表示時に円未満を切り捨てる。既存データは書き換えない |
| 過去の表示の証明 | 不要（D-06）。今の見込みを再計算できればよい |

下の §6.2 の表のうち、この決定と食い違う「要決定」「案」は、この決定を優先する。

### 6.2 入力・算式（案）

| 項目 | 提案 |
|---|---|
| 対象予定 | 本人のformal区分、activeまたはchanging、選択月内。cancelled/supersededとtestは合計から除外 |
| 単価の根拠 | 本人が受諾した適用版の確定済みsnapshot内の構造化rate_groups。現在の単価マスタや未受諾の新版を使わない |
| 日給 | 適用する単価×合意した勤務日数。同じ日・work_group内の重複行は重複計上しない |
| 同日複数グループ | 各グループで日給が発生するか、同一依頼の1日1回かは要決定。日給を行数分だけ無条件に足さない |
| 時給 | 単価×対象予定の有償時間。有償時間・休憩・丸めが確定するまでは計算対象外として件数を示す案 |
| 変更確認中 | 旧い受諾版の金額と参加日を継続し「変更確認待ち」を示す。新版受諾後に切替。両版を足さない |
| 月跨ぎ | 勤務開始日が属する月に計上する案。依頼全体の金額を複数月へ丸ごと加算しない |
| 算定不能 | 金額・単価対応・時刻等が不明なら0円とみなさない。「算出できた予定の合計」と対象外件数を表示。全件不能は「算出できません」 |
| 精度 | Decimal使用。端数の規則と式の版を固定し、表示時にだけ所定の円単位へ丸める案。丸め方は未決 |
| 税・控除 | 表示額の税基準は未決。税・源泉徴収等を推測して加減せず、手取り見込みとして表示しない |

テスト予定は、既存LINEでは【テスト】付きで表示される。Webでも検証用に別表示するか非表示にするかを決めるが、通常の報酬・稼働日数には混ぜない。

### 6.3 具体例（上記案の検証用）

- 日給15,000円、本人参加8日なら120,000円。込みの費用はさらに加算しない。
- 旧版15,000円×8日から、新版16,000円×8日へ変更確認中なら、旧版の120,000円を表示。新版受諾後に128,000円へ切替。
- 上記に算定不能な時給勤務1件があるなら「算出済み分 約120,000円／算出対象外1件」とする。全予定の合計であるように表示しない。
- 日給15,000円で10/31と11/1に勤務なら、各月に15,000円ずつ。2勤務日を両方の月へ加算しない。

注記案: 「受諾済みの予定から算出した目安です。インセンティブは含みません。実際の支払額は変わる場合があります。」不足条件がある場合の表示をこの注記だけで済ませない。

## 7. 最小データ構成・API案

### 7.1 再利用するデータ

LineWorkerLink、Worker、WorkerScheduleEntry、OrderRequestSeries、OrderRequestVersion、OrderRequestDelivery、DeliveryParticipationStateと既存PDF発行処理を使う。公開用DTOに必要な項目だけ取り出し、管理者用API・内部発注元snapshotを直接返さない。

原則は閲覧専用の派生表示。新しい給与テーブル・日給会計モデルは作らない。実装前にDDL要否を確定し、不要なら理由を記録する。概算を再現可能にするため、元版ID、参加状態ID、対象勤務、適用単価、算式版、算定理由と取得日時を追跡できる形にする。

概算の履歴保存は **不要に決定（v0.2、統合計画 D-06）**。確定した版の内容と参加日の状態は追記のみで変わらないため、元の版・参加日の状態・対象月・対象の予定の集合・計算式の版を指定すれば、同じ結果を再計算できる。以下は v0.1 の検討内容として残す：推奨案はサーバー側に明細付きの算定記録を追記保存し、headerの合計を明細から集計する。必要最小列: worker_id、month、calculation_version、calculated_at、source_revision、明細ごとのversion_id/source_state_id/勤務日/work_group_id/単価/時間/概算額/対象外理由。新規テーブルならmigrationと参照制約・保存期間を詳細設計する。予定表へ金額を上書きしない。

### 7.2 APIの責務（パスは未確定）

- 本人認証・短命セッション生成: LIFFトークンを検証し、有効なLINE連携と稼働者状態を照合。
- ホーム取得: 月の予定、月間報酬・日数、確認事項件数と取得時点の識別子。
- 直近7日取得: 今日から7日間の本人予定を全件取得。ページ分割時の欠落・重複を防ぐ。
- 確認事項／受託済み依頼書一覧取得: 状態・版と本人権限をサーバー側で判定。
- 依頼書を開く: 本人との対応を再確認し、既存の期限付きPDF発行を安全に再利用。

同じ応答内の合計・日数・明細は同一DBスナップショットで整合させる案。別リクエスト間でrevisionが変わったら表示を更新する。閲覧で受諾・取消・送信を実行しない。更新機能を追加する場合は別設計として既存の系列ロック・再検証・監査を守る。

## 8. 認証・情報保護・障害時の動作

- LIFFのIDトークン等をサーバーで検証し、対象チャネル、有効期限、主体を確認する。クライアント申告のworker_id・プロフィールを本人確認に使わない。
- LINE LoginとMessaging APIのプロバイダー・主体対応、既存連携との照合方法、LIFFのURL・scope設定を実装前に確認する。既存登録チャネルが利用可能だと決めつけない。
- 本人の有効な連携・稼働者状態と機能公開状態を各APIで再確認する。解除後にセッションだけで閲覧を続けられないようにする。
- メニューURLは共通の入口。LINE ID・金額・恒久的な個人別トークンをURLへ載せない。他人に入口URLを転送しても、転送先は自分のデータだけを取得する。
- 他人の予定・PDFの直接ID指定、内部発注元・請求単価・他の送付先情報の漏えいを防ぐ。公開PDFの共通記載内容自体の変更は対象外。
- 個人情報・報酬応答のキャッシュを抑止し、戻る操作・再ログイン時の他人のデータ残留を防ぐ。セッション方式に応じCSRF・XSS対策を詳細設計する。
- 未連携・無効・期限切れは本人確認や運営への案内にする。取得失敗を「予定なし」「0円」「確認なし」と表示しない。再試行を用意する。
- 復帰時・月移動・回答後に再取得。オフラインでは古い値を最新として表示しない。
- iOS/AndroidのLINE内で確認し、外部ブラウザでは必要なログインを案内する。

公式確認先（前の検討で参照、実装時に再確認）:
- https://developers.line.biz/ja/docs/liff/overview/
- https://developers.line.biz/ja/docs/liff/using-user-profile/
- https://developers.line.biz/ja/docs/messaging-api/using-rich-menus/

## 9. 監査と会計への非干渉

既存の受諾・辞退・取消・予定生成・改訂・PDF発行の監査を継続する。Web閲覧ではこれらの業務状態を変更しない。新規監査の提案は、メニュー公開/停止、概算算定（記録ID・算式版・根拠参照）、必要に応じ本人確認失敗。トークンやLINE ID全文を記録しない。通常閲覧ログの必要性・保存期間は要決定。

invoice/payout/actual/closingと会計用の単価スナップショットを、閲覧や概算生成で変更しない。締め後でも見込みと確定支払は別であり、概算を確定支払へ書き戻さない。追記する概算履歴は会計伝票ではない。
