# ワークスペース全体のコードレビュー（2026-10-13）

## 対象と前提

- 主対象は稼働中の Ver.0.42.0、コミット 2b46d68 の作業用コピー。src、管理Web、スタッフWeb、モデル・マイグレーション・試験の構成を確認し、認証・登録・承認・CSV・時間計算・請求・支払・締め・OCRの主要経路を調査した。
- ワークスペース直下は Ver.0.35.1、コミット f323a45。未コミットの移動・文書変更・競合コピーがある。最新コードと混同して上書き・同期してはならない。
- Ver.0.42.0 の変更は作業用コピーの CHANGELOG.md に記録済み。古い直下のCHANGELOGへ新しい版番号だけを転記すると、package.jsonと不一致になる。
- このレビューではアプリコードとVPSを変更していない。再現確認は一時SQLiteとモックブラウザだけで行った。全ファイルの全行を精査した保証、実機・PostgreSQLの検証完了を意味しない。

## 優先度の高い修正

### R01: 締め後・請求発行後のCSV洗い替えを止めていない（高、再現済み）

根拠: src/services/csv_import.py の import_csv（105行目）、replace_scope処理（238行目前後）。APIのCSV入口にも締め状態確認がない。

Hard Close済みかつ請求発行済みの実績へ修正CSVを取り込むと、成功1件になり、元の実績が superseded へ変わった。発行済み帳票と集計の整合性が崩れる。

対応: 取り込み対象の案件・期間と、発行／承認済み明細の実績参照を洗い替え前に検査する。固定済みの範囲を拒否し、同時に締める処理とも競合しないようにする。部分取り込みでも固定済み実績を変更しない受入試験が必要。

### R02: 請求・支払が休憩前の総時間を数量として使う（高、再現済み）

根拠: src/services/invoice_service.py:116、src/services/payout_service.py:100・759。集計は src/services/aggregation.py:286 で calc_minutes_billable を使う。

総時間540分、休憩60分、対象時間480分、売上単価1,500円の例で、集計は12,000円、請求小計は13,500円になった。CSV hours優先で開始終了がないケースでは総時間0となり、請求が0になる可能性もある。

対応: 時間数量の正本を確定し、請求・支払・集計を揃える。時間単価と日額単価を分け、休憩・丸め・CSV hoursのみのケースを検証する。発行済み帳票を直接再計算しない。

### R03: 発行済み／承認済みの同じ実績を再計上できる（高、再現済み）

根拠: src/services/invoice_service.py:508、src/services/payout_service.py:471 の対象実績抽出。生成時に除去するのは preparing のみ。個別生成APIからこれらのサービスが呼ばれる。

既存の請求を発行した後に再生成すると、同じ actual_id の明細を持つ2枚目が作れた。承認済み支払と新しい支払にも同じ actual_id が入った。月次バッチのスキップ処理は個別APIを保護していない。

対応: 発行／承認済み明細との重複をサービス共通で拒否する。同時生成と、案件別／月次一括の範囲重複も防ぐ。追加実績だけを請求する場合は差額・訂正のルールを決める。

### R04: 二者承認が承認者名の文字列比較だけになっている（高、再現済み）

根拠: src/api/main.py:9059〜9065、src/services/closing.py:220。Hard Closeとその解除にも同様の承認者引数がある。

存在しない non-existent 相当の承認者名を渡してもSoft Closeを解除できた。本人の認証による承認、有効な承認者の存在と権限を確認していない。

対応: 解除申請と、別の認証済みユーザーによる承認を分ける。期限・回数・理由のガードと一緒に状態遷移を確定する。単にユーザー名の存在を調べるだけでは本人の承認の証明にならない。

## その他の修正候補

### R05: 請求下書きの再生成が明細の制約で失敗する（中、再現済み）

根拠: src/services/invoice_service.py:488〜505。親だけを session.delete し、明細の非NULL invoice_id と衝突する。

明細付きの preparing 請求を再生成すると IntegrityError（invoice_lines.invoice_id）になった。

対応: 下書き更新の範囲を明確にし、既存明細も整合するよう更新する。物理削除が必要なら、非破壊を基本とする仕様との整合を確認する。支払の同型処理も確認する。

### R06: 請求再発行サービスが明細を複製していない（中、再現済み）

根拠: src/services/invoice_service.py:426〜485。

再発行すると合計14,850円のまま、明細0件の請求が作られた。現在、この関数を呼ぶ公開API経路は確認できなかったが、サービスとしては明細正本の原則を満たさない。

対応: 金額・明細・宛先などのスナップショットを新版へ複製し、再発行前後の内容とPDFを検証する。

### R07: 別のLINE本人で再認証した後、新しい表示値と比較票を取得しない（中、静的に確認）

根拠: apps/admin-web/src/pages/PublicLineRegistrationPage.tsx:265〜272、apps/admin-web/src/lib/lineRegistrationForm.ts:74。

別の本人への切替時は入力と比較票を消すが、新しいフォーム取得は同じ本人の分岐だけで行う。切替先が紐付け済みなら、保存済み情報を表示できず、比較票なしで新しい送信が409になる。同じ本人でも再認証の途中で紐付けが成立すると、表示値と比較票の更新が不足する。

対応: 本人変更時は旧入力を消した後で新しい本人のフォームを取得する。同じ本人は入力・再送内容の保持と、紐付け先変更の検出を両立させる。保存済み再送を先に返す仕様は維持する。

### R08: OCR端末番号の補正が無効入力を有効な別番号へ変える（中、既存試験で再現）

根拠: src/services/ocr/parsers/settlement_terminal_id.py:84〜93。G/gを0へ無条件変換する。

GGGGGGGG-GGGG-GGGG-GGGG-GGGGGGGGGGGG が全ゼロのUUIDに変わる。端末番号の読み取り違いは照合先の誤りにつながる。実際のOCR試料でも端末番号の期待値と異なる試験が5件ある。

対応: 厳密な入力検証とOCR候補の補正を分ける。補正は原文・確信度と確認待ちを残し、根拠のない別番号を自動確定しない。

## 試験結果と不足

- バックエンド既存試験: 648件中608件成功、25件失敗、15件スキップ（76.98秒）。SQLiteのみ。
- 失敗内訳: LINE6件、OCR／照合18件、役割API1件。LINE6件は新しいフォーム比較票を送っていない旧試験。OCR／照合の失敗は仕様差・試料・実装の切り分けが必要で、全てを実運用の不具合とは断定しない。
- 登録画面の既存ブラウザ試験: 10件成功、1件失敗。Web新規登録試験が変更前の「氏名」枠を探して止まる。新しい4枠と入力欄への保存済み情報表示は、現在の試験では十分に検証されていない。
- PostgreSQL競合15件は接続設定なしのためスキップ。過去版の合格を今回のコードの合格とみなさない。
- 確認用に作成したデータは一時SQLite内だけ。アプリコード・VPS・業務データの変更はない。
