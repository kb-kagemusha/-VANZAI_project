# 外部レビューへの回答と本人の訂正

更新: 2026-10-26。対象は計画レビュー。実装の合否を示すものではない。

## 3回目のレビューへの回答（DEC-118）

- ①の既存Userの閲覧権限を確認する提案を採用した。起床状況はwake_status_read、出勤可否/配置はavailability_read、依頼書/参加日はorder_readを各APIで最新DBから確認する。全運営の全件閲覧は、対象の運営役割への必要権限の設定で実現する計画であり、LINEだけの役割迂回は設けない。文書修正で本番の役割設定まで変更した意味ではない。
- カレンダー入口の「availability_readまたはorder_read」は、どちらかがあれば両方のデータを返してよい意味ではない。データ種別ごとに認可・表示し、権限剥奪は次の要求から既存LINEセッションにも反映するテストを追加した。
- レビューの「site_managerは担当案件だけ参照」は現行の正本と実装には合わない。DEC-056とsrc/services/auth.pyのcan_access_projectは全案件参照。担当案件限定なのはcan_submit_project_csvのCSV提出。ROLE_PERMISSIONS内に残る古いコメントと、実際の認可処理を区別する。よってLINEだけを担当分へ変更する追加判断は不要とし、両画面の閲覧範囲を揃える。
- ②のレビュー依頼文・作業5の「管理画面ログインなし」は「毎回のパスワード入力なしで、対応Userと最新の閲覧権限を確認」に修正。③の運用書の古い段落はDEC-117/118を反映した現行計画へ統合した。
- 将来の「担当範囲の制限」まで既存の閲覧許可チェックボックスだけで変更できるとは約束しない。現行は全件参照であり、担当範囲を追加する際は範囲モデルと管理画面/LINE双方の仕様を別途揃える。

## 再レビューへの回答（DEC-117）

- DEC-066参照漏れの指摘を採用。期限式、5分おき3回、権限wake_alert_receiveによる通知先、通知後の報告の追加通知、対象外勤務、駅すぱあとAPI導入条件、8割の通数警告は決定済みだった。通知計画とDEC-116の「未確定」記載を訂正した。本人へ有効性を再質問しない。
- 本人から「LINEだけの運営は存在しない」と回答。運営全員が管理画面Userを持つ前提で、LINE本人→スタッフ→既存Userを対応させる。LINE内で毎回パスワードを入力しないことと、管理画面IDが存在しないことを区別する。運営専任という語は稼働者を兼ねない意味で、Userがない意味ではない。
- 通知先は既存Userのwake_alert_receiveと有効なスタッフ/LINE連携で判定し、VanzaiStaff側へ新しい受信可否項目を追加しない。全運営の全件閲覧は維持し、通知受信の権限とは区別する。User停止/削除や権限剥奪は送信時に再評価する。
- DEC-066の後続補記は、初稿の「手入力で先行」「受信者0ならadmin全員へ送る案」より優先する。駅すぱあと導入前の自動催促は開始しない。実導入・契約が済んでいるかは未確認であり、計画上の決定と稼働状態を混同しない。
- 送信不能・ブロック・LINE未連携時の連絡運用が未定義という指摘も採用。5分おき3回の業務ルールを再決定することと、遅延/再起動時の送信時刻境界を設計することは分ける。

再レビューでは、関連文書に「管理画面IDのない運営を許可」「通知先/催促回数を未確定とする」古い案が現行仕様として残っていないか、Userとの対応・権限変更時の失効・通知宛先の重複防止を確認してほしい。

## 本人からの訂正（最優先）

未報告を見つけてすぐ電話する運用ではない。**公式LINEから本人への催促が先で、その後も未報告なら運営へ氏名・登録電話番号をLINE通知し、運営が必要に応じて電話する。** 現状の要望はこの運営通知が届くこと。電話番号を画面で閲覧できることや、連絡記録をLINE画面で入力することを必須としていない。

## 指摘ごとの判断

| 指摘 | 判断と理由 | 計画への反映 |
|---|---|---|
| ① 起床状況に電話番号がない | 一律除外が本人指定ではなかった指摘は妥当。ただし、既存画面がphoneを返すことは「未報告なら即電話」という業務順序の根拠にならない | 本人への催促が先。未報告継続時の運営通知へ氏名・登録電話番号を含める。画面への番号掲載・連絡記録入力は未決定 |
| ② エイリアス方式で切替を簡略化 | 採用。LINE公式のrichmenuswitchで往復できる。通常切替ごとのサーバー割当処理は不要。ただし連携失効時の表示修正や失敗時の再試行まで不要になるわけではない | 切替ごとの世代管理/キューを省く。承認・失効時の割当状態と再同期は残す。再起動後の保持とWebhook欠落を実機確認 |
| ③ 運営専任者には切替領域を置かない | 3項目の専任者用画像は合理的な候補だが、本人確定は運営4項目。構成変更は未決定 | 画像制作前の表示選択として残す。押せない切替を置く初期案を確定仕様として扱わない |
| ④ follow/unfollowのメニュー修正 | 採用。現行コードはunfollowで運営連携を失効させるがメニュー解除・follow再判定はない | unfollowで解除を試み、followで現在の有効な連携から再判定。再友だち追加だけでは運営権限を復活させない |
| ⑤ 兼務者の起床報告が1操作遠い | 操作負担は認識するが、起床報告追加や朝の強制切替は本人未指定 | 現段階では往復導線を確保。4項目の追加変更や時刻での自動切替は採用決定しない |
| ⑥ 既定メニュー・管理API・認証用途の分離 | 維持 | 全員の既定メニューは変更せず、管理APIの認証を緩めない |
| 別案a 招待と閲覧ページの分離 | 採用。招待なしの閲覧が招待エラーへ落ちる構造を避ける | 同じLIFFを利用しつつ閲覧を別ページ/ルートへ分離。入口とliff.stateの共存を検証 |
| 別案b 起床対応リストを優先しカレンダーを後回し | 未採用。本人は両画面を希望しており、試験人数・開始日のレビュー内の記述も今回の仕様根拠にはしない | 起床状況とカレンダーの要件を維持。開発順は検証可能な単位に分けるがカレンダーを取り下げない |

## 再レビューしてほしい点

- 閲覧画面と、本人への催促・運営への通知の別工程が混同されていないか。
- 電話番号の通知許可と、全運営への一斉通知許可を混同していないか。
- richmenuswitchはサーバーの事前認可なく切り替わるため、古い表示が残る場合のAPI拒否と表示修正が十分か。
- LINE切替時の補助Webhookを、現在の表示の絶対的な正本にしていないか。
- 設計案と本人確定要件、実装済みと未実装を区別できているか。
