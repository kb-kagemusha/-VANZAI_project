# PAYGATE精算 在庫照合 パイロット記録テンプレート（Phase 0-Step1）

参照: `PAYGATE精算レシート OCR・在庫照合 計画書（改訂版 v4）` Phase 0

## 位置づけ

本ドキュメントは、実在庫入力の正式ルール（入力者・タイミング・修正権限）を確定する **前** に、
少数端末・数日分のデータで「通常取引数＝販売台数」という業務前提を検証するための、
**暫定・手動運用のパイロット記録テンプレート**です。

システム化（`inventory_snapshots` テーブルおよび入力UI）は Phase 2 で行うため、
このパイロット期間は本テンプレート（スプレッドシート or 本ファイルのコピー）に
事務局が手作業で記録することを想定しています。

## 実施しないと何が困るか（循環依存の解消）

- 実在庫入力の正式ルールを決めるには、実際にどんな差異パターンが出るかを見る必要がある
- 差異パターンを見るには、先に（暫定でよいので）実在庫記録を集める必要がある
- → 正式ルール確定を待たず、まず少数端末・数日で暫定記録を先行実施する

## パイロット対象（案・要事務局確認）

- 対象端末数: 2〜3端末（東京支社・武蔵野支社・商業施設から各1程度を推奨）
- 対象期間: 稼働日ベースで5〜10日分
- 記録者: 事務局（現場稼働者からの申告 or 現場での目視在庫確認）

## 記録項目（テンプレート）

| 項目 | 内容 | 記入例 |
|---|---|---|
| branch_id | 支社/現場コード | tokyo_shokuten |
| terminal_short_id | レシート記載の端末識別番号 | f353 |
| work_date | 稼働日（深夜またぎは前日扱い。詳細は下記ルール参照） | 2026-06-13 |
| staff_id | 稼働者（分かる範囲） | worker_042 |
| opening_count | 稼働開始時点の在庫数 | 20 |
| closing_count | 稼働終了時点の在庫数 | 12 |
| ocr_transaction_count | 精算レシートの通常取引数（後でOCR結果と突合） | 7 |
| inventory_decrease | opening_count - closing_count | 8 |
| diff | ocr_transaction_count - inventory_decrease | -1 |
| diff_reason_memo | 差異の推定理由（自由記述。販売以外の増減があれば必ず記入） | 破損1個 |
| entered_by | 記録者 | ops_tanaka |
| entered_at | 記録日時 | 2026-06-13 23:40 |
| note | その他気づき（複数精算の有無、レシート再発行の有無等） | 同日2回精算あり |

## 深夜またぎの稼働日判定ルール（暫定・Phase 0で検証）

精算時刻が **06:00未満** の場合、精算日の前日を稼働日（`work_date`）とする。
（例: 精算日 2026/06/14, 精算時刻 05:30 → work_date = 2026/06/13）

このルールは `src/services/ocr/work_date.py` に実装済み。パイロット期間中に実態と合わない
ケースが見つかった場合は `docs/decisions/DECISION_LOG.md` に理由付きで記録し、ルールを見直す。

## パイロットで確認すべき論点（Phase 0-Step2 で使用）

1. `通常取引数 = 販売台数` とみなせるか（複数台販売・返品・取消・テスト決済の影響）
2. 同一端末・同一稼働日に複数回精算が発生する頻度と典型パターン
3. `terminal_short_id` が支社をまたいで一意か（同じ短縮IDが別支社に存在しないか）
4. 差異が出た場合の典型的な原因分類（破損・紛失・移動・入力ミス・レシート不足等）

## 収集後のアクション

パイロットデータが集まり次第、Phase 0-Step2（`phase0-verification`）で上記論点を検証し、
その結果を踏まえて Phase 0-Step3（`docs/spec/OCR_INVENTORY_RECONCILIATION_SPEC.md`）の
正式ルールを確定する。
